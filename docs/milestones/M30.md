# M30 - Worldgen data foundations

**Status:** implemented locally on `dev/M30-worldgen-foundations` from `main` at
`7d656be` (`feat: M29 persistence hardening`). Local tag `m29` points at this
commit.
**Owning crates:** `mc-data` for sidecar inventory and narrow worldgen loaders,
`mc-worldgen` for deterministic Solaris-owned selectors and feature placement,
`mc-world` for generated chunk fallback and persistence interactions,
`mc-server` for config/seed/startup wiring, and `mc-test-harness` for generated
world regression coverage.

## Goal

Move worldgen from Solaris-only terrain toward data-driven overworld generation
foundations without copying Mojang algorithms. M30 should consume declarative
sidecar facts where ADR 0001 permits them, keep terrain and placement strategy
owned by Solaris, and make seed/config behavior explicit enough for long-running
survival worlds.

M30 is not vanilla worldgen parity. It should clearly separate sidecar-loaded
facts from independent approximations and leave parity-sized algorithms for later
reviewed slices.

## Current Foundation

M20/M21 already added the first worldgen seams:

- `mc-data` can load biome spawn rules, biome feature/tag membership, and placed
  plus configured ore feature facts from local `data/vanilla` sidecar files.
- `mc-worldgen` has deterministic terrain, biome buckets, caves, ores, surface
  decorations, and a narrow structure-template marker seam.
- `mc-server` wires sidecar-backed biome and ore rules when available and falls
  back to deterministic Solaris rules when the local sidecar is missing.
- Generated chunk overlays and heightmaps have flush/reopen coverage from the
  existing storage path.

M30 builds on those seams instead of replacing them with a vanilla algorithm
port.

## Strategy

1. Inventory sidecar worldgen data before adding loaders. Record what exists
   locally, what Solaris can safely consume as declarative facts, and what must
   remain out of scope because it encodes algorithmic behavior.
2. Keep loaders narrow and typed. Prefer small facts such as biome ids/tags,
   feature references, placement hints, configured block states, and template
   paths over a generic executor for vanilla's feature graph.
3. Make seed ownership explicit across config, server startup, world storage
   fallback, and tests. Generated chunks must be reproducible from config plus
   persisted edits.
4. Replace hardcoded decisions incrementally where the sidecar provides stable
   facts; document each remaining approximation in the milestone notes.
5. Preserve portable fallback behavior for fresh clones without Mojang data.
   Missing `data/vanilla` files should skip sidecar tests or fall back with clear
   logs, not panic in normal development.

## Risks / Pitfalls

- Vanilla worldgen JSON can describe algorithmic behavior that Solaris should not
  execute by translation. Keep the boundary at declarative facts and independent
  placement policy.
- Sidecar tests can become fake validation if they assert only synthetic fixture
  data. Prefer real local sidecar facts and clear skips when absent.
- Seed plumbing bugs can hide behind persisted chunks. Tests must distinguish
  generated fallback from already-flushed chunk data.
- Structure templates and extracted reports are Mojang bytes. Load them locally;
  never commit extracted payloads.
- Rich features can accidentally require cross-chunk mutation or expensive search.
  M30 should keep placement bounded and defer parity-sized pipelines.

## M30.c Loader Notes

`mc_data::worldgen_features` now loads every local placed feature and resolves its
paired configured feature into `WorldgenFeatureFacts`. The output is intentionally
plain data for Solaris-owned generation policy:

- placed feature id and referenced configured feature id;
- configured feature type id;
- placement modifier ids in source order;
- scalar placement hints: constant/uniform count, rarity chance, height range,
  heightmap name, and presence of a biome filter;
- referenced block-state `Name` identifiers found in the configured payload;
- referenced tag identifiers found in placed/configured payloads.

The loader does not execute placement modifiers, providers, predicates, tree
placers, processors, jigsaw pools, or noise functions. Unsupported shapes are
left as absent scalar hints while preserving the modifier/type ids for future
policy decisions.

Real-sidecar coverage currently asserts `minecraft:patch_grass_plain` resolves to
`minecraft:grass`, has `minecraft:simple_block`, count `32`, a biome filter,
`WORLD_SURFACE_WG`, `minecraft:short_grass`, and `minecraft:air` facts. Synthetic
coverage pins rarity, height range, heightmap, biome, block-state, and tag
extraction without requiring local Mojang data.

## M30.d Seed Notes

`example.toml` now describes `data.seed` as the deterministic Solaris generation
seed and calls out that persisted chunks in `world_dir` win over fallback
generation. This replaces the old M7-era baseline wording.

`mc-worldgen` now has `different_seeds_change_generated_chunks`, which compares
several sampled chunks generated from seed `0` and seed `1` and requires at least
one block difference. Existing determinism coverage still pins repeated
generation with the same seed and chunk position.

Additional M30.d coverage:

- `persisted_chunk_edit_wins_after_seed_change` writes an edit into a generated
  chunk with seed `0`, flushes it, reopens the world with seed `1`, and asserts the
  persisted edit wins over regenerated fallback terrain.
- Existing seed-`0` tests are intentional default-seed regressions and keep names
  such as `default_seed_origin_remains_land_spawn`.

## M30.e Biome / Noise Notes

Biome bucket construction remains the existing M21 seam: `mc-server` loads
`BiomeWorldgenData` from biome JSON plus `tags/worldgen/biome`, logs loaded biome
and tag counts, and builds `BiomeRules::from_worldgen_data` when the sidecar is
complete enough. Buckets backed by sidecar tags/data today include overworld,
deep ocean, ocean, beach/shore, river, taiga/cold, forest, badlands, savanna,
mountain/hill, jungle, and named cave-biome membership. Sparse buckets fall back
to the portable Solaris `BiomeRules::vanilla_overworld()` lists.

Terrain/noise remains deliberately Solaris-owned. Constants such as
`BASE_HEIGHT`, `HEIGHT_AMPLITUDE`, `CONTINENT_FREQUENCY`, `OCEAN_THRESHOLD`, cave
frequency, and ore spacing are independent policy values, not vanilla-derived
noise settings. The current local sidecar has no `worldgen/noise_settings`
directory, and M30 does not invent or translate that schema.

Tests covering the seam:

- `biome_rules_can_use_sidecar_tags` for sidecar-backed bucket construction.
- `every_overworld_biome_is_reachable_by_selector` for selector reachability.
- `continental_mask_produces_water_coasts_and_land_biomes` for fallback selector
  behavior.

## M30.f Feature Pipeline Notes

`mc-server` now loads `mc_data::worldgen_features::load_feature_facts` from local
`data/minecraft/worldgen` and passes the facts into
`TerrainGenerator::with_feature_facts`. Missing or invalid sidecar feature data
logs a warning and keeps the previous deterministic Solaris decoration fallback.

`mc-worldgen` consumes only scalar facts from the new loader:

- `minecraft:patch_grass_plain` can provide the grass decoration block state and
  a count-derived spacing hint.
- `minecraft:flower_plain` can provide flower block-state choices.
- `minecraft:patch_cactus` can provide the cactus block state.

Placement remains Solaris-owned: the existing bounded per-column decoration pass
decides candidate positions, biome buckets, surface constraints, heightmap refresh,
and dirty tracking. No vanilla placement modifier, provider, predicate, tree,
jigsaw, or processor algorithm is executed.

`feature_facts_drive_grass_decoration_block` proves a synthetic sidecar fact can
replace the grass decoration block used by the generator. Existing
`surface_decorations_are_visible_and_refresh_heightmaps` and
`generated_overlays_survive_flush_and_reopen` continue to prove visible overlays,
heightmaps, dirty tracking, and persistence.

## Scope Drift / M31 Handoff

M30 stayed inside the planned data-foundation scope. The main implementation
choice was to make visible decoration data-fed through `WorldgenFeatureFacts`
rather than starting a broader feature graph interpreter.

Remaining handoff items:

- Richer feature families can consume more `WorldgenFeatureFacts` entries, but
  should continue converting them into Solaris policy rather than executing the
  vanilla feature graph.
- Structure set and template-pool facts are inventoried but not consumed beyond
  the existing narrow template marker seam.
- Multi-noise biome source parameter lists are inventoried but not used for
  vanilla biome-source parity.
- Processor-list semantics, jigsaw behavior, vanilla terrain/noise formulas, and
  structure placement algorithms remain out of scope.
