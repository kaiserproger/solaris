# M22 - Gameplay survival loop

**Status:** planned on `dev/M22-gameplay-survival-loop` from local tag `m21`.
Manual gate remains disabled under the active YOLO-mode instruction; automated
cargo gates are authoritative unless the owner explicitly asks for PrismLauncher.
**Owning crates:** `mc-data` for vanilla sidecar readers, `mc-entity` for item
entity and pickup state, `mc-world` for block mutation and drop placement,
`mc-protocol` for verified inventory/use packets, `mc-net` for server-authoritative
player actions, and `mc-test-harness` for wire-level gameplay coverage.

## Goal

Make the first normal survival loop playable without claiming full vanilla parity:
survival block breaking becomes server-timed rather than instant, broken blocks can
drop item entities, pickups move stacks into authoritative inventory, held tools
affect mining through data-shaped rules, and eating at least one real food item
updates health/food state through verified packet paths.

Creative remains the instant-edit development path. Adventure and spectator remain
restricted until their full permission semantics are deliberately scoped.

## Strategy

1. Keep all gameplay authority on the server. Client block, inventory, and use-item
   claims either validate against server state or trigger a resync/ignore path.
2. Use data-shaped rules for hardness, drops, tools, durability, food, and recipes.
   Missing data falls back safely and visibly rather than inventing parity.
3. Verify every new packet ID/layout from `.analysis/protocol-dump.txt`, `javap`,
   or `wire-probe` before adding codec tests.
4. Land vertical slices that exercise real Play paths in `mc-test-harness`; avoid
   debug commands as acceptance proof for normal survival behavior.
5. Preserve existing M20/M21 terrain, entity, persistence, lighting, and block-edit
   behavior while tightening survival-only rules.

### M22.b - Timed survival mining seam

Replace instant survival break denial with server-tracked progressive breaking.
Creative keeps instant mutation; adventure and spectator keep rejecting mutation.

Acceptance:

- `START_DESTROY_BLOCK` in survival records a pending break instead of mutating the
  block immediately.
- Completion requires a server-approved elapsed tick budget for the target block,
  current gamemode, and held item.
- Aborting, switching target, changing gamemode, or changing the held item clears or
  invalidates the pending break.
- Existing creative block-edit harness coverage remains green.

### M22.c - Block hardness, tools, and durability rules

Add a narrow data-shaped mining rule table that can be fed by local vanilla data
later while providing deterministic fallback rules now.

Acceptance:

- Common blocks have explicit fallback hardness/drop/tool behavior.
- Held tools affect break speed or eligibility through rule data.
- Missing or unknown data uses a safe slow/no-special-tool fallback.
- Successful survival mining can damage tools through an inventory-authoritative
  seam without implementing enchantments.

### M22.d - Drops and item entity pickup

Produce server-owned item entities for at least one common broken block family,
tick them through existing runtime entity infrastructure, and pick them up into
the player's server inventory when intersecting.

Acceptance:

- Broken survival blocks can spawn item entities through the real world path.
- Item entities move/tick through the existing entity loop and are removed after
  successful pickup.
- Pickup merges into server-authoritative inventory slots where possible and leaves
  overflow in the world.
- Wire coverage verifies clients see spawn/update/remove behavior using verified
  packets only.

### M22.e - Food use loop

Add a server-authoritative use-item path for at least one edible item.

Acceptance:

- The server rejects or ignores eating attempts for non-food or missing stacks.
- Eating consumes one stack item, updates food/saturation state, and emits the
  verified health/food packet path.
- The same path works without debug commands.
- Missing food data falls back to a small explicit table rather than fake parity.

### M22.f - Recipe data foundation

Load shaped and shapeless recipe JSON into plain Solaris data for later
server-authoritative crafting. Execute the minimal crafting path only if packet
support is already verified within the slice.

Acceptance:

- `mc-data` parses real local vanilla recipe JSON without committing sidecar bytes.
- Portable tests cover parser behavior with small synthetic recipe JSON.
- Startup tolerates missing sidecar recipe data.
- If UI execution is deferred, the milestone doc records the exact packet oracle
  work remaining.

### M22.g - Death and respawn seam

Acceptance:

- Health-zero state is explicit in server survival state.
- Any respawn packet additions are oracle-pinned before implementation.
- If respawn is deferred, the server behavior and follow-up are documented.

## Risks / Pitfalls

- Survival mining can accidentally reintroduce client-authoritative edits. Keep
  mutation behind server completion and inventory/gamemode checks.
- Item entity packets may require new verified metadata. Do not guess; reduce the
  slice or add oracle capture first.
- Inventory resync can balloon into full container UX. Prefer narrow authoritative
  slots and tested ignore/resync paths.
- Food and recipes touch broad vanilla data. Parse data into small Solaris rule
  types instead of executing full vanilla semantics.
- Death/respawn packets are easy to get wrong. Land the dead-action guard even if
  verified respawn recovery is deferred.
