# M55 - Campfire cooking

**Status:** closeout complete; M55.a-b landed and M55.c documented the persistence deferral. Branch: `dev/M55-campfire-cooking`, cut from `main` at `m54` after recipe routing.
**Owning crates:** `mc-net` for campfire interaction/runtime state, `mc-world` if block-attached persistence needs a small storage hook, `mc-test-harness` for survival integration coverage, `docs` for readiness updates.

## Goal

Make campfires usable as a no-GUI survival cooking station: a player can place a
raw food item on a lit campfire, Solaris consumes one input item, waits the recipe
cook time from vanilla data, and drops the cooked result back into the world.

This closes the current readiness gap where campfire recipes are parsed but not
runtime-routed, and it gives players another visible survival loop without adding
new protocol shapes.

## Scope

- Detect `ServerboundUseItemOn` against `minecraft:campfire` and
  `minecraft:soul_campfire` block states.
- Accept only items that match loaded `minecraft:campfire_cooking` recipes.
- Consume exactly one matching input item from the used hand.
- Track up to four cooking slots per campfire position.
- Advance cooking from the server tick loop using each recipe's `cooking_time`.
- Spawn the cooked result as an item entity near the campfire and clear the slot.
- Keep the behavior deterministic and covered by a Solaris-only integration test.

## Non-Goals

- Campfire smoke, particles, sound, or visual item-on-campfire metadata parity.
- Exact vanilla item ejection vectors or randomized output motion.
- Campfire extinguish/relight behavior beyond respecting existing block identity.
- Hopper automation, comparator output, or block entity NBT parity.
- Persisting in-flight campfire cook slots across restart in M55.a.
- Any new packet layout based on memory or guessing.

## Strategy

1. Reuse the recipe loader's existing `RecipeKind::CampfireCooking` support and
   the recipe-routing helpers added for furnace/smoker/blast furnace work.
2. Add a minimal campfire runtime map keyed by block position. Each value stores
   four optional slots: input item id/count of 1, result item id/count, and ticks
   remaining.
3. In `UseItemOn`, before normal placement handling, check whether the clicked
   block is a campfire. If it is, attempt campfire insertion and stop normal
   placement only when an item was accepted.
4. Tick campfire cook entries from the existing play/session tick path. When a
   slot reaches zero, use the existing dropped-item/entity spawn path to emit the
   result and broadcast it to nearby players.
5. Add focused tests before broadening behavior: pure recipe/slot tests first,
   then one harness survival flow that places or uses a campfire, inserts raw
   food, waits for output, and observes the cooked item entity or pickup.
6. Update `docs/REPLACEMENT_READINESS.md` only at closeout once the integration
   gate proves the loop.

## Sub-Milestones

### M55.a - Runtime campfire cooking vertical slice

Status: landed in `b8d6ed0`.

Implementation target for the next subagent:

- In `mc-net`, add a campfire cooking runtime state owned by the same play/session
  layer that already owns furnace runtime updates.
- Add a helper similar in shape to the furnace cooking lookup that returns a
  `CampfireCooking` recipe for an input item id from loaded `RecipeKind` values.
- In the `ServerboundUseItemOn` handling path, when the clicked block id is
  `minecraft:campfire` or `minecraft:soul_campfire`, try to insert one held item
  into the first free campfire slot if a campfire recipe exists.
- On successful insert, decrement the held stack, send the normal slot update,
  record `ticks_remaining = recipe.cooking_time`, and do not place the held item
  as a block.
- On each server tick, decrement campfire slots; when a slot completes, clear it
  and spawn the recipe result as a dropped item at the campfire position using the
  existing item entity/drop broadcast helper.
- Add unit coverage for recipe matching, four-slot capacity, invalid item reject,
  and completion producing exactly one configured result.

Acceptance:

- Raw food with a loaded campfire recipe can be inserted into a lit campfire by
  right-clicking the campfire.
- Non-matching items are not consumed.
- A campfire accepts no more than four simultaneous cooking entries.
- Completion uses the vanilla-data recipe result and `cooking_time`; no hardcoded
  food table.
- Existing furnace/smoker/blast furnace behavior remains unchanged.
- Focused unit tests pass.

Landed notes:

- `UseItemOn` against `minecraft:campfire` and `minecraft:soul_campfire` inserts
  matching recipe inputs, consumes one held item, and rejects invalid or full
  campfires without consuming.
- Four volatile cooking slots are tracked per block in `SessionRegistry`, tick by
  `recipe.cooking_time`, and spawn the result item entity above the campfire.
- Replacing the campfire clears in-flight cooking state.
- Deferred: visual block-entity item metadata, persistence for in-flight cooking,
  vanilla timing parity beyond recipe `cooking_time`, and smoke/sound particles.
- Focused gate passed: `cargo test -p mc-net campfire -- --nocapture`; fmt check
  passed.

Suggested focused gate:

```sh

```

### M55.c - Persistence and closeout

Status: closeout complete.

Acceptance:

- Decide whether campfire in-flight cook slots belong in existing block storage or
  remain documented as volatile runtime state for now.
- If a small persistence hook fits existing world/container storage, persist
  in-flight slots across save/restart; otherwise document the deferral explicitly.
- Update `docs/REPLACEMENT_READINESS.md` from partial to ready or partial with the
  exact claim that landed.
- Fill the What Landed Where table.
- Baseline validation passes.

Landed notes:

- Persistence for in-flight campfire slots is deferred. M55 stores runtime slots in
  `SessionRegistry`, and Solaris does not yet implement visual campfire block-entity
  item metadata, so an isolated persisted slot format would be premature.
- Future persistence should be designed together with block-entity parity for
  campfires rather than inventing M55-only save data.
- Readiness is documented as usable partial support: matching held inputs cook into
  dropped item entities, while visual metadata, restart persistence, smoke/sound,
  exact ejection vectors, and hopper/comparator automation remain unclaimed.

## Protocol and Data Oracles

- No new protocol packet IDs or field layouts are expected for M55.a-b. Use the
  existing verified `ServerboundUseItemOn`, slot update, block update, and item
  entity spawn paths.
- Vanilla data sidecar is required: `data/vanilla/` must include recipes so
  `minecraft:campfire_cooking` entries drive accepted inputs, outputs, and cook
  times.
- If M55 later attempts visual item-on-campfire block entity parity or exact
  clientbound block entity updates, first capture the behavior with
  `wire-probe`/`.analysis/server.jar` and cite the dump per ADR 0002.

## Risks

- Campfire visual parity may require block entity packets; defer visuals rather
  than guessing packet content.
- Runtime state keyed only by position can go stale if the campfire block is
  broken or replaced; clear slots on block change/removal.
- Existing dropped-item helpers may assume player/block-break causes; keep the
  spawn path small and deterministic.
- Cook timing can make harness tests slow if they wait the full vanilla duration;
  prefer a test-local recipe fixture or tick helper if the existing harness
  already supports one, without hardcoding production behavior.
