# M60 - Sapling tree growth

**Status:** Closed locally; M60.a through M60.e landed. Branch:
`dev/M60-sapling-tree-growth`, cut from `main` after M59 closeout.
**Owning crates:** `mc-net` for sapling growth planning, random-tick and
bonemeal integration, multi-block edits, and focused tests; `mc-test-harness`
for Solaris-only survival coverage; `docs` for readiness updates at closeout.

## Goal

Make planted saplings produce visible trees in normal survival play, starting
with a deliberately small oak-sapling vertical slice.

M57 through M59 made farming useful: crops grow, bonemeal works on crops, and
harvest drops are visible. M60 applies the same replacement-readiness approach
to trees: use existing block updates, block registries, random ticks, bonemeal
consumption, relight, and harness paths instead of guessing protocol effects.

## Scope

- Add deterministic Solaris sapling growth for `minecraft:oak_sapling` first.
- Reuse existing `RandomTickFamily::Sapling`; it is already classified but is
  currently a no-op.
- Reuse existing `ServerboundUseItemOn` bonemeal handling and held-slot sync.
- Replace a sapling with a small generated tree through the existing block-edit
  batch path.
- Resolve block states from the loaded block registry by namespaced id and
  properties, never by hardcoded numeric block state ids.
- Generate only stable block states already understood by the client: oak logs,
  oak leaves, and air checks.
- Keep the shape deterministic and documented as Solaris-owned, not vanilla
  tree-feature parity.
- Add focused `mc-net` tests first; add a Solaris harness test once the oak
  bonemeal slice is stable.

## Non-Goals

- Vanilla tree-feature, RNG, foliage placer, decorator, bee-nest, or biome parity.
- Two-by-two saplings, giant trees, azalea trees, mangroves, mushrooms, bamboo,
  chorus plants, cactus, sugar cane, or stem-crop expansion.
- Exact light/soil/survivability rules beyond simple free-space checks.
- Particles, sounds, statistics, advancements, game events, or level-event
  effects for bonemeal or tree growth.
- New packet IDs, packet field layouts, entity metadata, custom payloads, or
  guessed clientbound effects.
- Leaf-distance propagation as a general world system. M60 may choose explicit
  stable leaf states for generated trees, but broad leaf-update parity remains
  deferred.

## Strategy

1. Keep M60.a on verified paths: a player uses bonemeal on a sapling, Solaris
   plans block edits, applies them through the existing batch path, sends normal
   block updates/acks, then consumes one bonemeal only after success.
2. Support only `minecraft:oak_sapling` in the first slice. Other saplings should
   acknowledge bonemeal as unsupported and must not consume bonemeal or mutate
   blocks.
3. Generate a small deterministic oak tree with a four-block `minecraft:oak_log`
   trunk and a compact `minecraft:oak_leaves` canopy above it.
4. Require the replaceable volume to be air, except the source sapling position.
   If the tree does not fit, do not edit blocks and do not consume bonemeal.
5. Use named block-state lookup helpers for:
   - `minecraft:oak_log`, preferably with `axis=y` when that property exists;
   - `minecraft:oak_leaves`, preferably with stable non-decaying properties such
     as low `distance` and `persistent=false`, or `persistent=true` if a low
     distance state cannot be resolved from the loaded registry;
   - `minecraft:air` for occupancy checks.
6. Keep all shape rules local to a small sapling-growth helper so later slices
   can add more species without touching unrelated block-break or crop logic.
7. After M60.a, wire random ticks for oak saplings to the same planner so trees
   can grow without bonemeal.
8. Extend to common one-by-one saplings only after the oak path and tests are
   green.
9. Update `docs/REPLACEMENT_READINESS.md` only at closeout with the exact tree
   growth claim that landed.

## Sub-Milestones

### M60.a - Oak sapling bonemeal vertical slice

Target for immediate implementation:

- Add a sapling-growth planner for `minecraft:oak_sapling`.
- When a survival player uses `minecraft:bone_meal` on an oak sapling and the
  target volume is clear, replace the sapling with a deterministic small oak
  tree using existing block edits:
  - trunk: `minecraft:oak_log` at the sapling position through three blocks
    above it, total height 4;
  - canopy: `minecraft:oak_leaves` centered around the top of the trunk, limited
    to a compact radius that fits in currently loaded blocks and avoids chunk
    boundary complexity in the first slice.
- Resolve all block states by namespaced id and properties through the loaded
  block registry. Do not use numeric state ids.
- Consume exactly one bonemeal only after the block-edit batch applies at least
  one tree-growth edit successfully.
- If the held item is not bonemeal, the target is not `minecraft:oak_sapling`, a
  required block state is missing, or the target volume is obstructed, do not
  consume bonemeal and do not mutate blocks.
- Preserve existing crop bonemeal behavior unchanged.
- Preserve current sapling random-tick no-op behavior until M60.b.
- Add focused `mc-net` tests proving successful oak bonemeal creates logs and
  leaves, consumes one bonemeal, obstructed growth is a no-op, unsupported
  saplings are no-op, missing block states are safe, and crop bonemeal
  regressions still pass.

Acceptance:

- A player can plant or target an oak sapling, use bonemeal, and see a small oak
  tree appear through normal block updates.
- Bonemeal is decremented only after successful tree growth.
- Obstructed or unsupported targets do not consume bonemeal.
- Crop bonemeal still advances supported crops one age and mature crops still do
  not consume bonemeal.
- No new packet IDs, field layouts, entity metadata, particles, sounds,
  statistics, game events, or level events are introduced.
- Focused `mc-net` tests pass.

Suggested focused gate:

```sh
cargo test -p mc-net sapling -- --nocapture
cargo test -p mc-net bonemeal -- --nocapture
cargo fmt --all -- --check
```

Landed locally:

- Bonemeal on a clear `minecraft:oak_sapling` creates a deterministic small oak
  tree through the existing block-edit batch path.
- The tree planner resolves `minecraft:oak_log`, `minecraft:oak_leaves`, and
  `minecraft:air` states from the loaded block registry instead of numeric state
  ids.
- Growth requires a clear target volume and consumes exactly one bonemeal only
  after applied edits.
- Existing crop bonemeal behavior is preserved.
- Sapling random ticks remained no-op until M60.b.
- Focused gates passed: `cargo test -p mc-net sapling -- --nocapture`,
  `cargo test -p mc-net bonemeal -- --nocapture`, and
  `cargo fmt --all -- --check`.

## Protocol and Data Oracles

- M60 must not add new packet IDs or field layouts. It reuses existing
  verified use-item-on, block update/ack, inventory slot sync, relight, registry,
  and world-storage paths.
- No `wire-probe` or `javap` oracle is required for M60 because particles, sounds,
  statistics, game events, level events, new metadata, and new clientbound
  effects remain deferred.
- Vanilla data sidecar is required for block registries. Sapling, log, leaf, and
  air block states must be resolved from namespaced block ids and properties, not
  numeric block state ids.
- Tree shape, height, and canopy layout in M60 are Solaris-owned deterministic
  rules, not a translation of Mojang tree-feature algorithms.
- If a later slice attempts exact vanilla tree features, bonemeal effects,
  particles, sounds, statistics, game events, level events, bee nests, or new
  metadata, first capture or cite the needed behavior from the local oracle per
  ADR 0002 and keep Mojang data files as runtime input per ADR 0001.

## Risks

- Multi-block tree edits touch more blocks than crop growth. Keep M60.a's shape
  compact, avoid chunk-boundary complexity, and prove obstruction behavior.
- Leaves may decay if generated with inappropriate `distance`/`persistent`
  properties. Resolve explicit stable leaf states and test they are not immediate
  `distance=7` decay candidates.
- Bonemeal handling currently returns early for crop growth. The sapling path
  must preserve crop behavior and consume only after successful sapling edits.
- Relight cost is higher than a one-block crop update. Reuse existing block-edit
  batch relight behavior and avoid per-block ad hoc light updates.
- A deterministic small oak tree is visibly useful but not vanilla parity. Keep
  readiness language clear that this is scoped replacement-readiness gameplay,
  not exact feature generation.
- Harness block-update ordering can be noisy for many edits. Assert final block
  states and held-slot changes rather than every packet ordering detail.
