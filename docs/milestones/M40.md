# M40 - Water locomotion and visible drops recovery plan

**Status:** implemented locally on the dirty local M39/M40 worktree; automated
focused gates pass, owner PrismLauncher manual confirmation is still pending.
**Owning crates:** `mc-net` for play-state movement, entity simulation, item
pickup/drop timing, and session dispatch; `mc-physics` for fluid classification
and entity body stepping; `mc-protocol` for missing serverbound/clientbound packet
shapes; `mc-test-harness` for wire-level reproduction; `docs` for this recovery
plan.

## Goal

Make three owner-observed manual issues reproducible, explainable, and fixed
through real vanilla-client behavior instead of speculative patching:

- Players enter water but move as if walking along the bottom instead of swimming.
- Water mobs do not swim or float naturally.
- Broken blocks do not leave visible collectible drops in normal play.

M40 is not a broad aquatic update. It does not claim boats, bubble columns,
drowning, oxygen, tridents, guardians, fish schooling, currents, or full vanilla
movement parity. The scope is the minimum replacement-server behavior needed for
a vanilla 26.1.2 client to swim in water, see aquatic/passive mobs react to water,
and see/pick up block drops after survival mining.

## What I Tried And Why It Was Insufficient

The local attempt after the manual report touched real code paths and passed the
automated baseline, but the owner correctly reported that it did not solve the
manual symptoms. Treat these as investigation notes, not shipped fixes.

Attempted changes:

- `mc-physics::BlockMaterialIds` was changed from one optional water/lava state to
  vectors of fluid states.
- `mc-net::server::material_ids` was changed to derive all water/lava states from
  `BlockFactsTable` for entity physics sampling.
- `mc-protocol` gained `ServerboundPlayerCommand` decoding for the command packet
  that includes sprint start/stop.
- `mc-net::play` stored a `PlayerPose::sprinting` flag from
  `ServerboundPlayerCommand::{StartSprinting, StopSprinting}`.
- Item entities got a short pickup delay, and `pickup_nearby_items` started
  running from the 50ms play tick instead of only immediately after selected drop
  spawn sites.

Why this was not enough:

- The player swimming symptom was not reproduced with a protocol capture before
  patching. Storing a sprinting flag is not useful unless the server also handles
  the vanilla swim/sneak/input/pose contract that makes the client stay in the
  swimming state.
- The own-player movement path currently trusts client positions and only applies
  selected survival side effects. There is no authoritative player-fluid state,
  fluid drag, swim pose metadata, eye-in-fluid tracking, or correction path.
- The server likely lacks one or more protocol-visible signals the client expects
  for swimming: player command actions, player input, entity metadata pose, shared
  flags, or fluid tag/height semantics. M40 must verify this from Mojang bytecode
  and wire captures, not from memory.
- Mob physics and mob AI are conflated. Recognizing fluid blocks can make the
  physics sampler aware of water, but land mobs, fish, squid, and hostile mobs need
  different water goals, buoyancy, drag, target depth, and despawn/ground rules.
- The drop change made item pickup more plausible in tests, but it did not prove
  that a manual player sees an item entity long enough in the exact break path the
  owner used. Visibility, spawn packet ordering, pickup delay, and inventory slot
  updates need a manual-style harness.
- Passing `cargo test --workspace` and clippy only proved no existing tests broke.
  Existing tests did not encode the failed manual water behavior.

## Current Foundation

- Server-owned entities already have a physics tick and basic `BlockMaterial`
  classification in `mc-physics`.
- The play handler accepts client movement packets and tracks `PlayerPose`, but it
  does not simulate player movement as an entity body.
- Block breaking already has a survival-timed path, block replacement, item stack
  lookup through loot data, item entity spawn, pickup, and inventory slot updates.
- `mc-test-harness` can connect over real TCP and assert packet order, but current
  tests do not drive a vanilla-style underwater movement sequence.
- ADR 0002 still applies: any new packet id, metadata serializer, field layout, or
  enum must be verified from `.analysis/protocol-dump.txt`, `javap`, or a
  `wire_probe` capture against vanilla.

## Strategy

1. Reproduce first, then patch. No M40 gameplay change lands without a failing
   harness or a saved manual-wire capture that explains the defect.
2. Separate player swimming, mob water behavior, and drop visibility. They share
   water/drop observations, but they are different runtime systems.
3. Verify protocol shape from local Mojang artifacts before adding or changing
   packet handling.
4. Prefer minimal server behavior that makes the vanilla client behave correctly;
   do not build a full movement engine unless the capture proves it is required.
5. Keep manual gates explicit. If PrismLauncher behavior differs from harness
   behavior, the manual observation wins and the harness must be improved.

## Risks / Pitfalls

- Client swimming may be mostly client-predicted, but the server can still cancel
  it by missing command/input/metadata responses. M40 must identify the exact
  cancellation path before patching.
- Entity metadata indices are version-sensitive. Adding guessed pose/shared-flag
  metadata will create worse client desyncs.
- Making all mobs buoyant can break hostile combat and land-mob movement. Aquatic
  and non-aquatic behavior must be separated if tests show different needs.
- A pickup delay that is too long feels laggy; a delay that is too short hides the
  item entity. The acceptance gate is a visible window plus fast collection, not a
  hardcoded vanilla-perfect tick count.
- Existing automated tests are currently weaker than the owner manual gate for
  this area. M40 must improve tests instead of arguing from green CI.

## M40 Implementation Notes

Local oracle checks:

- Extracted `META-INF/versions/26.1.2/server-26.1.2.jar` from
  `.analysis/server.jar` into `%LOCALAPPDATA%/Temp/opencode/` for `javap`.
- Verified `ServerboundPlayerInputPacket` delegates to
  `net.minecraft.world.entity.player.Input.STREAM_CODEC`.
- Verified `Input$1` is one byte with bits: forward `0x01`, backward `0x02`,
  left `0x04`, right `0x08`, jump `0x10`, shift `0x20`, sprint `0x40`.
- Verified entity metadata uses `Entity.DATA_SHARED_FLAGS_ID` before other base
  accessors and `Entity.DATA_POSE`; `EntityDataSerializers` registers `BYTE` as
  serializer `0` and `POSE` as serializer `20`; `Pose.SWIMMING` id is `3`.

Implementation slice:

- Added `ServerboundPlayerInput` decoding and tests in `mc-protocol`.
- Extended `ClientboundSetEntityData` support to byte and pose metadata, keeping
  existing item-stack metadata for item entities.
- `PlayerPose` now tracks last player input, sprint/shift, water overlap,
  eye-in-water, and swimming pose. Movement/input/command packets refresh water
  state from the real world storage and block-facts fluid table.
- The server now sends own-player and observer-visible pose/shared-flag metadata
  when sprint-swimming or crouching state changes.
- Survival fall damage and farmland trampling are suppressed while the previous
  or new player pose overlaps water.
- Existing M39/M40 local item-drop code keeps a 4-tick pickup delay and periodic
  50 ms pickup scan, so survival mining can spawn item metadata before pickup.
- The survival block-drop harness now fails if the item spawns before the break
  update/ack or if pickup/removal arrives before a short visible window after item
  metadata.

Follow-up local recovery slice after the owner re-tested and reported that player
swimming and visible water physics were still not working:

- Added a minimal player water-motion assist in `mc-net`: `ServerboundPlayerInput`
  in water now produces `SetEntityMotion` for the local player from yaw, pitch,
  forward/back/strafe, sprint, jump, and shift. This is a visible-motion aid, not
  a full authoritative player movement engine.
- Added `mc-entity::GoalState::AquaticWander` so fish/water mobs no longer use the
  same horizontal land-wander goal as cows. The new goal sets 3D velocity,
  disables `on_ground`, and updates pitch/yaw/head-yaw from the swim vector.
- `mc-net` now assigns aquatic wander to water mob spawns and to restored persisted
  aquatic entities (`cod`, `salmon`, `tropical_fish`, `pufferfish`, squid-like
  mobs, dolphins, axolotls, turtles).
- Aquatic entity relative movement now also sends `SetEntityMotion`, so clients see
  velocity updates after spawn instead of only sparse position/rotation deltas.
- Water herd spawning was adjusted to use all water fluid states and choose the
  middle of the best water column instead of the top surface block.
- Added unit coverage for player water motion, aquatic wander, restored aquatic
  goals, water-spawn column selection, and spawn-plus-relative-move suppression for
  newly visible observers.
