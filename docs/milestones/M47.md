# M47 - Fluid and falling-block parity

**Status:** agent-side complete on `dev/M47-fluid-falling-parity`.
**Owning crates:** `mc-world` for scheduled tick persistence, `mc-net` for runtime
block/fluid edits and packet dispatch, `mc-physics` for falling/fluid intent
primitives, `mc-test-harness` for vanilla and Solaris observations.

## Goal

Finish the M44-deferred block/fluid physics cases with capture-backed changes:
underwater breaking, water/lava replacement, source/flowing spread timing,
scheduled fluid ticks, and falling-block start behavior.

## Scope

- `water-lava-replacement` vanilla capture and Solaris comparison.
- Underwater block breaking replacement/drop behavior.
- Source/flowing water and lava spread for a small bounded fixture.
- Scheduled fluid tick persistence and timing in loaded chunks.
- `sand-gravel-fall-start` for sand, gravel, and anvil start/update behavior.

## Non-Goals

- Full vanilla fluid simulation.
- Redstone, pistons, bubble columns, cauldrons, boats, or pathfinding.
- Performance rewrites unless a scoped parity test regresses tick budgets.

## Strategy

1. Capture vanilla fluid/falling-block windows before changing runtime behavior.
2. Keep captures local and cite packet/world-state observations in docs/tests.
3. Add real play-path Solaris regressions for each fixed behavior.
4. Preserve M44 sugar-cane and item-drop behavior while changing fluid/block edits.

## M47.a/M47.b Capture Notes

Local vanilla captures produced by `wire-probe`:

- `.analysis/physics-oracles/water-lava-replacement.vanilla.capture`
- `.analysis/physics-oracles/sand-gravel-fall-start.vanilla.capture`

The falling-block capture shows support break -> `BlockChangedAck` ->
`AddEntity(type_id=51, data=<block state>)` at the block center -> source block
to air, followed by landing block updates and `RemoveEntities`. The fluid capture
is narrower: ordinary dirt next to water breaks to air immediately; broad fluid
spread timing remains out of scope until a smaller assertion window is selected.

## M47.c/M47.d Runtime Notes

Runtime falling-block start is implemented for sand, red sand, gravel, and anvil
variants when a block edit removes their support into air/fluid. Solaris clears
the source block, broadcasts the block update, and spawns `minecraft:falling_block`
with the removed block-state id in `AddEntity.data`, matching the captured start
window. Falling entity landing is still handled only by generic entity physics;
full landing placement parity remains deferred.

Scheduled fluid tick storage/persistence was already present before this slice;
this change leaves broad fluid simulation untouched except for the new capture
tooling and documentation.

## M47.e Closeout

Mapped fixes:

- Falling-block start: backed by the vanilla `sand-gravel-fall-start` capture,
  mirrored by the Solaris `physics_validation` real play-path regression. Solaris
  clears the support, clears the falling source, and emits `AddEntity` with the
  captured block-state id in entity data.
- Falling-block persistence/wire shape: `minecraft:falling_block` entities carry
  their block state through in-memory snapshots, persisted entity NBT, and
  clientbound spawn packets.
- Fluid oracle tooling: `water-lava-replacement` is now captured locally and
  documented as a narrow block-edit observation rather than broad simulation
  parity evidence.

Deferred:

- Full falling-block landing placement/removal parity remains future work.
- Broad fluid spread/lava-water interaction parity remains future work pending a
  smaller vanilla-backed assertion window.

## Risks

- Fluid spread can explode edit counts if budgets are not preserved.
- Falling blocks may need new entity packet/layout support; do not guess IDs or
  metadata.
- Underwater breaking touches drops, replacement states, and client acks in one
  path.
