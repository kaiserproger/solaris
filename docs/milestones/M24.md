# M24 - Survival loop parity

**Status:** in progress on `dev/M24-survival-loop-parity` from local tag `m23`.
**Owning crates:** `mc-world` for typed block-entity storage and persistence,
`mc-net` for shared container execution and viewer sync, `mc-protocol` for any
new verified packet codecs, `mc-data` for repo-owned gameplay tables, and
`mc-test-harness` for wire-level survival coverage.

## Goal

Move the M23 survival MVP toward a full survival loop parity slice without
turning M24 into a broad vanilla rewrite. The first coherent target is shared
furnace block-entity state: furnace contents, burn/cook progress, and viewers
must be world-owned rather than per-connection state.

M24 should leave the server playable after every slice. Each implementation
slice must keep cargo gates green and add focused harness coverage for the new
behavior.

## Strategy

1. Start with the smallest high-value state-ownership correction: move furnace
   state from per-connection `InteractionState` into shared world/block-entity
   storage keyed by block position.
2. Keep client-local runtime fields (`container_id`, `state_id`, carried stack,
   and open-window mapping) in `mc-net`; move durable gameplay state into
   `mc-world`.
3. Preserve the verified M23 furnace wire flow first: `OpenScreen`,
   `ContainerSetContent`, `ContainerSetData`, and `ContainerClick` remain the
   baseline unless a new packet is verified from local oracles.
4. Persist typed furnace state through the existing Anvil chunk save/load path,
   while continuing to pass through unknown block entities without inventing
   structure.
5. Add multiplayer correctness only after shared state exists: concurrent viewers
   of the same furnace must see the same slots and progress through their own
   container ids.
6. After furnace state is shared and persistent, move to the next survival loop
   gaps in small verified slices: real crafting-table menus, use-duration food,
   and one hostile-mob pressure path.

### M24.b - Shared furnace block-entity storage

Move furnace slots and burn/cook progress out of per-connection
`InteractionState` into shared world storage keyed by block position.

Acceptance:

- `mc-world` exposes a typed furnace block-entity model or accessor that stores
  three furnace slots plus burn/cook fields, without client-local container ids.
- `mc-net` active furnace windows reference a block position and keep only
  per-viewer runtime state locally.
- Closing and reopening the same furnace in one server runtime preserves slots
  and progress through world-owned state, not connection-owned maps.
- Existing furnace click/smelt harness coverage remains green and is updated to
  exercise the shared-state path.

### M24.c - Furnace persistence

Persist typed furnace contents and progress through save/restart using the
existing chunk storage path.

Acceptance:

- Furnace block-entity state marks the containing chunk dirty when slots or
  progress change.
- Save/load preserves furnace input, fuel, output, burn remaining/total, and cook
  progress/total where the on-disk schema supports them.
- Unknown block-entity payloads continue to round-trip without Solaris claiming a
  typed shape it does not understand.
- A focused storage or harness test proves furnace state survives flush and reload
  through real `WorldStorage` code.

### M24.d - Concurrent furnace viewers

Let multiple connected clients view and mutate the same furnace block entity with
shared slots/progress and per-viewer container ids.

Acceptance:

- Opening a furnace registers a viewer by block position and unregisters on close,
  disconnect, or container switch.
- Slot/progress changes broadcast to all current viewers using each viewer's own
  `container_id` and state tracking.
- Concurrent click handling remains server-authoritative and does not trust client
  changed-slot or carried-stack hints for mutation.
- A two-client harness test proves one client can insert input/fuel and the other
  observes the same content/progress/output.

### M24.e - Crafting table menu and result slot

Replace the M23 `PlaceRecipe` shortcut path with a real crafting-table container
slice when protocol facts are verified.

Acceptance:

- Any new packet ids, menu types, or recipe-display fields are verified from local
  26.1.2 oracles before implementation.
- The server opens a crafting-table menu for the matching block interaction and
  maintains a 3x3 input grid plus result slot server-side.
- Taking the result consumes ingredients, returns container items where supported,
  and resyncs the window through verified packets.
- At least one shaped and one shapeless recipe flow are covered by focused tests,
  using repo-owned data or local sidecar loaders rather than hardcoded `mc-net`
  constants.

### M24.f - Food use durations

Replace instant food use with start/finish/cancel semantics and data-driven food
values.

Acceptance:

- Food nutrition/saturation comes from `mc-data` repo-owned data or a documented
  loader, not fallback arrays in `mc-net`.
- Eating requires a use duration and can be canceled/interrupted before applying
  food stats.
- Hunger/exhaustion remains server-authoritative and existing regen/starvation
  behavior keeps passing.
- Focused harness coverage proves early cancel does not consume food and completed
  use does.

### M24.g - Hostile mob pressure slice

Acceptance:

- Hostile AI acquires a player target, approaches, and applies melee damage with a
  server-side cadence and reach check.
- Existing armor mitigation and durability paths apply to hostile damage.
- A focused harness test covers hostile damage and killing the mob for a drop.

## Risks / Pitfalls

- Furnace state can accidentally remain cloned per connection. Runtime windows
  should hold references/positions plus per-viewer ids, not owned furnace copies.
- Borrowing shared world state from `mc-net` can balloon quickly. Prefer narrow
  storage accessors over exposing chunk internals.
- Persistence must not discard opaque vanilla block entities. Typed furnace support
  should coexist with the existing pass-through behavior.
- Multi-viewer sync can mix container ids. Broadcast code must render each update
  per viewer instead of reusing one client's id/state.
- New crafting packets and recipe ids are protocol-sensitive. Verify from local
  oracles before adding codecs or tests.
- Do not hardcode vanilla gameplay constants in `mc-net` when a `mc-data` table or
  loader is practical.

## Furnace NBT Oracle Notes

M24.c pins the minimal furnace disk shape from local `javap` metadata against
`.analysis/extracted/META-INF/versions/26.1.2/server-26.1.2.jar`:
`AbstractFurnaceBlockEntity` saves `Items`, `lit_time_remaining`,
`lit_total_time`, `cooking_time_spent`, and `cooking_total_time`; item entries
use `ItemStackWithSlot` with `Slot`, `id`, and `count`. Solaris persists those
fields and deliberately omits `RecipesUsed` until XP-award recipe history is
implemented.
