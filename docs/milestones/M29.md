# M29 - Persistence hardening

**Status:** implemented locally on `dev/M29-persistence-hardening` from `main`
at `46c58e6` (`refactor: split large play modules`). Local tag `m28` points at
`ac876f6`; M29 intentionally started after the post-M28 play-module refactor so
the persistence work could use the smaller module layout.
**Owning crates:** `mc-world` for Anvil/world metadata, chunk dirty tracking,
block entities, simulation queues, and entity storage; `mc-net` for player
session lifecycle, save/shutdown hooks, and runtime entity ownership;
`mc-protocol` only if restart coverage exposes missing packet shapes; and
`mc-test-harness` for real-storage restart tests.

## Goal

Make world, player, entity, and simulation persistence robust enough for
long-running survival worlds and crash-aware shutdown.

M29 is not full vanilla NBT parity. It should persist the survival-visible state
Solaris owns today, preserve unknown payloads it does not understand, and report
save failures clearly instead of silently discarding dirty state.

## Strategy

1. Verify Anvil/player/entity field names before writing new persistent fields.
   Acceptable sources are local world files, minecraft.wiki, and local 26.1.2
   metadata oracles; do not infer NBT names from memory.
2. Preserve unknown NBT at every boundary. Solaris may update owned fields, but
   unmodeled block-entity, entity, player, and chunk metadata must round-trip.
3. Prefer narrow persistence seams over broad schema frameworks. Add a shared
   abstraction only when at least two real save paths need it.
4. Test restart behavior through real temporary storage paths. In-memory fixtures
   are useful for unit edges, but acceptance depends on data surviving process-like
   teardown and reload.
5. Harden flushing before adding more state. A dirty object without a visible save
   path or error report is a data-loss bug.

## Risks / Pitfalls

- NBT naming mistakes can create worlds that look saved but are unreadable by
  later Solaris code. Verify field names before writing.
- Save paths can appear correct while connection-local state still owns the real
  data. Runtime ownership must be explicit before persistence is trusted.
- Unknown NBT loss is easy when rewriting player/entity/block-entity compounds.
  Preserve raw payloads unless Solaris owns the exact shape.
- Dirty tracking bugs are data-loss bugs. Every mutation path added in M27-M28
  should have a clear mark-dirty path or a reason it does not need one.
- Restart tests can pass by construction if they bypass storage. Use real temp
  directories and reload through the same code paths used by the server.

## Oracle Notes

M29.b pinned the first persistence fields before code wrote them:

- Player files use vanilla's `playerdata/<uuid>.dat` gzip-compressed named NBT
  location. Field names used by M29.c are the vanilla player data names documented
  by minecraft.wiki's player.dat format and cross-checked against the current
  Solaris runtime model: `Pos` as three doubles, `Rotation` as two floats,
  `OnGround` as byte, `playerGameType`, `Health`, `foodLevel`,
  `foodSaturationLevel`, `foodExhaustionLevel`, `SelectedItemSlot`, `Inventory`,
  `SpawnX`, `SpawnY`, `SpawnZ`, `SpawnAngle`, `XpLevel`, `XpP`, `XpTotal`, and
  `XpSeed`.
- Player inventory uses the vanilla `Inventory` list of item compounds with
  `Slot`, `id`, and `count`. The item id/count shape is the same shape already
  verified for chest block entities in M28. Solaris preserves unmodeled root keys
  and per-item keys while updating the owned fields. The only modeled component is
  `components.minecraft:damage`, matching the M23 local class-oracle component
  work.
- Runtime entity persistence uses a Solaris-owned `solaris/entities.dat` gzip NBT
  file rather than pretending to implement vanilla entity region files. Individual
  entity compounds use vanilla-shaped field names where Solaris owns the data:
  `id`, `UUID`, `Pos`, `Motion`, `Rotation`, `OnGround`, `Health`, `Age`,
  `PickupDelay`, and item-entity `Item` with `id`/`count`. `SolarisEntityId` is an
  explicit project-owned field for stable runtime entity ids.
- World metadata uses Solaris-owned `solaris/world.dat` gzip NBT. It persists
  `SolarisWorldTime`, driven by the server entity tick cadence, and
  `SolarisWorldIdentity`, currently the configured world root path. Bind logs a
  mismatch if the stored identity differs from the configured root. Weather is not
  persisted because Solaris has no authoritative runtime weather state yet.

M29.c now loads player state during Play login when a world root is available,
uses it for the initial position, gamemode, selected slot, inventory, and survival
health packet, mirrors runtime state into a persistence snapshot during Play, and
writes it back on Play exit. Load/save errors are logged with player context;
unknown player root fields and unchanged item payload fields are preserved.

M29.d now loads persisted entities at network bind and restores them into the
shared `SessionRegistry` before clients connect. The entity tick task writes live
entity snapshots once per second so dropped items and living entities have a real
storage path across restart. Loaded entity chunks are marked as already spawned so
passive herd generation does not duplicate the same chunk after restart.

M29.e keeps chunk-scoped simulation queue persistence on the existing Anvil path:
scheduled block ticks, scheduled fluid ticks, chest block entities, and furnace
block entities already have real flush/reopen coverage in `mc-world`. M29 adds the
missing world-level metadata file for world time and identity.

M29.f adds an internal save-all path behind `mc_net::SaveHandle`. Shutdown now
binds the server explicitly, keeps a save handle, and on Ctrl-C saves active
player snapshots, server entities, world metadata, then dirty chunks. The report
accumulates contextual errors (`player <uuid>`, `entities`, `world metadata`, or
`dirty chunks`) and shutdown returns an error if any save step fails. Public
`/save-all` command UX remains a follow-up; the internal hook is now present.

M29.g adds real temporary storage coverage for playerdata, entity storage, world
metadata, and save-all. Existing `mc-world` tests continue to cover edited chunks,
fluid ticks, scheduled ticks, furnaces, and chests through flush/reopen paths.
