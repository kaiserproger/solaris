**Estimate:** 60–100 h (PROJECT_SPEC §9 Phase 1, "Chunks + entities

**Owning crates:** `mc-protocol` (one new clientbound packet), `mc-net`

`WorldStorage`/`BlockRegistry` it already opens with `mc-net`.

## Goal

Make a vanilla 26.1.2 client connected to Solaris render the
spawn-area floor of `.analysis/test-world/` instead of the M1 black
void. Concretely: when Play state starts, send `Set Center Chunk`
followed by a view-distance window of `Level Chunk With Light`
packets sourced from the `WorldStorage` opened at startup, then enter
the existing KeepAlive loop unchanged. The acceptance gate is a
manual vanilla-client connect; the regression gate is an automated
raw-TCP integration test in `mc-test-harness`.

This is the first milestone where Solaris's network surface depends
on the world surface, so most of the M2 follow-ups stop being
theoretical: the per-chunk re-read in `WorldStorage::ensure_chunk`
will be exercised, the "extras" channel will still be missing, the
empty light arrays are now required on the wire.

## Strategy

Same posture as M1 / M2 (PROJECT_SPEC §8.1, ADR 0001, ADR 0002).

- No Mojang source or Mojmap-informed names. The packet shape is
  taken from `javap -p net.minecraft.network.protocol.game.\
ClientboundLevelChunkWithLightPacket` plus the encoder it composes
  (`ClientboundLevelChunkPacketData`, `ClientboundLightUpdatePacketData`),
  cross-checked against `minecraft.wiki` and a `wire-probe` capture
  from the bundled vanilla server. Identifier names in our code
  are ours.
- Packet IDs come from the same javap dump used in M1.g.2 (Play
  state IDs already cite their `PacketType` constant per
  ADR 0002). We never invent IDs.
- The integration test reads the *real* test world generated by
  `tools/generate-test-world.sh`. We do not synthesise chunks for
  the test — same posture as the M2 round-trip oracle.
- Order of work is wire format → conversion → wiring → streaming
  loop → cache → harness. We deliberately defer the region cache
  (M2 follow-up #1) until *after* the first end-to-end experiment
  so the cache lands with a measurement, not a guess.

## Reference sources (read-only oracles)

- `javap -p` on the unobfuscated vanilla 26.1.2 jar via
  `tools/dump-vanilla-protocol.sh`, scoped to the Level-Chunk and
  Light-Update packet classes plus the inner `*PacketData` helpers.
- `minecraft.wiki` pages "Chunk format", "Level Chunk With Light"
  (under Java Edition protocol), "Block states", "Heightmaps".
- The existing `wire-probe` capture of a vanilla-server → vanilla-
  client session: gives us actual bytes to diff our encoder against
  for one or two real chunks around spawn.
- Our own M2 codec (`mc_world::anvil::chunk_nbt`) — paletted
  containers have the same encoding on disk and on the wire modulo
  the bit-packing convention (Anvil uses non-crossing entries;
  protocol uses the same since 1.16). Reuse where the layouts
  actually match; do not couple the types.

## Sub-milestone decomposition

Tentative ordering. The first three are foundational and serial; the
later ones may be reshuffled.

### M3.a — `LevelChunkWithLight` packet type

In `mc-protocol::packets::play`:

- Add `LevelChunkWithLight` (clientbound, encode only — server never
  receives it). Fields:
  - `chunk_x: i32`, `chunk_z: i32`
  - `heightmaps: Nbt` — vanilla emits this as a network-NBT (unnamed
    root) compound with at least `MOTION_BLOCKING` and
    `WORLD_SURFACE` `long[]` entries.
  - `data: ByteArray` — paletted-container blob (see M3.b).
  - `block_entities: Vec<BlockEntityInfo>` — empty in M3.
  - Light payload: bitsets for sky/block light present/empty masks,
    then arrays. Empty arrays + "all empty" masks are legal and what
    M3 emits; real lighting is later.
- ID verified via `javap` on
  `net.minecraft.network.protocol.game.GameProtocols`; cite the
  `PacketType` name in a comment exactly like the M1.g.2 packets do.
- `impl Packet`: `encode` only. Tests synthesise a one-section
  payload byte-for-byte and assert structural invariants
  (lengths, bitset element count, NBT round-trip via `mc_nbt`).
- Diff-test: feed an *opaque* captured-wire blob from `wire-probe`
  into a `LevelChunkWithLightProbe::decode` helper (private to the
  test) and assert the publicly-encoded version produces the same
  bytes for the same logical input. This is a one-shot oracle; it
  does not require a server-side decoder.

Out of scope: `BlockEntityInfo` is a placeholder type (id + xz_packed
+ y + nbt) but never constructed in M3; the field exists so the wire
shape is right.

### M3.b — `Chunk → wire payload` conversion

New module under `mc_world` (e.g. `mc_world::wire`) — *not* in
`mc-protocol`, because the conversion needs `Chunk` internals and
`mc-protocol` must stay free of `mc-world`.

- `encode_chunk_data(&Chunk) -> Vec<u8>` produces the `data: ByteArray`
  body: for each of 24 sections, `short block_count` then a paletted
  container for block states then a paletted container for biomes.
  Paletted container = `u8 bits_per_entry`, palette (single value /
  indirect / direct), packed `long[]` data — vanilla's exact layout
  since 1.18, same bit-packing convention `M2.c` already uses on
  disk.
- `encode_heightmaps_nbt(&Chunk) -> Nbt` builds the network-NBT
  compound. Reuses the on-disk `long[]` packing directly — no
  recompute (carry-over from M2 follow-up #5).
- Empty light arrays helper that produces the `[18×u64 bitset, 0
  sky entries, 0 block entries, all-empty masks]` shape.
- Tests: round-trip a synthetic `Chunk` (single-state air sections
  + one bedrock section) through `encode_chunk_data` and then
  decode it back via a private probe; assert byte equality at
  every `(x, y, z)`. Plus a test that decodes a *real* chunk from
  `.analysis/test-world/`, re-encodes via the wire path, and asserts
  the `data` blob is a structurally valid paletted-container stream
  (count + element shapes match what `M3.a`'s probe expects).

### M3.c — `mc-net` reads `Arc<WorldStorage>`

Currently `ServerConfig` carries `Arc<VanillaData>` only and
`mc-server` opens-then-drops a `WorldStorage`. Plumbing pass:

- `mc_net::ServerConfig` gains `world: Option<Arc<WorldStorage>>`
  and `blocks: Arc<BlockRegistry>` (the latter already exists in
  scope but is not currently passed in).
- `mc_server::main` keeps the `WorldStorage` it opens and passes
  it into `ServerConfig::new`. When no world is configured or
  opening failed, `world = None` — the M1 black-void fallback is
  preserved.
- `mc_net::play::handle` accepts the storage via the existing
  config-on-connection plumbing.

No protocol behaviour change yet. This is a refactor commit; its
acceptance test is that `cargo test --workspace` stays green and
the M1 spawn burst still works against `wire-probe`.

### M3.d — single chunk experiment

In `mc-net::play::handle`, between the `GameEvent
(start_waiting_for_level_chunks)` and the KeepAlive loop:

1. Emit `Set Center Chunk { x: 0, z: 0 }` (new packet in
   `mc-protocol::packets::play`, ID from javap).
2. Pull chunk `(0, 0)` from `WorldStorage`; if present, encode via
   M3.b and emit `LevelChunkWithLight`. If absent or world is
   `None`, skip silently.

Goal: prove the encoder is right *before* we add the streaming
loop. Manual vanilla-client connect: client should render exactly
the 16×16 area at origin and still-black everywhere else. If the
client kicks us with "invalid packet" or "bad chunk", we caught
the wire-shape bug at minimum surface area. If it renders, we move
on.

Out of scope here: any view-distance logic, any preload.

### M3.e — view-distance streaming

Replace the one-chunk emission with the spawn-area window:

- Compute the chunk window around spawn from `LoginPlay.view_distance`
  (currently `10`, hard-coded — leave as-is, M3 does not turn it into
  config).
- Iterate spawn-out in a spiral or row-major (vanilla uses spiral; we
  do row-major and revisit if the client visibly hitches). For each
  chunk, fetch from `WorldStorage`. Missing chunks send a "single-
  state air" placeholder so the client doesn't keep waiting on them.
- Emit chunks *before* entering the keepalive loop; the loop must
  still tick on schedule, so chunk streaming has to either finish
  fast (likely fine for view-distance 10 = 441 chunks from one
  region) or interleave with keepalive (deferred to M3.f if needed).

Test (raw-TCP harness, see M3.g): assert that within N seconds of
`GameEvent` the client receives ≥ `(2×vd+1)²` Level-Chunk packets
with `(chunk_x, chunk_z)` covering the expected window and parseable
heightmap NBT.

### M3.f — region-level read cache

Now that M3.e generates a real load pattern, fold in M2 follow-up
#1:

- `WorldStorage` keeps a small LRU of `(rx, rz) → DecodedRegion`
  (decompressed payload + per-chunk offsets), keyed independently
  of the existing per-chunk LRU.
- `ensure_chunk` checks the region cache before re-opening the
  `.mca`.
- Bench: time-to-stream the M3.e window before vs. after the cache
  on `.analysis/test-world/`. Record the numbers in this doc's
  closeout appendix. Cache lands only if the win is real.

If the win is negligible (the test world is one region and
filesystem cache makes the re-read fast) we still ship the cache
because the architectural shape is right for M4, but we say so
explicitly.

### M3.g — raw-TCP integration test in `mc-test-harness`

`mc-test-harness` currently only has the one-shot `wire-probe`
binary. M3.g grows a small library `client` module that:

- Performs Handshake → Login → Configuration → Play exactly as a
  vanilla client does. Reuses the wire-probe's connection plumbing
  (frame I/O, compression toggle) but exposes it as an `async fn`.
- Asserts the M3.e packet stream: chunk packets received, set of
  `(cx, cz)` matches the expected window, each `data` blob has the
  right number of sections, heightmap NBT parses.

The test target lives in `crates/mc-test-harness/tests/` and skips
silently when `.analysis/test-world/` is absent — same posture as
the M2 round-trip oracle. It boots the server on a random local
port via `mc_net::run` in a `tokio::spawn`, connects, asserts,
shuts down.

This is the CI gate. The manual vanilla 26.1.2 connect is the
acceptance gate, run once at M3 closure (see "Plan for closure").

## Out of scope (so it does not creep)

- Real lighting (block + sky propagation, light updates) — empty
  arrays only. Lighting is its own milestone.
- Block entities on the wire — `block_entities` field stays empty
  even though `mc-world` knows about them. Re-introduce when a
  typed block entity actually needs to render (signs, chests, …).
- Chunk modification, `Block Update`, `Section Block Update` packets
  — M4.
- Worldgen — still M4–M6. M3 streams what `.mca` has.
- Compression toggle (`Set Compression`) — chunk packets are large
  enough to justify enabling compression, but the M1 handler still
  runs `Compression::Disabled`. Enabling it is a one-line refactor
  in `mc-net::login`; deferred unless the vanilla client refuses
  uncompressed chunks. (It accepts uncompressed chunks; tested in
  M1 indirectly.)
- Player movement / break / place handlers. The client may send
  serverbound movement packets while looking at the chunks; we
  continue to log-and-ignore them as today.
- Heightmap recompute from block data (M2 follow-up #5) — chunks
  are not modified in M3, so the on-disk heightmap is correct as-is.
- "Extras" channel for the chunk fields M2 dropped (follow-up #2)
  — needed when chunks start being written back. M3 only reads.
- Direct-mode palette growth past 256 (follow-up #3) — load path
  bypasses the cap; mutation does not happen yet.
- LZ4 read path (follow-up #4) — vanilla rarely emits it; pull in
  `lz4_flex` when a real region needs it.

## Open questions to resolve along the way

- **Paletted-container "single value" mode on the wire.** Vanilla
  encodes a section with one block state as `bits_per_entry=0`,
  followed by a single VarInt palette entry, followed by a
  zero-length `long[]`. Our M2 disk codec emits the same shape but
  the protocol may forbid the all-air section's `block_count` being
  zero in combination with non-trivial biome data. Verify on a
  capture before assuming symmetry.
- **`Set Center Chunk` placement.** Wiki suggests "before chunk
  data"; vanilla source emits it after Login(Play) and before
  the first chunk batch. Match vanilla; do not guess.
- **Chunk-streaming pacing vs. KeepAlive.** If the view-distance
  window takes >15 s to send (it should not, for one region), the
  KeepAlive scheduler starves. Hold off on a pacing mechanism
  until we see this in the harness test.
- **Heightmap NBT root name.** Network-NBT is unnamed-root since
  1.20.2; `mc_nbt::write_unnamed` is the right tool. Anvil's
  heightmap uses *named*-root NBT; do not mix them up.
- **Missing chunks.** Vanilla generates them on demand; we have no
  worldgen yet. M3.e's "single-state air placeholder" keeps the
  client happy but invites a 'falling forever' visual when the
  player walks off the loaded region. Acceptable for M3; M4 starts
  filling these in.

## Pitfalls (carry-over from M1 + M2 review)

- The Play-state packet ID surface is volatile across patch
  releases. Cite the javap source for *every* new ID; do not
  copy-paste from older `wire-probe` output without re-verifying.
- Network NBT in 26.1.2 is the unnamed-root flavour. Anvil NBT is
  the named-root flavour. Calling the wrong codec will look right
  on small fixtures and break on real chunks — same trap M2
  documented.
- `mc-net::ServerConfig` currently does its own field plumbing
  rather than going through a derive; make sure the new
  `world`/`blocks` fields propagate through `mc_server::to_network`
  and that the `--check` mode in `mc-server` still resolves cleanly
  without a world directory.
- The `wire-probe` capture used as an oracle is a *single* run
  against the bundled vanilla server; if Mojang ships a network-
  protocol patch in 26.1.3 the oracle gets re-recorded, not the
  encoder rewritten. Note the capture's source commit.
- Per [[feedback-no-external-artifacts]], the captured wire blobs
  and any generated chunks used as test fixtures stay in
  `.analysis/` (git-ignored). Anything checked into `tests/` is
  synthesised at runtime from the test-world or from code.

## Open follow-ups (handed to M4)

- **`extras` opaque channel for dropped chunk fields** (M2 follow-
  up #2, still open). Block / fluid ticks, structures,
  PostProcessing, per-section sky/block light, InhabitedTime,
  LastUpdate, DataVersion. Read path drops them; round-trip back
  to disk would lose game-state continuity. M4 needs this before
  chunks start being modified.
- **Direct-mode palette growth past 256 states** (M2 follow-up #3,
  still open). Load path is fine; only post-load mutation hits the
  cap.
- **LZ4 read path** (M2 follow-up #4, still open). One-line crate
  addition when a real region needs it.
- **Heightmap recompute from block data** (M2 follow-up #5, still
  open). Required once chunks start being modified.
- **Set Compression enable.** Chunk packets are 2–8 KiB; enabling
  zlib compression in `mc-net::login` would meaningfully shrink the
  spawn burst. Vanilla clients accept uncompressed today, so this
  is opt-in performance, not a correctness fix.
- **Spiral iteration order.** `emit_chunks_around` walks row-major.
  Vanilla walks a spiral so the player's tile renders first; not
  visibly hitching on our 441-chunk burst, so deferred.
- **Light propagation.** All `LevelChunkWithLight` packets carry
  `LightData::empty()`. The vanilla client runs its own per-chunk
  skylight pass only for the chunk under the player; every
  surrounding chunk renders pitch-black as observed during the M3.i
  manual acceptance. Real lighting is its own milestone.
- **Worldgen.** M3 streams what `.mca` already has. Chunks outside
  the test world's region files are absent and the client falls
  through. M4–M6 begin filling these in.
- **`SetDefaultSpawnPosition` re-introduction.** Skipped in M1.g
  because the 26.1.2 wire shape changed (no `angle` field, ID
  uncertain). Cosmetic — compass anchor only. Verify and re-add
  when convenient.
