# M36 - Multiplayer hardening

**Status:** plan on `dev/M36-multiplayer-hardening` from `main` at local tag
`m35` (`3c296bf`, `feat: M35 commands admin surface`).
**Owning crates:** `mc-net` for session lifecycle, chunk subscriptions,
authoritative shared mutations, broadcasts, and limits; `mc-server` for runtime
configuration and lifecycle wiring where needed; `mc-test-harness` for
multi-client race coverage.

## Goal

Make multi-player survival sessions authoritative, race-safe, and stable under
join, movement, block edit, container, combat, pickup, and disconnect pressure.

M36 is not a rewrite of the networking or simulation model. The target is a
focused hardening pass: deterministic main-thread ordering, clean teardown,
bounded session pressure, correct per-viewer broadcasts, and wire-level tests
that exercise real shared-world behavior with more than one client.

## Current Foundation

- M35 added an admin command surface and enough state-changing commands to drive
  multi-client scenarios without relying on opportunistic world events.
- Play sessions already own chunk streaming, inventory, entity visibility,
  container handling, survival state, persistence hooks, and command feedback.
- M35 closeout noted raw harness frame drains and hot shared locks as follow-ups;
  M36 should fix race-prone harness coverage only where it blocks reliable
  multiplayer assertions. The server-wide lock mitigation pass remains reserved
  for M39.
- The project architecture still prefers deterministic tick-thread ownership and
  narrow queues over broad mutexes around world state.

## Strategy

1. Audit session lifecycle first. Disconnect/reconnect cleanup must be explicit
   before adding tests that churn players.
2. Stabilize chunk and entity visibility under movement, teleport, death/respawn,
   and disconnect without adding global locks.
3. Route shared mutations through deterministic authoritative paths and reject
   stale or invalid client input before mutation.
4. Verify broadcasts from the receiving clients' point of view. Container ids,
   entity ids, block positions, and viewer-specific state must be correct per
   recipient.
5. Add multi-client harness tests for real races instead of manufactured state.
6. Add bounded limits and timeout/teardown observability where the runtime already
   has the necessary hooks.

### M36.b - Session lifecycle audit and cleanup

Review and harden login, Play entry, disconnect, reconnect, chunk subscription,
entity visibility, container registration, and persistence cleanup.

Acceptance:

- Disconnect removes the player from viewer registries, chunk subscriptions,
  open containers, entity visibility sets, and pending shared-world queues.
- Reconnect with the same stable identity receives fresh state without inheriting
  stale viewer/container/chunk registrations.
- Cleanup is idempotent for normal disconnect, network error, kick, and shutdown
  paths.
- Logs expose session counts and cleanup pressure without leaking local paths or
  secrets.
- Unit or harness tests cover disconnect cleanup and reconnect freshness.

### M36.c - Chunk view and visibility hardening

Stabilize chunk view tracking under rapid movement, teleport, death/respawn,
dimension-placeholder absence, and disconnect.

Acceptance:

- Chunk subscribe/unsubscribe decisions are deterministic for repeated movement
  across boundaries and teleports.
- Disconnect cancels pending chunk work for that session where Solaris owns the
  queue or safely drops late results at send time.
- Entity visibility enter/leave broadcasts stay correct when players move or
  disconnect mid-update.
- Tests cover at least one multi-client movement or teleport visibility scenario.

### M36.d - Shared mutation ordering

Make block edits, fluid ticks, entity damage, item pickup, and container clicks
deterministic across clients.

Acceptance:

- Two clients editing the same block converge on one authoritative final block
  state and both viewers receive the resulting update.
- Concurrent container interaction applies server-side slot rules once and sends
  per-viewer state updates with correct container ids.
- Item pickup and combat mutations cannot double-apply rewards, drops, damage, or
  death side effects when multiple players interact in the same tick window.
- Stale client input is rejected or resynchronized rather than weakening protocol
  validation.
- Tests cover at least two shared mutation races.

### M36.e - Broadcast consistency

Audit and fix block, entity, container, inventory, player, death/respawn, and
command-triggered updates for multi-viewer correctness.

Acceptance:

- Affected viewers receive the right packet type, entity id, container id, block
  position, and state for their own session.
- Unaffected viewers do not receive updates for invisible or unsubscribed objects
  when Solaris can cheaply avoid them.
- Broadcasts happen after authoritative mutation succeeds.
- Tests assert from more than one client stream where possible.

### M36.f - Limits, timeouts, and teardown observability

## Risks / Pitfalls

- Broad mutexes can hide races while violating the architecture. Prefer
  deterministic ownership, queue ordering, snapshots, and cleanup checks.
- Multi-client harness tests are easy to make flaky by draining frames from the
  wrong client. Add buffering/filtering only where assertions need it.
- Per-viewer protocol state matters. A correct global mutation can still send the
  wrong container id or entity id to one recipient.
- Disconnect paths are often duplicated. Cleanup must be idempotent rather than
  assuming one happy-path close.
- Session limits and timeouts must not break local development or existing
  single-client tests by default.

## M36 Implementation Notes

Implemented hardening:

- Play-session registration now uses admission control before sending the Play
  entry burst. `max_players` is enforced as an active-session cap instead of only
  being advertised in status/Login Play, and duplicate offline profiles are
  rejected while the first session remains active.
- Registered Play sessions are protected by an unregister guard. If an early
  Play-entry write, command tree write, teleport sync, chunk-center write, or
  later loop setup fails, session cleanup still removes viewer state, chunk
  tickets, container registrations, and persistence handles through the existing
  `SessionRegistry::unregister` path.
- Reconnect with the same name/UUID is accepted after the old session unregisters
  and receives fresh visibility state. A multi-client harness test covers Bob
  disconnecting, Alice receiving removal, and Bob reconnecting as a new visible
  entity.
- Item pickup now claims the server entity under the session registry lock before
  mutating the player's inventory. A stale second picker cannot merge the same
  item into its inventory after another session removes or decrements the entity.
- XP pickup removal now reports whether the orb was actually removed; stale
  candidates no longer grant XP after another session already collected the orb.
- Chest and furnace clicks now perform storage read, click mutation, and storage
  write while holding one storage lock, then dispatch per-viewer updates after
  the authoritative mutation succeeds. This removes the previous lost-update
  window between separate load and save lock sections.
- Admission and shared-pickup unit tests were added in `mc-net`; wire-level tests
  were added/extended in `mc-server` and `mc-test-harness` for full-server
  admission rejection and disconnect/reconnect visibility cleanup.
