# M56 - Shield blocking

**Status:** Closed as partial/usable shield support after M56.b; vanilla parity remains deferred. Branch: `dev/M56-shield-blocking`, cut from `main` at `e2fface` (`docs: M55 closeout`).
**Owning crates:** `mc-net` for item-use state and damage mitigation, `mc-entity` only if reusable damage-source helpers need a small seam, `mc-test-harness` for survival coverage, `docs` for readiness updates.

## Goal

Make shields useful in normal survival combat: a player holding and using a shield
can block incoming frontal melee and basic projectile damage through Solaris'
existing combat pipeline.

This directly closes a named replacement-readiness gap, builds on M33 combat and
M54 arrows, and gives players a visible survival defensive loop without adding new
packet IDs or guessed metadata.

## Scope

- Recognize `minecraft:shield` in either hand.
- Track per-player shield-use state from the already verified item-use and
  use-release paths.
- Apply a short activation delay before the shield can block damage.
- Block only incoming damage whose source direction is in front of the player.
- Cover player-facing hostile melee and basic arrow/projectile damage sources
  already routed through Solaris damage handling.
- Keep shield durability, disable windows, and animation/metadata parity deferred
  unless an implementation slice proves a tiny existing hook can be reused safely.
- Add focused unit tests first, then one Solaris-only harness scenario once the
  runtime behavior is stable.

## Non-Goals

- Exact vanilla shield angle, cooldown, disable, knockback, sound, particle, or
  durability parity.
- Axe shield-disabling rules.
- Enchantments, banner patterns, custom shield rendering, or equipment-component
  parity.
- New clientbound entity metadata, equipment, sound, or particle packet layouts
  unless first captured from the local vanilla oracle per ADR 0002.
- Full projectile parity beyond the existing basic arrow/projectile path.
- Crossbow, trident, explosion, firework, splash potion, or special mob attacks.

## Strategy

1. Keep M56.a entirely on verified gameplay paths: existing item-use/release
   packets, player inventory lookup, player yaw/look direction, and damage routing.
2. Add a small runtime shield state beside existing pending item-use state instead
   of inventing persisted item metadata.
3. Normalize damage sources to the minimum needed for blocking: attacker/projectile
   origin if known, otherwise unblockable.
4. Apply shield mitigation late in the shared player damage path so melee and
   projectile callers get the same behavior.
5. Use deterministic Solaris rules and document them: shield becomes active after a
   short server tick delay, blocks frontal damage, and leaves side/back or unknown
   source damage unchanged.
6. Defer all visual parity that needs unverified metadata. If the client already
   shows local shield use because the player is holding right-click, treat that as
   sufficient for M56.

Status: committed as `0782c03` (`feat: add basic shield blocking`).

Landed notes:

- Added volatile shield-use state from the existing `ServerboundUseItem` path for
  main-hand and offhand `minecraft:shield` use.

  game mode changes, and lazy held-stack revalidation failures.
- Frontal mob melee and arrow player damage can be blocked after a 5-tick
  activation delay.
- Side, rear, unknown-source, environmental, and non-shield cases pass through
  unchanged.
- No new packets, metadata, sounds, particles, durability, or shield-disable
  behavior landed in M56.a.
- Focused gate passed: `cargo test -p mc-net shield -- --nocapture` (5 tests).
- Format check passed: `cargo fmt --all -- --check`.

Acceptance:

- Holding right-click with a shield in main hand or offhand starts server-side
  shield state through existing packet handling.
- Releasing use or losing/changing the shield clears the state.
- After the configured activation delay, frontal mob melee and basic arrow damage
  are blocked by the shield helper.
- Side, rear, unknown-source, and non-combat/environmental damage are not blocked.
- No new packet IDs, field layouts, or entity metadata are introduced.
- Focused `mc-net` tests pass.

## Protocol and Data Oracles

- M56.a must not add new packet IDs, field layouts, entity metadata, sound, or
  particle packets. It should reuse existing verified `ServerboundUseItem`,
  use-release, inventory slot sync, damage, health, and entity paths.
- Item identity may come from loaded registry/item data or existing item-id lookup;
  no hardcoded protocol id is needed beyond the namespaced item id
  `minecraft:shield`.
- If any later slice attempts shield pose metadata visible to other players,
  shield disable behavior, sounds, particles, or exact clientbound equipment
  updates, first capture the behavior with `wire-probe` against
  `.analysis/server.jar` and cite the dump per ADR 0002.
- Vanilla gameplay algorithms must not be translated from decompiled source.
  Solaris owns a documented approximation for timing, angle, and mitigation.

## Risks

- Client-side shield animation may appear local-only without server metadata; do
  not chase visual parity in M56.a.
- Damage callers may not all preserve source origin. Unknown origins should fail
  closed as unblockable rather than broadening mitigation silently.
- Direction checks can be flaky if based on stale yaw. Unit-test the pure helper
  with fixed vectors before wiring it into session state.
- A too-broad mitigation hook could block fall, fire, drowning, or starvation.
  Restrict M56.a to explicit melee/projectile sources.
- Harness projectile setup can become brittle. Prefer pure `mc-net` coverage for
  M56.a and add the harness only after the runtime seam is stable.
