# M10 - Light perf + heightmap foundations

**Status:** complete on `dev/M10-light-perf-geometry` (6 commits
ahead of `main` at tag `m9`). Awaiting owner review, manual gate,
merge, and `m10` tag.
**Estimate:** broad milestone, 18-35 h. This intentionally bundles
the top M9 light-performance follow-ups plus the smallest geometry
fix that removes the hard-coded spawn height.
**Owning crates:** `mc-world` (light storage, heightmaps), `mc-net`
(spawn position + edit hooks), `mc-test-harness` if the spawn/manual
gate needs protocol coverage.

## Goal

After M10, Solaris has a measurable light-engine performance
baseline, a cheaper incremental BFS queue, lazy per-section light
storage, and a first-class highest-opaque-Y heightmap that fixes the
worldgen spawn-in-ground issue and lets sky relight skip most edits
that do not cross the column top.

The milestone is deliberately ordered so every optimization has a
before/after guard: benchmark first, queue second, storage refactor
third, then the gameplay-visible heightmap/spawn fix.

## Strategy

1. **Measure first.** Add a light benchmark target that times full
   recompute and an edit-storm workload against real `mc-world`
   code paths. The benchmark should be runnable with `cargo bench`
   and useful even if exact timings vary by machine.
2. **Shrink incremental queue traffic.** Replace tuple queue entries
   in the incremental BFS hot path with packed window-local entries,
   eliminating repeated world-to-window conversion in the pop loop.
3. **Change light storage shape.** Move `ChunkLight` from flat
   per-chunk byte vectors to lazy per-section nibble arrays. The wire
   encoder, workspace, cache, and parity tests must keep identical
   output.
4. **Make heightmaps authoritative.** Track highest opaque Y as chunk
   state, update it on edits, use it for adaptive spawn, and use it
   as a sky-reseed guard so normal underground edits skip the sky
   pass.

## Sub-milestone decomposition

### M10.a - light benchmark harness

Add a benchmark under `mc-world` that covers:

- full `compute_chunk_light` / `compute_chunk_light_in` recompute;
- incremental place/remove sequences through
  `apply_block_change_to_light`;
- at least one flat test-world-like chunk and one generated/noisy
  chunk shape.

The benchmark is a measurement tool, not a correctness oracle. The
existing M9 unit tests and harness parity remain the correctness
gate. Server/manual validation continues to use debug builds; this
bench target may use Cargo's benchmark profile because it does not
build or run the `mc-server` release binary.

### M10.b - packed incremental BFS queue

Replace the incremental BFS queue entry type with a packed `u64`
containing window-local coordinates and light level. Keep the full
recompute queue unchanged unless the benchmark proves the same
packing is worthwhile there too.

Acceptance for this slice is behavioural parity against the existing
M9 tests plus benchmark output captured in the commit body or status
appendix. If the benchmark does not show a real improvement, keep the
change only if it is simpler or revert before moving on.

### M10.c - per-section lazy light storage

Refactor `ChunkLight` so sky and block light are stored per vertical
section, with empty all-zero sections represented without allocating
a 2048-byte nibble array. The public operations should continue to
read/write light by block coordinate; callers should not care about
the storage layout.

Required touch points:

- `LightWorkspace` construction and reuse;
- `LightCache` insertion, mutation, and comparison;
- `encode_chunk_light` masks and update arrays;
- M9 unit tests that compare cached light to full recompute;
- M9.d wire-parity harness expectations.

This is the riskiest slice. Land it as one coherent refactor commit
only when the full baseline is green; use a follow-up `fix:` commit
if the harness exposes a wire-mask edge case.

### M10.d - heightmap + adaptive spawn + sky skip

Add a highest-opaque-Y heightmap to chunk state and keep it updated
when blocks change. Use it to choose a spawn Y above the actual
spawn-column surface instead of the current flat-world-only `-59.0`.

Then thread the same heightmap into incremental sky relight: if an
edit does not change the highest opaque Y for its column, skip the
direct-sky column reseed and any sky removal/addition work that is
provably unaffected. Block-light relight stays unchanged.

### M10.e - harness/manual gate + closeout

Add or extend integration coverage if the spawn change changes
observable packets or client placement. Close out with:

- this document's status appendix and `What landed where` table;
- README status paragraph update;
- `project-status` memory update.

Owner still merges to `main` and tags `m10`.

## Acceptance criteria

1. `cargo test --workspace` green after every sub-milestone commit.
2. `cargo clippy --workspace --all-targets -- -D warnings` clean.
3. `cargo fmt --all -- --check` clean. No `unsafe`.
4. `cargo bench -p mc-world --bench light_engine` or the final bench
   target name runs and reports full recompute + edit-storm timings.
5. Existing M9 incremental-light unit tests and wire-parity harness
   still pass with per-section storage.
6. Worldgen-only spawn places the player above the generated surface,
   not inside terrain; bundled flat-preset spawn still lands above
   the grass surface.
7. Manual gate: debug `cargo run --bin mc-server -- --config
   example.toml`; owner connects with PrismLauncher 26.1.2, verifies
   spawn, walking, break/place, and no obvious light pop-in.

## Out of scope

- Disk-persistent light arrays in `.mca` files.
- Multi-edit batching / `SectionBlocksUpdate` relight merging.
- Async/background relight or flush.
- Set Compression at login.
- Survival break timing, reach validation, or anti-cheat.
- Parallel light propagation.

## Pitfalls

- **Benchmark noise.** Absolute timings depend on host load; use the
  benchmark mainly for before/after direction and obvious regressions.
- **Cargo.lock churn.** If the benchmark harness adds a dependency,
  the lockfile change is justified by M10.a and must be kept scoped.
- **Nibble-mask parity.** Lazy all-zero sections must still produce
  the same light masks/update arrays as the flat representation.
- **Aliasing mutable cache slots.** Per-section storage should not
  make `LightCache` borrow patterns more fragile; prefer keeping the
  current take/mutate/put-back shape.
- **Heightmap semantics.** Highest opaque Y must match the light
  table's `propagates_sky`/opacity semantics, not an unrelated
  visual-solid heuristic.
- **Spawn packet shape.** If adaptive spawn reintroduces or changes
  any packet beyond existing login/position flow, verify packet IDs
  and field layout through `.analysis/protocol-dump.txt` or
  `wire-probe`, not memory.

## Open questions

- Should the per-section light storage expose section-level helpers
  directly, or keep only block-coordinate operations until a caller
  needs section iteration?
- Should the heightmap live inside `Chunk`, next to block sections,
  or be a derived sidecar owned by storage/cache? Default plan:
  store it on `Chunk` because edits already mutate chunks in place.
- If M10.c overruns, should M10.d be cut to adaptive spawn only and
  leave sky-reseed skipping for M11? Default plan: yes; do not risk
  the storage refactor baseline for a secondary optimization.

  Play computes spawn Y from chunk (0, 0)'s light-table-driven
