# M71 - Container parity

**Status:** Closed locally. Branch: `dev/M71-container-parity`, stacked after
local M70. M71.a through M71.z landed.
**Owning crates:** primarily `mc-net`, `mc-world`, and targeted
`mc-test-harness` coverage for client-visible container behavior.

## Goal

Close the most visible container parity gaps left after the M68/M69 cleanup:
smoker and blast-furnace menu/storage identity, barrel-specific behavior, and the
remaining open-window click assertions for furnace and chest menus.

## Priority Backlog

### M71.a - Furnace-Family Menu And Storage Identity

Make smokers and blast furnaces present as their own vanilla container types and
persist with their own block-entity ids while preserving the shared Solaris
cooking core.

Oracle evidence:

- `data/vanilla/reports/registries.json` records menu protocol ids:
  `minecraft:blast_furnace` = `10`, `minecraft:furnace` = `14`, and
  `minecraft:smoker` = `22`.
- `data/vanilla/reports/registries.json` records block-entity type ids:
  `minecraft:furnace` = `0`, `minecraft:smoker` = `28`, and
  `minecraft:blast_furnace` = `29`.
- Existing recipe data already carries `smelting`, `smoking`, and `blasting`
  categories plus per-recipe `cooking_time`.

Scope:

- Replace the single furnace menu id at open time with a menu id derived from
  `FurnaceKind`.
- Keep recipe filtering by `FurnaceKind` and assert smoker/blast-furnace cooking
  uses the loaded recipe category and cooking time.
- Preserve the current shared `FurnaceBlockEntity` runtime shape, but store the
  furnace-family kind alongside it where persistence needs to write the correct
  vanilla block-entity id.
- Extend focused unit or harness coverage so opening a smoker/blast furnace checks
  the menu id and at least one specialized recipe path.

Non-goals:

- Rewriting the furnace runtime into separate block-specific state machines.
- Hopper/comparator automation, sounds, particles, or lit-state block updates.
- Guessing additional block-entity update packet shapes.

Landed so far:

- Furnace, smoker, and blast-furnace windows now open with their own vanilla menu
  type ids while retaining the shared furnace-family runtime.
- Anvil decode accepts `minecraft:furnace`, `minecraft:smoker`, and
  `minecraft:blast_furnace` block entities into the shared typed furnace state.
- Anvil encode writes the furnace-family block-entity id from the block state at
  that position, so placed smokers and blast furnaces no longer save as
  `minecraft:furnace`.
- Focused unit and harness coverage checks menu id mapping, real open-screen
  packets for smoker/blast furnace, and furnace-family block-entity id
  round-trip behavior.

### M71.b - Barrel Storage Identity And Client State

Separate barrels from chest identity enough that vanilla clients and saved chunks
see barrel-specific behavior instead of chest behavior with a barrel title.

Oracle evidence:

- `data/vanilla/reports/registries.json` records `minecraft:barrel` block-entity
  type id `27`.
- `data/vanilla/reports/registries.json` records single-container storage menu
  type `minecraft:generic_9x3` as protocol id `2`, which remains the correct
  27-slot storage menu shape for a barrel.

Scope:

- Preserve the 27-slot storage mechanics already shared with single chests.
- Persist barrel block entities with `minecraft:barrel` identity instead of
  `minecraft:chest` when the block at the position is a barrel.
- Add a narrow client-visible state update only if local vanilla evidence verifies
  the exact open/close block-state or event behavior.
- Add harness or unit coverage for barrel storage persistence and open-screen menu
  behavior.

Non-goals:

- Double-barrel behavior; vanilla barrels are single containers.
- Hopper/comparator parity unless the storage identity work makes it trivial and
  testable.
- Sound/game-event/statistics parity.

Landed so far:

- Barrel storage continues to share the single 27-slot chest storage mechanics and
  `minecraft:generic_9x3` menu shape.
- Anvil decode accepts `minecraft:barrel` block entities into the shared typed
  chest-storage state.
- Anvil encode writes `minecraft:barrel` instead of `minecraft:chest` when the
  stored block at that position is a barrel.
- Focused unit coverage checks chest/barrel block-entity id round-trip behavior.

### M71.c - Furnace And Chest Click Coverage Hardening

Close the exact M69 coverage leftovers for open furnace and chest windows without
expanding the click system surface area.

Scope:

- Add focused assertions for `Swap` and `Throw` inside an open furnace window.
- Add focused assertions for `Swap` and `Throw` inside an open chest or double
  chest window.
- Prefer unit tests if they exercise the real shared click core and menu adapters;
  use harness tests only for packet-visible behavior that unit tests cannot
  honestly cover.
- Update `docs/M68_CONTAINER_CLICK_COVERAGE.md` if the matrix materially changes.

Non-goals:

- Exhaustive click-mode parity for every vanilla menu.
- Changing ack/revision behavior unless a test exposes a real bug.

Landed so far:

- Added focused unit coverage for furnace-window `Swap` and `Throw` through the
  real furnace menu adapter.
- Added focused unit coverage for chest-window `Swap` and `Throw` through the real
  chest storage adapter.
- Updated the M68 coverage matrix so the old furnace/chest swap/throw gaps no
  longer remain open.
