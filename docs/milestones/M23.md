# M23 - Survival completeness follow-up

**Status:** complete locally on `dev/M23-survival-completeness` from local tag
`m22`.
Manual gate remains disabled under the active YOLO-mode instruction; automated
cargo gates are authoritative unless the owner explicitly asks for PrismLauncher.
**Owning crates:** `mc-protocol` for verified item stack/data-component and
crafting/respawn packets, `mc-net` for server-authoritative gameplay execution,
`mc-data` for recipe/item data inputs, and `mc-test-harness` for wire-level
survival coverage.

## Goal

Close the highest-value gaps deliberately deferred by M22: represent enough item
stack component state for tool durability, damage held tools through the
authoritative survival mining path, pin crafting and respawn protocol facts from
local oracles, and land minimal execution paths only where the packet evidence is
complete.

This milestone is not a full vanilla inventory, recipe-book, or respawn parity
push. It is a survival-completeness slice that keeps server authority and the
ADR 0001/0002 oracle rules intact.

## Strategy

1. Verify every new packet ID/layout and item-stack component encoding from
   local vanilla class oracles before implementing codecs. `.analysis/decompiled/`
   is a local-only inspection mirror; committed Rust records only protocol
   metadata, not translated vanilla algorithms.
2. Extend `ItemStack` narrowly for durability-related component state instead of
   attempting broad DataComponentPatch parity.
3. Keep durability mutation inside the server-authoritative inventory path used
   by successful survival mining.
4. Treat crafting and respawn as oracle-first work: pin packet facts, then land
   the smallest execution path if the verified sequence is sufficient.
5. Preserve all M22 gameplay behavior and harness coverage while adding focused
   tests for each new vertical slice.

## Risks / Pitfalls

- DataComponentPatch can balloon quickly. Keep M23.b limited to durability-shaped
  state that current gameplay actually mutates.
- Tool damage can accidentally trust client inventory. Mutate only server-owned
  inventory state and resync the client.
- Crafting protocol has recipe-book and container UX traps. Do not implement from
  names alone; reduce to an oracle/doc slice if packet evidence is incomplete.
- Respawn recovery can desync dimensions, abilities, position, or health. Land only
  the packet sequence that is verified locally.
- Sidecar data remains optional/local. No Mojang bytes enter git.

## Closeout Notes

M23 closes the three M22 follow-ups with narrow, verified implementation rather
than broad vanilla parity. `mc-protocol::ItemStack` now carries the verified
`minecraft:damage` component (`DataComponents.DAMAGE`, local registration id 3,
VarInt integer payload) and still rejects unsupported component shapes. Survival
mining mutates held tool damage only after a successful server-timed break and
resyncs the changed hotbar slot.

Crafting lands as a minimal `ServerboundPlaceRecipe` execution path for player
container 0. The server matches one recipe, consumes ingredients from the
authoritative inventory, and emits existing verified `ContainerSetSlot` updates.
Recipe ingredients now preserve item-vs-tag alternatives, so local tag data can
resolve recipes such as planks/sticks/crafting tables. When sidecar recipe JSON
is absent, Solaris exposes a small fallback survival set: torches, oak planks,
sticks, crafting tables, wooden tools, stone tools, and furnaces. `useMaxItems`
now repeats the server-authoritative craft until inputs or output space run out.

`ServerboundContainerClickPacket` is now decoded from the local vanilla class
shape, including bounded `HashedStack` changed-slot and cursor data. Solaris does
not trust the client-supplied hashes for mutation yet; it uses them only to keep
the stream aligned, then applies server-authoritative player-inventory clicks for
container 0. Left/right pickup and shift-click move stacks through a tracked
server cursor and resync the full window content after each accepted or rejected
click. Full recipe-book discovery, `UpdateRecipes`, and non-player container UX
remain later work.

Furnaces now open a real furnace menu instead of using the old instant-smelt
shortcut. The server sends verified `OpenScreen`, `ContainerSetContent`, and
`ContainerSetData` packets, maps the 39-slot furnace window back onto the
authoritative player inventory, and ticks input/fuel/output progress while the
screen is open. Furnace contents are kept by block position for the current
server runtime so closing and reopening does not drop inserted stacks. Block
entity persistence and cross-process reload are still later work.

Armor slots now reject non-matching armor pieces, shift-click can equip one armor
piece from inventory/hotbar, and survival damage applies the local vanilla
CombatRules armor/toughness formula. Equipped armor takes one durability point on
incoming survival damage and breaks at vanilla-derived material/type durability.
The current scope uses explicit vanilla armor material constants verified from
the local class oracle; registry-driven equippable components, enchantments, and
special head-slot items remain later work.

The survival gather/place loop is now closed for basic blocks: repo-owned
`crates/mc-data/data/survival_loot.json` drives grass-to-dirt,
stone-to-cobblestone, common ore drops, and apple drops from oak/dark-oak leaves;
newly picked up stacks prefer empty hotbar slots; and `UseItemOn` can place held
block items in survival instead of being creative-only. The same repo-owned loot
file drives minimal passive mob food drops through the verified standalone
`ServerboundAttackPacket`; no loot behavior depends on `.analysis` or gitignored
Mojang JSON.

Respawn lands as a minimal recovery sequence: `ServerboundClientCommand` action
0 (`PERFORM_RESPAWN`) is accepted only while dead, then the server resets health,
food, pending break, and position, and emits verified `ClientboundRespawn`,
`SynchronizePlayerPosition`, and `SetHealth`. Death still blocks normal actions
before that request.

Known follow-ups:

- Crafting should grow from one recipe request into real recipe-book/display id
  synchronization and 2x2/crafting-table grid behavior.
- Respawn should eventually mirror the full vanilla recovery bundle, including
  ability/state refreshes and dimension-change edge cases.
- Furnace block-entity persistence and multi-player concurrent furnace views
  still need shared world-level storage.
- Hostile night pressure, effects, enchantments, equippable component parity, and
  broad loot-table parity remain outside this MVP loop.
