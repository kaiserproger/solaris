# M31 - Overworld worldgen parity slices

**Status:** implemented locally on `dev/M31-worldgen-parity-slices` from `main` at
`cacc160` (`feat: M30 worldgen data foundations`). Local tag `m30` points at
this commit.
**Owning crates:** `mc-data` for additional sidecar fact loaders, `mc-worldgen`
for deterministic Solaris-owned terrain/population policy, `mc-world` for
generated chunk persistence interactions, `mc-server` for startup wiring and
spawn-window reporting, and `mc-test-harness` for exploration regressions.

## Goal

Expand overworld generation from M30 data foundations into practical survival
exploration slices: more distinct terrain and surfaces, common cave/ore and
vegetation coverage, one narrow structure path where feasible, deterministic
population ordering, and explicit debug-build performance budgets.

M31 is still not bit-perfect vanilla worldgen parity. Sidecar data may provide
declarative facts and local assets under ADR 0001, but terrain, cave, feature,
and structure placement policy remains Solaris-owned and independently
implemented.

## Current Foundation

M30 shipped the data and generator seams M31 should widen:

- `mc-data::worldgen_inventory` records local worldgen sidecar presence and
  counts without committing Mojang bytes.
- `mc-data::worldgen_features` exposes placed/configured feature ids, feature
  types, placement modifier names, scalar hints, block-state ids, and tag ids.
- `mc-worldgen::TerrainGenerator` can consume feature facts while preserving a
  bounded Solaris decoration pass.
- Biome buckets, cave-biome membership, ore facts, and simple surface
  decoration already have deterministic fallback behavior when sidecar data is
  absent.
- Generated overlays, heightmaps, dirty tracking, and persisted edits have
  regression coverage.

## Strategy

1. Improve visible exploration outcomes in narrow, reviewable slices instead of
   introducing a generic vanilla worldgen executor.
2. Prefer sidecar facts for identifiers, block states, tags, counts, height
   hints, structure references, and biome membership; keep placement math and
   RNG policy independent.
3. Preserve portable fallback generation for fresh clones without local
   `data/vanilla` or `.analysis` assets.
4. Add regression tests at the seam that changed: loaders in `mc-data`,
   deterministic generated chunks in `mc-worldgen`, and client exploration in
   `mc-test-harness`.
5. Treat performance as an acceptance criterion. Spawn pre-generation and
   exploration streams must have an explicit debug-build budget and observable
   timing.

## Risks / Pitfalls

- Vanilla worldgen data often encodes algorithmic behavior. M31 must keep using
  facts as inputs to Solaris policy rather than translating feature, carver,
  jigsaw, processor, or noise algorithms.
- Broader decoration can become expensive if every chunk scans all sidecar facts.
  Normalize facts once and keep hot-path lookup bounded.
- Cross-chunk structures and caves can break persistence if generated after a
  neighboring chunk was edited. Prefer single-chunk or deterministic local
  overlays unless a tested boundary protocol exists.
- Visual parity claims are easy to overstate. Document approximations as such and
  avoid wording that implies bit-perfect vanilla output.
- Local Mojang sidecar assets remain gitignored; tests using them must skip
  clearly when unavailable.

## M31.b Surface Notes

`mc-worldgen::TerrainGenerator` now resolves additional registry-backed fallback
surface materials at construction time: `red_sand`, `gravel`, `podzol`, and
`snow_block`, each falling back to stone if the block id is absent from a stub
registry. Surface selection remains independent Solaris policy:

- water, river, beach, and shore buckets use sand top/filler;
- badlands use red sand;
- desert uses sand;
- mountain and stony buckets use gravel over stone;
- cold/snow/frozen buckets use snow block over dirt;
- birch/dark/pale/old-growth forest-like and taiga buckets use podzol over dirt,
  while the default `minecraft:forest` spawn-friendly path stays grass over dirt;
- remaining grassland-like buckets use grass over dirt.

`biome_surface_rules_are_visibly_distinct` pins those choices, while existing
determinism and persistence tests continue to prove fixed-seed output and
persisted edits winning over regenerated chunks.

## M31.c Cave / Carver Notes

The cave pass remains bounded to the current chunk and runs after base terrain
but before biome assignment/decorations/structures. M31 widens the existing
predicate with a second branch noise field and sparse deterministic room cells;
it still does not copy vanilla carver algorithms and does not mutate neighbor
chunks.

`feature_layer_adds_caves_and_ores_without_cave_fluids` covers cave air, ore,
and deepslate reachability in sampled chunks, and repeated-generate tests cover
determinism.

## M31.d Feature Notes

`DecorationBlocks::from_feature_facts` now consumes more simple facts from
`WorldgenFeatureFacts`:

- tree-like placed features can provide log/leaves block states for plains,
  forest, taiga/cold, and jungle buckets;
- `patch_sugar_cane` / `sugar_cane` can provide the shoreline plant block state;
- the M30 grass, flower, and cactus fact paths remain in place.

Placement remains Solaris-owned and bounded per generated column. The feature
facts only alter resolved block states and count-derived spacing where those
facts are simple scalars. `feature_facts_drive_tree_blocks` and the existing
grass/decoration tests prove synthetic facts can visibly alter output without
breaking deterministic generation.

## M31.e Structure Notes

`mc-data::worldgen_structures` adds a narrow structure-set fact loader for
structure references plus random-spread spacing, separation, salt, and placement
type ids. It is intentionally not a jigsaw, processor, or placement executor.

`mc-server` loads those facts from `data/minecraft/worldgen/structure_set` when
available and feeds village spacing facts into the existing plains-village
template marker seam. Template NBT loading remains local-only under ADR 0001.
When sidecar structure-set data is absent, Solaris keeps the existing fallback
spacing. Structure placement still filters to eligible grassland cells, pastes
intersecting template blocks into the current chunk, and refreshes affected
heightmaps.

Tests added/retained:

- `mc_data::worldgen_structures::loads_synthetic_structure_set_facts`;
- `mc_worldgen::structures::structure_set_facts_adjust_plains_village_spacing`;
- `structure_rules_paste_intersecting_template_blocks`;
- `generated_overlays_survive_flush_and_reopen`.

## M31.f Population Ordering Notes

`GENERATION_STAGE_ORDER` records the tested generated-chunk lifecycle:

1. `base_terrain_and_surfaces`
2. `caves_and_ores`
3. `biome_assignment`
4. `surface_decorations`
5. `structures`
6. `heightmap_refresh`
7. `persistence_or_streaming`

The code path still refreshes heightmaps for decoration and structure overlays,
marks generated chunks dirty for storage, and leaves persisted chunks winning
over regenerated fallback. `generation_stage_order_is_explicit` pins the order.

## M31.g Performance Notes

`mc-server` now logs a final `empty world pre-generation finished` event with
chunk count, elapsed milliseconds, and chunks per second after spawn-window
materialization. The hot path normalizes sidecar facts at startup; generated
chunks do not scan sidecar directories.

Debug-build probe run locally:

```sh
cargo test -p mc-worldgen generated_spawn_window_debug_budget_reports_throughput -- --ignored --nocapture
```

Observed local result: 25 chunks in 1933 ms, about 12.9 chunks/s. M31 debug
budget is 25 chunks under 10 seconds on this workstation for the focused probe.

Performance pass update on `dev/M31-worldgen-parity-slices`: terrain generation
now builds a per-chunk column plan before filling blocks, reusing cached world
coordinates, height, biome, surface/fill materials, and decoration hash across
base terrain, caves/ores, biome assignment, and decoration placement. Ore
placement now filters rules by column biome/range and probes deterministic
candidate cells instead of scanning every solid block through every rule; caves
sample bounded two-block vertical candidates below the non-surface solid range.
Known-y decoration overlays update heightmaps directly from the placed top while
structure overlays retain the safe rescan path.

The same pass also avoids decoration surface `get_block` calls by using planned
surface material, caps cave/ore work to underground solid ranges, reserves small
biome palettes during assignment, and batches spawn pre-generation worker sends
in `mc-server` to reduce channel churn without release-only behavior.

Debug-build probe after the pass:

```sh
cargo test -p mc-worldgen generated_spawn_window_debug_budget_reports_throughput -- --ignored --nocapture
```

Observed local result: 25 chunks in 465 ms, about 53.7 chunks/s.

## Scope Drift / M32 Handoff

M31 stayed within parity-slice scope and did not attempt bit-perfect vanilla
worldgen. Remaining gaps:

- Surface rules are still bucket-level approximations, not biome JSON surface
  rule execution.
- Cave/carver behavior is independent noise policy, not vanilla carvers.
- Feature placement consumes simple block/count facts only; providers,
  predicates, trunk/foliage placers, and full feature graphs remain out of
  scope.
- Structure support remains the narrow plains template marker seam plus
  structure-set spacing facts; jigsaw/template-pool/processor semantics remain
  deferred.
- Lighting and persistence gates should continue to be watched as larger
  cross-chunk structures or fluids are added.
