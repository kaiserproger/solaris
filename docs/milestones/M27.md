# M27 - Fluids and buckets

**Status:** code complete on `dev/M27-fluids` from `main` at local tag `m26`;
M27.a-M27.i have landed locally. Manual PrismLauncher gate is deferred to owner
run.
**Owning crates:** `mc-world` for scheduled fluid tick storage and Anvil
round-trip, `mc-data` for data-backed fluid/block facts, `mc-net` for bucket
interaction, simulation ticks, edit broadcast, relight, and inventory sync, and
`mc-test-harness` for survival-visible wire tests.

## Goal

Add the first playable fluid slice: water and lava can be placed and collected
with buckets, flow through the existing world-owned simulation path, interact in
a narrow tested set, relight and broadcast to nearby players, and persist across
restart.

M27 is not full vanilla fluid parity. Waterlogging, boats, kelp, cauldrons,
lava fire, exact vanilla flow timing, and broad edge-case behavior are out of
scope unless needed to keep the narrow bucket and flow loop correct.

## Strategy

1. Model fluid facts outside `mc-net`. Fluid-bearing block states, source/flowing
   levels, replaceability, and water/lava identifiers should come from sidecar
   block-state data, tags, or repo-owned fallback fixtures in `mc-data`.
2. Turn `fluid_ticks` from opaque Anvil extras into typed scheduled runtime
   state. M26 verified the same saved tick field shape for fluids, but M27 must
   intentionally model the queue before writing that root key.
3. Reuse the M26 batch edit backbone. Fluid waves should apply block deltas
   through the shared cache invalidation, heightmap, relight, dirty marking, and
   multiplayer broadcast path instead of ad hoc mutations.
4. Verify bucket wire behavior before adding packet or inventory assumptions.
   Existing packet types may be enough, but placement, pickup, ack, and slot
   resync order must be checked against local oracles where behavior is unclear.
5. Keep flow bounded and documented. The first implementation should be stable,
   deterministic, and playable, not a copied vanilla algorithm.

## Risks / Pitfalls

- Bucket use may rely on subtle client prediction, ack, and inventory slot order.
  Verify with `.analysis/protocol-dump.txt`, `javap`, or `wire-probe` before
  adding new codecs or changing packet assumptions.
- Flow can easily become a broad vanilla parity project. Keep the first rules
  deterministic, bounded, and documented.
- `fluid_ticks` currently round-trip as opaque extras. Once modeled, the codec
  must avoid duplicate root keys and preserve unrelated unknown data.
- Relighting each fluid cell independently could make flow waves expensive. Batch
  deltas and reuse the M26 edit path wherever possible.
- Waterlogging and special blocks are likely to collide with replaceability rules;
  defer them unless needed for the narrow acceptance tests.
- Current Anvil tick codecs use current tick `0` for saved delays. If M27 needs
  real save/load time, fix it deliberately for both modeled tick queues.

## Scope Drift / Follow-ups

- M27 keeps bucket inventory narrow: single held filled/source bucket flows are
  authoritative; stacked empty-bucket pickup is rejected instead of trying to
  split stacks into another slot.
- Flow is deterministic and bounded, not vanilla-exact. Water uses levels 0-7;
  lava uses a conservative 0-3 spread range and slower scheduled delay.
- Waterlogging, kelp, boats, bubble columns, cauldrons, lava fire/spread, rain,
  sponge behavior, and exact vanilla fluid tick order remain future work.
- Interaction rules cover the common solid conversions only: water touching lava
  source -> obsidian, water above lava flow -> stone, other water/lava flow
  contact -> cobblestone.
- The Anvil codec still serializes saved tick delays against current tick `0`,
  matching M26 behavior. A future world-time persistence pass should update both
  block and fluid tick codecs together.
