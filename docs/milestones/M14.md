# M14 - Movement-aware chunk subscriptions

**Status:** planned on `dev/M14-view-subscriptions`, cut from `main` at
tag `m13`.
**Estimate:** medium milestone, 20-36 h. This slice turns the M13 static
spawn-window stream into a player-position-driven view subscription while
keeping the worker-backed chunk pipeline bounded and stale-result safe.
**Owning crates:** `mc-protocol` for verified movement packet decoding,
`mc-net` for Play-loop position tracking and chunk subscription updates, and
`mc-test-harness` for wire-level movement/backpressure coverage.

## Goal

After M14, a player crossing chunk boundaries should cause Solaris to update
the client's center chunk and stream the newly visible view around the new
center. Results prepared for older view generations must be dropped before any
socket write or `LightCache` mutation, and low queue/budget settings must not
block inbound movement or edits while the stream is active.

M13 established the worker-backed chunk pipeline, but the target view is still
the initial spawn window. M14 keeps the same single-player scope and adds the
smallest movement-aware subscription layer on top of that pipeline.

## Strategy

1. **Plan and oracle before code.** Movement packet IDs and field layouts must
   come from `.analysis/protocol-dump.txt`, a regenerated javap dump, or a
   wire-probe capture. Do not infer packet IDs from memory.
2. **Decode only the minimum movement surface.** Track the packet or packets
   needed to observe player X/Z changes and chunk crossings. No anti-cheat,
   collision, sprint, vehicle, or pose validation in this milestone.
3. **Keep Play as the subscription owner.** The Play task owns player position,
   current center chunk, `SetCenterChunk` emission, scheduler replans, socket
   writes, and `LightCache` insertion.
4. **Reuse the M13 scheduler generation model.** `ChunkScheduler::replace_view`
   already creates generations and rejects stale completions. M14 should harden
   the Play integration around that behavior rather than inventing a global
   ticket engine.
5. **Prefer dropping stale work over cancelling workers.** Workers may finish
   old jobs after movement; accepted results are filtered at the Play boundary.
   Active cancellation can wait unless it is a tiny follow-up to the existing
   generation checks.
6. **Test pressure, not only the happy path.** Harness coverage should move the
   player while the initial window is still preparing under small queue/budget
   settings, then prove stale chunks are not emitted and inbound traffic still
   progresses.

## Target flow

```text
serverbound movement -> update player position -> chunk crossing? ->
SetCenterChunk -> scheduler.replace_view(new spiral) -> workers prepare ->
Play accepts current-generation results -> socket write + LightCache insert
```

The first implementation remains per-connection. Shared chunk tickets,
multi-player dedupe, region ownership, and unload/save scheduling are out of
scope.

## Sub-milestone decomposition

### M14.a - Plan

Add this milestone document only. Confirm the branch starts from `main` at tag
`m13`, then commit the plan before code.

### M14.b - Movement protocol oracle

Verify the serverbound Play movement packet IDs and field order from the
protocol oracle. Add the minimal `mc-protocol` packet type or types needed to
decode player X/Z movement during Play.

Acceptance for this slice:

- Packet IDs and field layouts are cited in code comments or commit body from
  the javap/wire-probe oracle.
- Unknown movement-adjacent packets remain ignored rather than guessed.
- Existing serverbound Play decoders and tests stay green.

### M14.c - Player position and chunk-crossing state

Track the player's last accepted position and current chunk center inside the
Play connection state. On decoded movement, update position conservatively and
detect chunk-boundary crossings from X/Z only.

This slice should not add reach checks, collision checks, teleport correction,
or authoritative physics. It only gives the chunk streamer a correct center.

### M14.d - View subscription replan

On chunk crossing, send `SetCenterChunk` for the new center and feed a newly
computed spiral view into the existing scheduler. Preserve default spawn-window
behavior when the player does not move.

Important integration points:

- reset or rebase any stream ordering state that assumes the old center;
- keep near chunks prioritized around the new center;
- avoid duplicate requests for chunks already finished and still visible;
- leave world storage and light computation ownership unchanged.

### M14.e - Stale result and ordering hardening

Exercise real worker results from older generations and ensure they are dropped
before socket writes, stream counters, completion accounting, or `LightCache`
insertion. If strict sequence ordering can deadlock after a replan, narrow the
ordering rule so a missing stale sequence cannot block current-generation
chunks.

### M14.f - Backpressure and movement harness coverage

Add wire-level harness coverage for moving while chunks are still preparing,
using small queue/budget settings to force backpressure. The test should prove
that movement is processed during active streaming and that chunks around the
new center eventually arrive.

Useful existing patterns are the chunk-stream full-window checks and the
block-edit responsiveness tests from earlier milestones.

### M14.g - Optional unload oracle or explicit deferral

Check whether a verified, cheap clientbound chunk-unload packet belongs in this
slice. If the ID/layout is not immediately clear or the integration adds risk,
document unload as M15+ and do not ship a guessed packet.

### M14.h - Tests, docs, and manual gate

## Acceptance criteria

1. Static spawn streaming still emits the full 441-chunk window at default view
   distance when the player stays near spawn.
2. Moving across a chunk boundary sends a new `SetCenterChunk`.
3. Moving across a chunk boundary eventually streams chunks around the new
   center.
4. Prepared chunks from old scheduler generations are dropped before socket
   write and before `LightCache` insertion.
5. Low queue/budget configuration exercises backpressure without blocking
   inbound movement, keepalive, or block-edit handling.
6. Existing block-edit and incremental-relight harness tests remain green.
7. Any new movement or unload packet IDs/layouts are cited from javap or
   wire-probe oracle output, not memory.
8. `cargo test --workspace` is green.
9. `cargo clippy --workspace --all-targets -- -D warnings` is clean.
10. `cargo fmt --all -- --check` is clean.
11. Manual PrismLauncher 26.1.2 gate remains usable on the debug server.

## Out of scope

- Full global multi-player ticket graph.
- Folia-style region ownership.
- Entity scheduler, AI, redstone, fluids, or block physics.
- Real anti-cheat reach or movement validation.
- Collision, swimming, flying, sprint, or vehicle movement semantics.
- Tick-window edit batching and multi-edit relight batching.
- Disk-persistent light arrays.
- Vanilla algorithm ports.

## Pitfalls

- **Guessed protocol shapes.** Movement decoding must use the oracle workflow;
  packet names alone are not enough.
- **Ordering deadlocks after replan.** If current-generation emission waits for
  an old missing sequence, movement will appear to stall the stream.
- **Light cache pollution.** Stale prepared chunks must not update the
  connection light cache.
- **Unbounded stale work.** Rapid movement can leave workers finishing old jobs;
  bounded queues and generation checks are the safety boundary for M14.
- **Duplicate chunk emission.** Replanning around an overlapping view should not
  resend already-finished chunks unnecessarily unless doing so is required for
  correctness.
- **Fake unload support.** Client chunk unload should ship only if the packet is
  verified and the implementation is small.
- **Config drift.** Defaults must preserve the M13 manual-gate behavior.

## Open questions

- Which serverbound movement packet subset is sufficient for M14?
  Default: decode only the packet variants the real client emits for normal
  walking across chunk boundaries, verified by oracle.
- Should the scheduler treat already-finished chunks from an old generation as
  reusable if they remain in the new desired view?
  Default: yes, keep the M13 `replace_view` behavior unless tests expose a
  client-visible issue.
- Should replan clear all ready results or retain current-generation ready
  chunks still visible in the new view?
  Default: prefer correctness first; retain only if generation and ordering make
  it obviously safe.
- Should M14 send unloads for chunks outside the new view?
  Default: defer unless the verified packet and integration are cheap.
- How aggressive should rapid movement cancellation be?
  Default: generation-drop at acceptance boundary is enough for M14; true worker
  cancellation can be M15+.
