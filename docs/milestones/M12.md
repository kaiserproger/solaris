# M12 - Progressive worldgen and chunk streaming

**Status:** plan on `dev/M12-progressive-worldgen-streaming`, cut from
`main` at tag `m11`. Awaiting owner review before code.
**Estimate:** large release-critical milestone, 24-40 h. This moves the
fresh-world spawn path from one synchronous view-distance flush to a
progressive Play loop that keeps the client responsive while the rest of
the window streams.
**Owning crates:** `mc-net` for the Play event loop, chunk stream state,
and wire timing; `mc-world` and `mc-worldgen` if storage/generation need
async boundaries; `mc-test-harness` for progressive streaming and
responsiveness coverage.

## Goal

On a fresh empty world, Solaris should send the spawn chunk and nearby
rings quickly, enter a usable Play state, and continue streaming the
remaining view-distance chunks without blocking keepalive or inbound
player packets.

The M11 manual fresh-world gate showed the spawn chunk can be prepared
early, but the connection still waits for the full 441-chunk window:

```text
view_distance=10 staged=529 emitted=441 absent=0 bytes=8239171
fetch_ms=6345 build_ms=57112 write_ms=0 first_chunk_ms=155 elapsed_ms=64232
```

M12 treats the 57 s synchronous build phase as the release blocker. The
first slice measures it more precisely; the main slices then make chunk
work budgeted and progressive before adding heavier worker-pool machinery.

## Strategy

1. **Measure before moving work.** Keep the M11 timing line but split the
   coarse `build_ms` and `write_ms` buckets enough to distinguish chunk
   data encode, full light compute, light wire packing, frame compression,
   and socket write cost.
2. **Factor the stream before changing semantics.** Introduce a
   connection-owned chunk-stream state that preserves the current spiral
   order and final coverage, then make it run in bounded steps.
3. **Enter the Play loop early.** Send Login Play, position/game-event,
   center chunk, and the first near chunks, then select between keepalive,
   inbound frames, and chunk-stream budget work.
4. **Keep near chunks biased.** Spawn chunk and the first rings should be
   prepared before distant rings; full view-distance coverage remains the
   eventual target, not a Play-entry prerequisite.
5. **Defer parallelism until proven necessary.** Start with cooperative
   scheduling inside the connection task. If generation/loading still
   monopolizes the world lock, add a later slice for `spawn_blocking` or a
   small prepare worker boundary.

## Current bottleneck map

- `crates/mc-net/src/play.rs` `handle` sends initial Play packets, then
  awaits `emit_chunks_around` before inventory seed and `keepalive_loop`.
- `emit_chunks_around` walks `spiral_chunks`, loads/generates a 3x3
  neighbourhood through `WorldStorage::get_chunk`, builds one
  `LevelChunkWithLight`, writes it, and only returns after all 441 chunks.
- `build_chunk_packet` synchronously runs chunk data encode,
  heightmaps, full `compute_chunk_light_in`, light wire encode, and
  `LightCache` warmup.
- `keepalive_loop` currently starts after the full burst, so packets sent
  by the client during fresh-world streaming wait behind the burst.
- Harness tests in `chunk_stream`, `block_edit`, `incremental_relight`,
  and `persistence_inventory` assume full spawn-window drain before later
  interaction; M12 should keep full-coverage coverage while adding early
  responsiveness assertions.

## Sub-milestone decomposition

### M12.a - Timing breakdown

Extend the existing spawn-window log so one fresh-world manual run shows
where chunk build time goes. Track at least:

- storage/generation fetch time;
- chunk data and heightmap encode time;
- light compute time;
- light packet encode time;
- packet frame compression time when M11 compression is active;
- socket write time;
- first chunk and first near-ring latency.

This slice should not change stream ordering or semantics. It exists to
make the later improvements falsifiable.

### M12.b - Chunk stream state

Split `emit_chunks_around` into a connection-owned stream state with the
spiral queue, counters, reusable light workspace/cache access, and a
small `poll`/`step` style API. The first implementation may still be
called in a loop until complete, preserving current tests and behaviour.

The state should make cancellation cheap: dropping the connection drops
the queue and any un-emitted prepared chunks.

### M12.c - Progressive Play loop

Move chunk streaming into the Play event loop. The loop should select or
otherwise fairly rotate between:

- keepalive ticks;
- inbound client frames;
- bounded chunk-stream work;
- disconnect/shutdown handling.

The connection must no longer require the full view-distance window before
starting keepalive and read handling. Inventory seed packets should be
sent early enough for normal interaction instead of being trapped behind
distant chunk rings.

### M12.d - Budgeted chunk work and near-ring policy

Cap chunk work per turn by a small chunk count, elapsed time budget, or
both. Preserve the existing spiral order, but expose log counters for
first chunk, first ring, and full window completion.

Acceptance for this slice is operational, not just structural: a fresh
world should show near chunks emitted early and distant rings continuing
after the connection has entered the responsive Play loop.

### M12.e - Async prepare boundary, if needed

If M12.a-M12.d still show long stalls while loading/generating or building
individual chunks, move the expensive prepare step behind a narrow async
boundary. Prefer the smallest safe boundary first: `spawn_blocking` for
chunk prepare or a single per-connection worker, not a general-purpose
worldgen pool.

This slice is deliberately conditional. Do it only if measurements show
cooperative scheduling alone still leaves visible stalls.

### M12.f - Tests, docs, and manual gate

Update harness expectations so tests no longer require all 441 chunks
before the Play loop can process later traffic. Keep one full-coverage
test, and add coverage for early spawn/near chunk arrival and inbound
packet or keepalive responsiveness while chunks are still streaming.

Close out with the standard gates:

```sh
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

Then prepare the debug server manual gate and say `готов, подключайся` for
PrismLauncher 26.1.2 against a deleted fresh `.analysis/test-world`.

## Acceptance criteria

1. A fresh empty world no longer blocks the Play read/keepalive loop for
   roughly 60 s while flushing the full view-distance window.
2. Logs include concrete timings for first chunk, first near ring, full
   window, and the major prepare/encode/light/compression phases.
3. Spawn chunk and near rings are emitted early; remaining chunks stream
   progressively in the background.
4. Existing wire packet shapes stay valid: `LevelChunkWithLight`,
   `LightUpdate`, compression framing, and single-edit behaviour do not
   regress.
5. Harness tests cover both eventual full view-distance coverage and
   responsiveness before full coverage.
6. `cargo test --workspace` is green.
7. `cargo clippy --workspace --all-targets -- -D warnings` is clean.
8. `cargo fmt --all -- --check` is clean.
9. Manual PrismLauncher 26.1.2 gate on a fresh world reports a usable
   early spawn and progressive streaming.

## Out of scope

- Full multi-player chunk scheduling or ticket simulation.
- A general worldgen worker pool.
- Disk-persistent light arrays.
- Pre-baked lighting for generated chunks.
- Replacing Solaris terrain generation with vanilla algorithms.
- Survival reach validation, break timing, or tool durability.
- New clientbound protocol packets unless an oracle proves one is needed.

## Pitfalls

- **World lock stalls.** Cooperative scheduling does not help if one step
  holds `WorldHandle` for too long. Measure before choosing the async
  boundary.
- **Light cache warmup.** Edit-side incremental relight depends on the
  connection light cache. Progressive streaming must keep the cache
  coherent for emitted chunks and avoid assuming distant chunks are warm.
- **Test false positives.** A test that only waits longer for 441 chunks
  does not prove responsiveness. Add checks that traffic is handled before
  full coverage.
- **Packet ordering.** Initial Play packets, center chunk, teleport, chunk
  data, inventory, and block-change acks must remain in an order vanilla
  clients tolerate.
- **Compression accounting.** M11 compression means frame compression can
  hide inside write timing. Keep timing labels honest.
- **Overbuilding architecture.** Do not introduce a general scheduler or
  worker pool unless the measured single-connection path needs it.

## Open questions

- What near-ring target is sufficient for manual usability: spawn chunk
  only, ring 1, or ring 2? Default: ring 2 if it fits the early budget.
- Should inventory seed move before any chunk data, after spawn chunk, or
  after near rings? Default: after spawn/near chunks but before distant
  rings.
- Should the first progressive implementation be chunk-count-budgeted,
  time-budgeted, or both? Default: both, with conservative constants.
- If async prepare is needed, should it be per-connection or shared?
  Default: per-connection/smallest boundary for M12.
