# M89 - Auth, Chat, Permissions, And Anti-Corruption MVP

**Status:** Partial implementation in progress. Quality label: `draft`.

## Agent Start Prompt

Read the current login/session-auth implementation and this milestone before
changing security behavior. Treat older statements that Solaris is offline-only
as historical: the current tree has encrypted online-mode login and Mojang
session verification. Harden one bounded public-facing slice at a time and keep
claims narrower than a full anti-cheat or moderation system.

## Scope

- Online-mode encryption/session authentication and public-bind policy.
- Duplicate-name/profile handling, whitelist, banlist, operator persistence,

- Chat/command policy: basic chat if scoped, or commands-only with safe

- Movement, reach, container, malformed packet, and resource-pack status

## Acceptance

  obvious reach/mode constraints in scoped paths.
- Local-dev OP defaults are disabled or rejected outside loopback development;
  operator/whitelist/ban policy has restart coverage.
- Public-bind authentication claims are executable, not warning-only.
- Security claims remain scoped; no full anti-cheat claim.

## Current Authentication Baseline

The original bounded M89 admission slice was superseded by later auth work. On
the current tree Solaris no longer rejects `online_mode = true` merely because
session authentication is absent:

- online login emits the 26.1.2 RSA `EncryptionRequest`, verifies the encrypted
  challenge, enables stream encryption, computes the Java-compatible Minecraft
  server hash, and verifies `hasJoined` through `MojangSessionVerifier`;
- a custom `SessionVerifier` can be injected in tests, while production builds a
  Mojang verifier automatically;
- `prevent_proxy_connections = true` includes the connecting IP in session
  verification;
- public bind addresses fail closed unless online mode is enabled, and
  `allow_local_dev_operators` is rejected on public binds;
- whitelist/ban checks run against the verified profile name/UUID in online
  mode and the offline profile identity in offline mode;
- duplicate profile/name admission remains fenced at Play registration;
- omitted `[admin]` grants no operator privileges, and loopback auto-OP is an
  explicit opt-in only.

Executable coverage includes the real TCP encrypted-login tests in
`crates/mc-server/tests/login.rs` and the session-verifier/unit coverage in
`mc-net`.

## 2026-08-27 File-Backed Access-Control Checkpoint

The current checkpoint adds an explicit restart-stable source for operators,
whitelist entries, and bans without replacing the existing inline TOML policy.

### Configuration

`[admin]` accepts:

```toml
operators = ["InlineOp"]
operators_file = "ops.json"
allow_local_dev_operators = false
```

`[auth]` accepts:

```toml
whitelist_enabled = true
whitelist = ["InlineAllowed"]
whitelist_file = "whitelist.json"
banned_players = ["InlineBan"]
banned_players_file = "banned-players.json"
```

Relative file paths resolve from the directory containing the server config.
File-backed identities are merged with inline identities on every fresh server
startup. The files use vanilla-style JSON profile arrays: each object must
contain a valid `name`, `uuid`, or both. Extra fields such as operator level,
`bypassesPlayerLimit`, ban reason, source, creation time, or expiry are ignored
by this bounded identity-only reader.

The reader is fail-closed:

- an explicitly configured missing/non-file path is an error;
- each file is capped at 1 MiB with metadata and post-read size checks;
- each file is capped at 4096 profile objects;
- names must match Solaris/Minecraft login syntax (`3..=16` ASCII
  alphanumeric/underscore);
- UUIDs must parse and are normalized to canonical form;
- a profile object with neither name nor UUID is rejected;
- malformed JSON rejects both `mc-server --check` and normal startup.

Names/UUIDs are deduplicated before merge. Existing downstream policy then
normalizes the combined set again. Ban precedence over whitelist is unchanged.

### Runtime/restart evidence

Focused unit coverage proves relative-path resolution, inline+file merge,
vanilla-style extra fields, UUID/name normalization, fresh-config reload, and
all malformed/bounded failure cases.

A TCP integration test starts one server from the file-backed policy, proves a
whitelisted player reaches compression while a non-whitelisted player receives
`LoginDisconnect`, edits the same whitelist/ban files, starts a fresh second
server, and proves the now-banned whitelisted player is denied while the newly
whitelisted player is accepted.

A Play integration test uses `operators_file` and the actual
`ClientboundCommands` tree. The file-backed operator sees restricted `/time`, a
member does not; after rewriting `ops.json` and starting a fresh server, the old
operator loses `/time` and the new file-backed operator gains it.

The `mc-server --check` integration gate proves valid file-backed identities
appear in effective configuration output while missing and malformed configured
files exit non-zero with the exact field/path context.

Detailed evidence is recorded in
[`../evidence/m89-file-backed-access-control-2026-08-27.md`](../evidence/m89-file-backed-access-control-2026-08-27.md).

## Remaining M89 Work

This checkpoint does **not** make the whole M89 milestone complete. Remaining
work must be audited against the current tree rather than the historical draft:

- no server-side commands currently mutate/write `ops.json`, `whitelist.json`,
  or `banned-players.json`; the files are externally managed durable startup
  policy;
- chat signing/moderation/public chat policy still needs a current-scope audit;
- malformed/reach/movement/container/resource-pack fail-closed coverage exists
  in several later milestones but has not yet been consolidated into one current
  M89 anti-corruption matrix;
- auth concurrency/rate/abuse behavior and a public real-client deployment gate
  still need explicit current-tree disposition;
- no full anti-cheat claim is made.
