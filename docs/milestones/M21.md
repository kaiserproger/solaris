# M21 - Worldgen features

**Status:** planned on `dev/M21-worldgen-features` from local tag `m20`.
Manual gate remains disabled in the current YOLO phase; automated cargo gates are
authoritative unless the owner explicitly asks for PrismLauncher.
**Owning crates:** `mc-data` for vanilla sidecar readers, `mc-worldgen` for
feature/rule application, `mc-world` for generated chunk persistence and
heightmap bookkeeping, `mc-server` for startup wiring, and `mc-test-harness` for
disk-backed integration coverage.

## Goal

Turn the M20 worldgen seams into visible generated-world content while keeping
Solaris' generator deterministic and owned by Solaris. M21 should feed generation
from local vanilla data where ADR 0001 allows it, but it must not copy Mojang
terrain, feature-placement, or jigsaw algorithms and must not claim vanilla
worldgen parity.

## Strategy

1. Treat sidecar data as optional input: every loader has a deterministic Solaris
   fallback when local vanilla data is missing or incomplete.
2. Keep generator policy small and explicit. Convert parsed data into Solaris rule
   types instead of trying to execute the full vanilla feature graph.
3. Make visible features bounded: generation must remain predictable for spawn
   pre-generation and chunk streaming.
4. Refresh heightmaps and mark generated chunks dirty whenever feature overlays
   modify blocks.
5. Use real code paths in tests. Sidecar-gated tests may skip when local vanilla
   data is absent, but fallback tests must run everywhere.

### M21.b - Ore data feeds generation

Convert parsed `mc_data::worldgen_ores` output into `mc-worldgen` ore rules or a
new data-shaped equivalent, then wire those rules into startup when the sidecar is
available.

Acceptance:

- Missing or partial ore sidecar data falls back to Solaris default ore rules.
- Tests prove diamond, gold, emerald, and deepslate ore families reach generation
  through the data-fed rule path rather than hardcoded branch logic.
- Existing Solaris ore distribution remains deterministic for a fixed seed.

### M21.c - Biome bucket data input

Load overworld biome bucket membership from local sidecar tags/data where
available, while preserving `BiomeRules::vanilla_overworld()` as the portable
fallback. The selector remains Solaris-owned; only bucket membership becomes
data-fed.

Acceptance:

- Sidecar-backed biome rules can be built without requiring generated Mojang data
  in git.
- Missing tags/data fall back cleanly at server startup.
- All vanilla overworld biome ids remain reachable by the selector.
- Tests cover both fallback and sidecar-backed bucket construction.

### M21.d - Surface decorations

Add bounded deterministic surface feature passes for biome-appropriate visible
content: trees, grass, flowers, pumpkins, sugar cane, and cactus where registry
data makes those blocks available.

Acceptance:

- Decorations are deterministic for seed and chunk position.
- Density is bounded and does not create unbounded cross-chunk work.
- Generated chunks visibly contain at least one biome-appropriate decoration
  family in sampled regions.
- Decoration overlays refresh highest-opaque columns and heightmaps.

### M21.e - Structure expansion beyond marker

Extend the M20 structure seam from one plains fountain marker toward a small,
explicit set of deterministic village-like pieces loaded from local templates
where present. Placement stays Solaris-owned and non-jigsaw-parity.

Acceptance:

- Local template blocks resolve through `BlockRegistry`; air, jigsaw, and
  structure-void-like placeholders remain ignored.
- Placement can select more than one small piece or piece variant when sidecar
  templates are available.
- Cross-chunk paste behavior is tested without committing template bytes.
- Documentation and test names avoid claiming vanilla jigsaw parity.

### M21.f - Generation bookkeeping and persistence

Ensure feature and structure overlays are represented as normal generated block
changes that survive Anvil flush/reopen through the existing storage path.

Acceptance:

- Generated feature/structure chunks are dirty before flush and clean after
  successful flush.
- `flush_dirty` / reopen tests prove at least one decoration and one structure
  overlay persist on disk.
- Heightmaps/highest-opaque columns match the overlaid blocks after reopen.
- Existing chunk streaming, block edit, persistence, mob presence, and worldgen
  harness tests remain green.

## Risks / Pitfalls

- Vanilla data can describe far more than Solaris should execute in M21. Keep the
  conversion narrow and explicit instead of building a generic feature graph.
- Decorations can accidentally create cross-chunk mutation explosions. Use local
  bounded plans and test edge chunks.
- Structure templates are Mojang bytes and must remain local-only. Track loaders,
  rules, and tests, never extracted templates.
- Heightmap refresh bugs are easy to hide until streaming or persistence. Test the
  post-overlay heightmap state directly.
