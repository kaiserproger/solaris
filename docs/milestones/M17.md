# M17 - Vanilla entity and worldgen foundation

**Status:** landed locally on `main` after tag `m16`; automated gates are
green. The owner-run manual vanilla-client gate is disabled by active YOLO mode
until the owner re-enables it.
**Estimate:** large milestone, 35-70 h. This milestone moves Solaris back to
vanilla foundations before any mod replica work: non-player entities, mob
attributes/AI seams, and the next terrain-generation layer. It deliberately
does not start Villager Recruits/Workers or any other modpack replica. Vanilla
parity work has priority over mod-facing features until the server can sustain
large vanilla worlds with many active entities.
**Owning crates:** `mc-entity` for runtime entity state, attributes, and AI
seams; `mc-protocol` for verified entity/mob packets; `mc-net` for visibility
and per-connection routing; `mc-worldgen`/`mc-world` for caves, ores, and fluid
terrain features; `mc-test-harness` for wire and worldgen coverage.

## Goal

After M17, Solaris should have the first reusable vanilla entity foundation:
server-owned non-player entities can exist, tick, become visible to clients,
move, and despawn using verified 26.1.2 packets. The same foundation should
carry minimal vanilla-style attributes and goal hooks so later milestones can
add real mob parity without rewriting the network/session layer.

M17 also starts closing the biggest worldgen gaps left by M7: generated worlds
should no longer be only hill-noise stone/dirt/grass columns. The accepted slice
adds deterministic cave/ore/fluid generation primitives behind tests, while
keeping village/structure generation as a planned follow-up unless the entity
work lands faster than expected.

Entity design must assume very high active-entity counts. M17 should not build a
small object-oriented model that later collapses under load. Runtime storage and
tick APIs should be data-oriented, batchable, and ready for future entity-tick
parallelism across independent batches. Do not commit to Folia-style region
ownership as the primary scaling model; the preferred long-term direction is the
finest practical parallelization of entity ticks while keeping deterministic
world mutation boundaries.

## Non-goal correction

This milestone is **not** the `PROJECT_SPEC` roadmap's old M17
"Villager Recruits/Workers replica". The roadmap drifted substantially after
M4, and M16 showed Solaris still needs vanilla foundations before mod work.
Modpack replicas are deferred until vanilla mobs, AI, attributes, structures,
and richer worldgen are in place.

## Strategy

1. **Oracle first.** Every new packet ID, packet field order, entity type id,
   metadata shape, and attribute wire field is verified from
   `.analysis/protocol-dump.txt`, `javap`, `wire-probe`, or vanilla reports.
   No packet IDs or layouts are guessed.
2. **Generalize M16, do not fork it.** Reuse loaded-chunk-driven visibility and
   Play-task-owned outbound queues, but move non-player entity data into
   `mc-entity` instead of growing player-specific structs in `mc-net`.
3. **Data-oriented first.** Store hot entity state densely and expose batch/tick
   seams that can later run in parallel. Avoid per-entity heap/object graphs on
   hot paths.
4. **Start with server-owned passive entities.** The first renderable entity can
   be simple, but the data model must not be player-only. Avoid combat and
   breeding until attributes/spawn/move/despawn are stable.
5. **Attributes before serious AI.** Health, movement speed, follow range, and
   attack damage need a typed attribute model before goals can behave sanely.
6. **AI seams before parity.** Add deterministic goal ticking and navigation
   seams in M17; do not attempt full vanilla Brain/Sensor parity in the first
   pass.
7. **Vanilla first.** Whenever a choice conflicts between mod convenience and
   vanilla parity/scalability, choose vanilla parity/scalability. Mod-facing
   abstractions wait until the vanilla base is credible.
8. **Worldgen features stay deterministic.** Caves, ores, and fluids use
   Solaris-owned algorithms. Vanilla data can provide block ids and registry
   names, but no Mojang algorithm ports.
9. **Keep village generation out of the critical path.** Villages require
   structures, POIs, villagers, beds/jobs, and pathfinding. M17 may document the
   seam, but it should not block the entity/worldgen foundation from landing.

## Target flow

```text
server starts -> load vanilla registries -> create entity/worldgen services

chunk generated -> terrain base -> cave carving -> ore/fluid features
  -> lighting/storage/streaming as before

entity spawned -> entity table assigns runtime id/uuid/type/pose/attributes
  -> visibility diff from observer loaded chunks
  -> observer Play task receives spawn/metadata/attributes commands

tick -> entity goals update intent -> movement/nav updates pose
  -> observers receive movement/head/metadata deltas

despawn/unload -> observers receive remove packet
```

## Sub-milestone decomposition

### M17.a - Plan

Add this milestone document only. Confirm the work starts from `main` after tag
`m16`, then wait for owner review before protocol or code changes.

### M17.b - Entity and mob protocol oracle

Verify the minimal packet set for one non-player vanilla entity lifecycle:

- spawn/add entity;
- entity metadata/synced data, if the chosen entity requires it to render;
- attributes, if the chosen entity or health bar/state needs them;
- movement/rotation/head rotation;
- removal;
- animation/status packets that are needed for basic client-visible feedback.

Acceptance for this slice:

- Every new packet has a cited vanilla metadata name, wire id, and field order.
- Entity type ids come from local vanilla reports/registries, not literals from
  memory.
- Tests pin packet bytes only after the oracle pins the layout.

### M17.c - Runtime entity table

Implement the first `mc-entity` runtime model:

- stable runtime entity ids and UUIDs;
- entity type id/name;
- position, rotation, velocity, on-ground flag;
- loaded chunk coordinate;
- basic lifecycle state: alive, despawning;
- snapshot/delta API for networking;
- dense slot storage with stable ids mapped to slots;
- batch iteration/tick seams suitable for later parallel execution.

This should be standalone and unit-tested without sockets. It does not need ECS
yet unless the implementation stays small and clearly useful. Avoid a design
that requires locking each entity independently during normal ticks.

### M17.d - Non-player visibility routing

Extend M16 visibility routing from connected players to server-owned entities.
Visibility remains observer-loaded-chunk-driven. Play tasks still own socket
writes; `mc-net` routes spawn/move/despawn commands through outbound queues.

Acceptance for this slice:

- A server-owned entity in a loaded observer chunk spawns for that observer.
- Movement is sent only to observers that currently see the entity.
- Moving out of range or despawning sends removal and does not resurrect via
  stale queued updates.

### M17.e - Attributes foundation

Add a minimal vanilla-style attribute model in `mc-entity` and the verified
clientbound attribute update packet if required by the chosen mob path:

- max health;
- movement speed;
- follow range;
- attack damage, even if combat use is deferred.

The model should support base values and modifiers later, but M17 can encode
only base values if that is all the first mob needs.

### M17.f - First passive mob baseline

Spawn a deterministic passive vanilla mob near the test spawn and make it
visible to clients with correct lifecycle and basic idle motion. Candidate mob
is chosen only after the oracle shows the minimal metadata/attribute needs.

Acceptance for this slice:

- Vanilla client renders the mob without disconnecting.
- The mob id/type/metadata are verified.
- The mob can tick and move a small deterministic path.
- Existing player visibility and block edit behavior remain green.

### M17.g - AI tick seams

Add the first goal-tick API for mobs:

- idle/look-around goal;
- wander intent;
- follow-target seam without implementing full combat;
- deterministic fixed-tick scheduling;
- no async tasks inside the entity tick;
- tick APIs that can be split into independent batches in a future milestone.

This slice is about architecture and tests, not full vanilla parity.

### M17.h - Worldgen feature layer

Upgrade `mc-worldgen` beyond height columns:

- deterministic cave carving primitive;
- deterministic ore vein placement for at least coal/iron/copper or a similarly
  small vanilla subset;
- simple water/lava pocket or lake primitive where chunk encoding/storage can
  represent the resulting blocks correctly;
- tests proving determinism, block bounds, and persistence through Anvil IO.

Fluid simulation is out of scope; this is terrain placement only.

### M17.i - Visible interaction polish

Close the M16 residual gap by broadcasting verified connected-player hand swing
animation to visible observers for break/place/use flows. This is deliberately a
small polish slice after the entity packet oracle work, not the milestone's main
scope.

### M17.j - Harness, validation, and closeout

Add focused coverage for:

- packet byte/round-trip tests for newly verified packets;
- `mc-entity` unit tests for ids, snapshots, attributes, and goal ticks;
- harness coverage for non-player entity spawn/move/despawn visibility;
- worldgen tests for caves/ores/fluids determinism and persistence;
- regression coverage for M16 player presence and M15 block edits.

Close out with:

```sh
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

Manual gate: run the debug server with `example.toml`; the owner connects a
vanilla 26.1.2 client, confirms the first mob is visible and stable, then uses a
second client to verify player presence/block edits still work.

## Acceptance criteria

1. Start point is `main` after tag `m16`; local `example.toml`, `.serena/`,
   `.analysis/`, `data/vanilla/data/**`, and `work/` artifacts are not included.
2. No modpack replica code lands in M17.
3. Every new packet and entity/attribute id is oracle-verified before use.
4. `mc-entity` owns reusable non-player entity state instead of baking mobs into
   `mc-net` session structs.
5. Hot entity state is stored in a dense, batchable representation suitable for
   many active entities.
6. At least one server-owned non-player entity can spawn, move, and despawn for
   vanilla clients.
7. Entity visibility is scoped to observer loaded chunks.
8. Basic attributes exist for mobs and are unit-tested.
9. Basic AI tick seams exist, are deterministic, and expose future parallel batch
   boundaries.
10. Generated worlds include at least one tested cave/ore/fluid feature layer.
11. Existing M16 connected-player visibility remains green.
12. Existing block edit, chunk stream, persistence, relight, and worldgen tests
    remain green.
13. `cargo test --workspace` is green.
14. `cargo clippy --workspace --all-targets -- -D warnings` is clean.
15. `cargo fmt --all -- --check` is clean.

## Harness plan

- A client connects near the deterministic test entity and receives the verified
  spawn sequence for that entity.
- The entity moves or rotates while the client remains still; the client receives
  movement updates and no unrelated center-chunk update.
- The entity moves outside visibility or despawns; the client receives removal
  and no later stale update.
- Two clients still see each other after M16 player presence packets.
- The existing two-client block-edit test still confirms actor ack plus observer
  block/light delta while both players are visible.

## Out of scope

- Villager Recruits/Workers or any modpack replica.
- Full vanilla mob parity in one milestone.
- Full combat, damage, breeding, taming, projectiles, effects, or loot tables.
- Full Brain/Sensor parity.
- Village/structure generation unless all core entity/worldgen slices land early.
- Fluid simulation; M17 terrain fluids are placed blocks only.
- Plugin API, scripting, event bus, or public extension hooks.
- Copying Mojang worldgen/entity algorithms.

## Pitfalls

- **Guessed protocol.** Entity metadata and attributes are version-sensitive;
  verify before coding.
- **Player-specific leakage.** M16 player visibility is useful but should not
  become the general entity model.
- **Unscalable storage.** A per-entity object graph or lock-heavy model will make
  later mob parity and high entity counts expensive to recover from.
- **Client invisible mobs.** Many mobs need metadata/default synced data to
  render correctly; choose the first candidate after oracle proof.
- **Unbounded entity ticks.** Entity updates must not block Play socket tasks or
  chunk workers.
- **Parallelism dead end.** Region ownership can be useful for world mutation,
  but should not be the only scaling story. Keep entity tick work batchable.
- **Worldgen chunk seams.** Caves and ore veins crossing chunk borders must be
  deterministic from world coordinates, not generation order.
- **Scope creep.** Villages, full combat, and full AI parity can consume months;
  keep M17 focused on foundations that later milestones can reuse.

## Open questions

- Which first vanilla mob gives the best signal with the smallest verified
  metadata surface?
  Default: pick after protocol oracle; prefer a passive mob if it renders with a
  small metadata/attribute set.
- Should non-player entity ticking live in `mc-net` initially or behind a server
  world service?
  Default: keep runtime state in `mc-entity`; let `mc-net` only adapt snapshots
  to outbound commands for M17.
- Should M17 implement caves/ores before or after the first mob is visible?
  Default: entity protocol/runtime first, worldgen feature layer second, because
  protocol mistakes are riskier for the manual gate.
- Are villages an M17 stretch or a later milestone?
  Default: later milestone. Villages require structures, POIs, villagers, beds,
  professions, and navigation; M17 should create prerequisites.

## Status / validation appendix

- Protocol oracle:
  - `CLIENTBOUND_ANIMATE` = game-CB index 2, wire id `0x02`; body is VarInt
    entity id plus unsigned byte action. Verified with `javap -p -c` against the
    inner `server-26.1.2.jar` from `.analysis/server.jar`.
  - `CLIENTBOUND_ENTITY_EVENT` = game-CB index 34, wire id `0x22`; body is i32
    entity id plus signed byte event id. Verified with the same server jar.
  - `CLIENTBOUND_SET_ENTITY_MOTION` = game-CB index 101, wire id `0x65`; body is
    VarInt entity id plus `Vec3.LP_STREAM_CODEC`. Verified with the same server
    jar.
  - `minecraft:cow` entity type protocol id is `30` from local
    `data/vanilla/reports/registries.json`.
- `mc-entity` now has dense slot-backed runtime entity storage, stable runtime
  ids, UUID/type/pose/velocity/lifecycle snapshots, vanilla-style base
  attributes, deterministic idle/wander/follow goal seams, and batch ranges for
  future parallel entity ticks.
- `mc-net` now seeds one deterministic server-owned cow near spawn, ticks server
  entities on a shared interval, routes cow spawn/move/despawn through existing
  Play-task-owned outbound queues, and keeps visibility scoped to observer loaded
  chunks.
- `mc-protocol` now has typed packets and byte/round-trip tests for the verified
  simple entity packet set.
- `mc-worldgen` now applies Solaris-owned deterministic cave carving, coal/iron/
  copper ore placement, deepslate/deepslate-ore layers, and water/lava cave

  the generated terrain surface, and avoid walking through the air on uneven

  the active `example.toml` server regenerates a fresh M17 world from scratch.
- `mc-test-harness` adds `mob_presence.rs`, asserting a Play client receives the
  server-owned cow spawn and later motion. The existing block-edit two-client
