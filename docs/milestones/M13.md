# M13 - Async chunk pipeline and worker pools

**Status:** plan on `dev/M13-async-chunk-pipeline`, cut from `main` at
tag `m12`.
**Estimate:** large milestone, 36-64 h. This is the first real multicore
chunk pipeline slice: separate scheduling/ownership from socket IO, move
load/generate/light/encode/compress work onto bounded workers, and keep
the M12 progressive stream semantics under explicit budgets.
**Owning crates:** `mc-net` for Play-loop integration and send ordering,
`mc-world` for async-safe chunk load/generate/cache seams, `mc-server` for
config and runtime construction, and `mc-test-harness` for responsiveness,
coverage, and cancellation tests.

## Goal

After M13, initial and ongoing chunk streaming should no longer be a
single connection task doing storage, worldgen, lighting, packet encode,
compression, and socket writes in one cooperative loop. Solaris should
have a bounded chunk pipeline that can use multiple cores while preserving
client-visible ordering and responsiveness.

M12 made fresh-world streaming usable by slicing work cooperatively:

```text
view_distance=10 staged=529 emitted=441 absent=0 bytes=8239171
fetch_ms=6290 light_compute_ms=8310 first_chunk_ms=43
ring1_complete_ms=280 ring2_complete_ms=763 elapsed_ms=16371
```

M13 keeps that early-spawn behaviour, then moves the heavy stages behind
clear ownership and bounded queues so one slow chunk, player movement, or
future multi-player load does not monopolize the async connection task.

## Strategy

1. **Define the pipeline boundary first.** The Play task owns socket IO,
   inbound packets, keepalive, player view subscription, and final packet
   ordering. Worker tasks own bounded load/generate/light/encode/compress
   jobs and return prepared outputs.
2. **Build a minimal scheduler, not a full server architecture.** M13 needs
   per-player chunk requests, priority by spiral distance, cancellation of
   stale work, and bounded result queues. It does not need entity regions,
   plugin hooks, or a full ticket graph.
3. **Separate IO and CPU pools.** Region reads/writes belong on a bounded
   IO pool. Worldgen, lighting, packet encode, and compression belong on a
   CPU pool. The first implementation can be small, but the ownership must
   not mix all stages into one unbounded queue.
4. **Preserve M12 client semantics.** Spawn chunk and near rings still win;
   full 441-chunk coverage remains eventual; inbound edits and keepalive
   must progress while distant chunks are preparing.
5. **Make budgets the policy layer.** Config-backed send/load/generate/
   prepare budgets cap pressure and memory, but they sit on top of the
   async pipeline rather than replacing it.
6. **Use Paper as an architecture reference only.** Paper/Moonrise validates
   the split between common workers, IO workers, chunk-loading rates, cache
   sizing, compression policy, and delayed unload/save budgets. Do not copy
   Paper or Mojang implementation code.

## Target pipeline

```text
ticket/select -> load/generate -> light -> encode -> compress -> send
```

- `ticket/select`: connection-owned view subscription chooses desired
  chunks in spiral order and marks stale requests when the view changes.
- `load/generate`: IO worker reads existing Anvil data; CPU worker generates
  missing chunks; both return owned chunk snapshots or handles that do not
  hold the world lock during downstream work.
- `light`: CPU worker computes light using existing `mc-world` logic and
  updates only the connection cache once the chunk is accepted for send.
- `encode`: CPU worker builds `LevelChunkWithLight` payloads from immutable
  chunk/light data.
- `compress`: CPU worker applies the negotiated M11 compression policy.
- `send`: Play task drains prepared outputs in allowed order and writes to
  the socket under send budgets.

## Config surface

- `chunk_send_rate` - max chunks or bytes sent per player over time.
- `chunk_load_rate` - storage load pressure budget.
- `chunk_generate_rate` - generated-chunk pressure budget.
- `chunk_prepare_budget_ms` - cooperative fallback / per-turn scheduling
  budget for work that still runs on the connection task.
- `chunk_prepare_batch_size` - max prepared outputs accepted per turn.
- `chunk_io_threads` - bounded region IO worker count.
- `chunk_worker_threads` - bounded CPU worker count for generation,
  lighting, encode, and compression.
- `chunk_result_queue_size` - per-connection or global cap on prepared
  outputs waiting to be sent.
- `region_cache_size` - Anvil region cache capacity.
- `compression_level` - frame compression level if the current API exposes
  it cleanly without changing M11 protocol boundaries.

Defaults should reproduce M12 behaviour on a single player within timing
noise while allowing the CPU-heavy phases to use more than one core.

## Sub-milestone decomposition

### M13.a - Plan

Add this milestone document only. Confirm the branch starts from `main` at
tag `m12`, then commit the plan before any code.

### M13.b - Pipeline model and config

Introduce config and internal types for chunk pipeline policy: worker
counts, queue caps, per-stage budgets, and region/cache/compression knobs.
This slice may keep execution synchronous, but the types should name the
future ownership explicitly: request, priority, generation/load source,
prepared output, cancellation token or generation, and stop reason.

Acceptance for this slice is structural: no behaviour change, defaults
match M12, and config parsing has tests.

### M13.c - Chunk scheduler and cancellation

Extract a minimal scheduler from the current connection-owned stream state.
It should accept a player's desired view, enqueue chunks by spiral priority,
track in-flight requests, deduplicate duplicate chunk requests, and cancel
or ignore stale results when the view moves or the connection drops.

This is not a global ticket engine yet. It is the smallest scheduler that
prevents the Play task from owning every heavy step directly.

### M13.d - Bounded IO and CPU workers

Add bounded worker pools and route chunk preparation through them:

- IO pool for region reads and eventual write-side follow-up seams;
- CPU pool for generated chunks, light compute, packet encode, and
  compression;
- bounded channels so prepared chunks cannot become an unbounded memory
  spike;
- shutdown/cancellation behaviour that drops stale connection work cheaply.

The first implementation may keep stage grouping coarse if that reduces
risk, but IO and CPU work must not share one unbounded executor.

### M13.e - Async Play integration and ordering

Teach the Play loop to submit chunk requests, poll prepared outputs, and
send them in client-safe order while still handling inbound frames,
keepalive, disconnect, and shutdown. Near chunks remain prioritized;
distant chunks stream as worker results arrive but must not overtake the
ordering rules needed for vanilla client stability.

The M12 block-edit responsiveness test should still pass while the worker
pipeline is actively preparing chunks.

### M13.f - Budgets, backpressure, and metrics

Apply config-backed policy to the async pipeline:

- per-player send budget;
- load/generate budget or pressure counters;
- prepared-result queue cap;
- worker queue depth metrics;
- yielded turns and stop reasons;
- cache hit/miss counters where cheap.

Logs should show active policy and why the stream slowed down without
printing one line per packet.

### M13.g - Region cache and compression knobs

Wire `region_cache_size` through `WorldStorage` without changing default
capacity or persistence semantics. Expose `compression_level` only if the
current compression API supports it as a small, safe change; otherwise
document it as queued instead of shipping a fake knob.

### M13.h - Tests, docs, and manual gate

Add harness coverage for the real async properties:

- default full spawn-window coverage still observes 441 chunks;
- low queue/budget config increases backpressure or yielded turns;
- block edits are handled while chunk workers are still active;
- moving/disconnecting during streaming does not send stale chunks or leak
  unfinished tasks;
- logs include worker counts, queue caps, active budgets, and stop reasons.

Close out with the standard gates:

```sh
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

Then prepare the debug server manual gate on a deleted fresh
`.analysis/test-world` and say `готов, подключайся` for PrismLauncher
26.1.2.

## Acceptance criteria

1. Chunk load/generate/light/encode/compress work no longer runs wholly on
   the Play socket task for the normal stream path.
2. IO and CPU stages use separate bounded worker pools or equivalent
   bounded executors.
3. Per-player chunk requests are prioritized by spiral distance, deduped,
   and cancellable/ignorable when stale.
4. Prepared-result queues are bounded so multicore throughput cannot create
   unbounded memory growth.
5. Default config preserves M12 client-visible behaviour and fresh-world
   timing within noise or improves it.
6. Lower budgets or queue caps visibly apply backpressure without breaking
   keepalive or inbound responsiveness.
7. Full spawn-window harness coverage still observes 441 emitted chunks at
   view distance 10.
8. Block-edit responsiveness still passes during active chunk streaming.
9. Stream logs show worker counts, queue caps, active budgets, queue depth
   or yielded-turn data, and a meaningful stop reason.
10. `region_cache_size` reaches `WorldStorage` without changing default
    cache capacity.
11. `compression_level` is either safely wired or explicitly deferred; no
    fake/inert tuning knob ships.
12. `cargo test --workspace` is green.
13. `cargo clippy --workspace --all-targets -- -D warnings` is clean.
14. `cargo fmt --all -- --check` is clean.
15. Manual PrismLauncher 26.1.2 gate on a fresh generated world remains
    usable.

## Out of scope

- Folia-style region ownership for all game logic.
- Entity scheduler, AI, redstone, fluids, or block physics.
- Real tick-window edit batching and multi-edit relight.
- Disk-persistent light arrays.
- Async/background dirty chunk flush implementation beyond the IO-pool seam.
- Vanilla algorithm ports or copied Paper/Mojang implementation code.
- Multi-server/shard architecture or plugin ABI commitments.

## Pitfalls

- **World lock stalls.** Moving work to workers does not help if workers hold
  a global world lock through light/encode/compress stages.
- **Unbounded queues.** Multicore preparation can make latency worse by
  filling memory with stale encoded chunks unless queues are capped and
  cancellable.
- **Ordering regressions.** Worker completion order is not spiral order;
  the Play task must preserve client-safe send priority.
- **Light cache coherence.** Connection light cache updates should occur for
  accepted emitted chunks, not for stale worker results.
- **Cancellation races.** A stale result arriving after movement or
  disconnect must be dropped without touching the socket or cache.
- **Fake parallelism.** `spawn_blocking` around a monolithic function is not
  enough if all heavy work serializes on one mutex or one queue.
- **Config drift.** Defaults must not silently change the M12 manual-gate
  behaviour.
- **Log spam.** Pipeline metrics should summarize stage pressure and stop
  reasons without per-packet noise.

## Open questions

- Should the first scheduler be per-connection with shared workers, or a
  small global scheduler that can deduplicate chunks across players?
  Default: shared workers with the smallest scheduler that can dedupe
  in-flight chunk coordinates safely.
- Should pipeline stages be separate queues from day one, or should M13.d
  use one CPU job for generate/light/encode/compress and split later?
  Default: separate IO vs CPU now, split CPU sub-stages only where it stays
  small.
- Should send ordering wait for missing nearer chunks or allow farther
  ready chunks after a bounded delay? Default: keep strict near priority for
  spawn and first rings, then allow progressive distant sends within spiral
  priority windows.
- What queue cap is safe for one player at view distance 10 without hiding
  memory pressure? Default: cap prepared outputs well below the full 441
  window and let backpressure prove itself in tests.
- Is compression-level tuning cheap enough for M13, or should compression
  stay policy-only until the worker compression stage is stable?
