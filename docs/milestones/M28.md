# M28 - Containers and inventory parity

**Status:** planned on `dev/M28-containers-inventory-parity` from `main` at local
tag `m27`; implementation is pending owner review of this plan.
**Owning crates:** `mc-protocol` for verified click/resync packet shapes,
`mc-data` for stack and durability facts, `mc-world` for chest block-entity
storage and Anvil round-trip, `mc-net` for server-authoritative inventory and
container behavior, and `mc-test-harness` for wire-level survival coverage.

## Goal

Harden the player inventory and common container loop toward vanilla survival
behavior. M28 focuses on server-authoritative click handling, data-backed stack
rules, persistent chest storage, and concurrent viewer synchronization.

M28 is not full container parity. Barrels, hoppers, brewing stands, anvils,
smithing, enchanting, shulkers, villagers/trading, and broad recipe-book UI
behavior remain future work unless a narrow dependency is needed to keep chest or
inventory behavior correct.

## Strategy

1. Verify packet and storage facts before widening behavior. Click modes,
   buttons, resync packets, screen ids, and chest NBT shape must come from the
   local 26.1.2 oracles, not memory.
2. Keep the server authoritative. Client changed slots and carried stack are
   validation hints only; Solaris state decides every mutation and resync.
3. Replace remaining inventory stack heuristics with `mc-data` item facts where
   the M25 component loader already exposes max stack size and durability.
4. Expand click behavior in narrow, testable slices. Unsupported or impossible
   clicks should reject cleanly and send a complete authoritative resync.
5. Make chest contents world-owned. Container views should be projections over
   block-entity state so persistence, concurrent viewers, and later double-chest
   support share the same backing model.

## Risks / Pitfalls

- Container click behavior is dupe-prone. Reject unsupported modes with complete
  authoritative resync until each mode has a focused test.
- Client changed slots may look convenient but are not truth. Treat them as drift
  diagnostics, not mutation input.
- Chest ownership can split between connection-local state and world storage if
  the model is not explicit. M28 should make world/chunk state authoritative from
  the first chest slice.
- Double chests have orientation and pairing edge cases. If local oracles do not
  answer them quickly, ship single chest plus a documented follow-up.
- Stack limits and durability must not regress M25's data seam by adding new
  private item-name arrays in `mc-net`.
- Quick-craft and pickup-all can balloon into UI parity. Implement the narrow
  survival-visible path or reject cleanly with verified resync.

## Oracle Notes

M28.b checked the local 26.1.2 protocol dump and permitted metadata before click
implementation work:

- `ServerboundContainerClick` is game serverbound id `0x12`; field order is
  `containerId`, `stateId`, `slotNum`, `buttonNum`, `containerInput`,
  `changedSlots`, `carriedItem`. `containerId` and `stateId` are VarInts,
  `slotNum` is short, `buttonNum` is byte, and changed slots are capped at 128
  hashed-stack entries.
- `ContainerInput` ids are metadata-pinned as `0=PICKUP`, `1=QUICK_MOVE`,
  `2=SWAP`, `3=CLONE`, `4=THROW`, `5=QUICK_CRAFT`, and `6=PICKUP_ALL`.
- Quick-craft uses `button = header | (type << 2)`, with headers start `0`, add
  `1`, end `2`; type `2` is clone-only and therefore not valid for normal
  survival handling. Outside slot is `-999`.
- Relevant resync packets are already present in `mc-protocol`: `ContainerClose`
  id `0x11`, `ContainerSetContent` id `0x12`, `ContainerSetData` id `0x13`,
  `ContainerSetSlot` id `0x14`, `OpenScreen` id `0x3b`, `SetCursorItem` id
  `0x60`, and `SetPlayerInventory` id `0x6c`.
- Menu registry ids needed by M28: `generic_9x3 = 2`, `crafting = 12`, and
  `furnace = 14`.

M28.c routes normal inventory/container stack limits through the M25
`ItemFactsTable` when component facts are available. The previous `mc-net`
item-name checks remain only as a fallback for missing component reports.
