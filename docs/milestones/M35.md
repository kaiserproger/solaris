# M35 - Commands and admin surface

**Status:** plan on `dev/M35-commands-admin` from `main` at local tag `m34`
(`6fdcdd7`, `feat: M34 protocol edge-case hardening`).
**Owning crates:** `mc-protocol` for command/chat packet codecs and
oracle-pinned layouts, `mc-net` for player command handling, permissions,
feedback, save/stop hooks, and state mutations, `mc-server` for console/admin
entry points and config wiring, and `mc-test-harness` for wire-level command
coverage.

## Goal

Add the minimum vanilla-style command and admin surface needed to operate,
debug, and save a replacement server.

M35 should not pretend to implement the full vanilla command tree. A small,
correct, observable subset is better: verified command tree sync for supported
commands, one dispatcher shared by player and console commands, server-side
permission checks, real state mutations for backed systems, and operational
`save-all` / `stop` paths that use existing persistence and shutdown hooks.

## Current Foundation

- M34 hardened common protocol edge traffic, including command suggestion
  requests and empty suggestion responses.
- Login, Configuration, Play, chunk streaming, survival inventory, entities,
  combat/XP, and persistence are mature enough that admin commands now need to
  mutate authoritative state instead of client-only illusions.
- `mc-net` owns play-session state and already has paths for sending player
  state, inventory, entity, world, feedback-adjacent, and disconnect packets.
- `mc-server` owns config loading and process lifecycle, but does not yet expose
  a real console command loop or shared admin dispatcher.
- Existing save/persistence hooks should be reused by operational commands;
  M35 should not add a parallel save path.

## Strategy

1. Verify protocol layouts first. Command tree sync, chat command submission,
   command suggestions, and command feedback/result packets must be pinned to
   `.analysis/protocol-dump.txt`, `tools/dump-vanilla-protocol.sh`, `javap`, or
   `wire-probe` captures before codecs or packet ids are added.
2. Build one narrow dispatcher model shared by player commands and console
   commands. Parsing should be explicit and testable rather than spread across
   play-session packet handlers.
3. Add a small permission model before mutating commands. Unprivileged player
   commands must fail server-side even if a client guesses syntax.
4. Implement commands only where Solaris has authoritative backing systems.
   Prefer fewer commands with real effects over broad no-op compatibility.
5. Keep admin UX terse and observable through structured logs, command feedback,
   and tests.

### M35.c - Dispatcher foundation

Add a server-side parser and dispatcher that can execute the same command model
from player sessions and server console/admin input.

Acceptance:

- A shared command request type represents source, raw input, parsed command,
  arguments, and permission context.
- Parser behavior is deterministic for slash-prefixed player input, console
  input, quoting where scoped, unknown commands, missing arguments, and trailing
  garbage.
- Dispatcher returns structured success/error feedback without directly writing
  packets or logs from command implementations.
- Player command handling and console command handling call the same dispatcher.
- Unit tests cover parse success, parse errors, unknown commands, and source
  differences.

### M35.d - Permissions and op model

Load a minimal operator/permission configuration and enforce it for every
privileged command.

Acceptance:

- Server config can define local operators or permission levels without
  committing machine-local secrets.
- Console source has explicit administrative permission.
- Player source permissions are looked up from stable player identity available
  to Solaris, with documented behavior for offline/dev identities.
- Unauthorized commands fail before any state mutation and send clear feedback.
- Tests cover allowed console execution, allowed player execution, rejected
  player execution, and unknown/offline identity behavior.

### M35.e - Command tree sync and suggestions

Send vanilla clients a usable command tree for implemented commands and provide
bounded suggestions for that subset.

Acceptance:

- Command tree sent on Play entry contains only commands Solaris can parse and
  execute.
- Command syntax advertised to clients matches dispatcher parsing.
- Suggestions are bounded, deterministic, permission-aware where relevant, and
  safe for partial input.
- A player without permission does not receive misleading privileged completions
  where Solaris can cheaply avoid them.
- Wire/unit tests cover command tree encoding and representative suggestion
  responses.

### M35.f - Core state commands

Implement a minimal state-changing command subset where backing systems already
exist.

Acceptance:

- `/gamemode` changes authoritative player game mode and synchronizes affected
  client state.
- `/tp` updates authoritative player position through existing teleport/movement
  synchronization paths.
- `/give` inserts real item stacks through existing inventory semantics and
  rejects invalid or overflowing requests.
- `/summon` creates server-owned entities only for supported entity types and
  rejects unsupported names clearly.
- `/kill` routes through existing damage/death/removal paths where available.
- `/time` mutates authoritative world time only if the current world state has a
  real time source; otherwise the command is deferred and documented.
- `/weather` mutates authoritative weather only if a backed weather state exists;
  otherwise the command is deferred and documented.
- Tests cover successful mutation and rejected inputs for every implemented
  command.

### M35.g - Operational commands

Wire operational admin commands to real persistence and shutdown paths.

Acceptance:

- `/save-all` flushes existing player/world/entity persistence paths and reports
  success or failure without blocking the server indefinitely.
- `/stop` initiates graceful server shutdown through the existing process/runtime
  shutdown path.
- Console and permitted players can execute operational commands through the same
  dispatcher.
- Errors are logged and surfaced through command feedback.
- Tests cover successful save request routing, rejected unauthorized requests,
  and shutdown request signaling without terminating the test process.

### M35.h - Command feedback and observability

Make command outcomes visible to command sources and useful in logs.

Acceptance:

- Successful commands send verified feedback/system messages to player sources.
- Failed commands send terse, actionable errors without exposing local paths or
  secrets.
- Console/admin executions log source, command name, outcome, and relevant target
  identity.
- Feedback for state-changing commands is emitted after mutation succeeds, not
  before.
- Tests cover player feedback, console feedback/log result records, and failure
  messages.

## Risks / Pitfalls

- Command protocol is dense and version-sensitive. Packet ids, node flags,
  parser identifiers, suggestion providers, and feedback packet layouts must come
  from local oracles, not memory.
- A fake broad command tree is worse than no tree. Advertise only commands that
  map to real dispatcher behavior.
- Permission mistakes are security bugs. Parse and permission-check before any
  mutation, and test rejected paths as first-class behavior.
- Some desired commands may not yet have backing systems. Defer `/time` or
  `/weather` rather than implementing client-only illusions.
- Save and stop commands can deadlock or terminate tests if wired carelessly.
  Route through existing bounded hooks and use test seams for shutdown signaling.
- Console input must not become a second command language. Keep console and
  player execution on one dispatcher.

## M35.b / M35.c / M35.e / M35.f Initial Command Surface Notes

Local oracle sources used for this slice:

```text
.analysis/protocol-dump.txt
.analysis/decompiled/server-26.1.2/net/minecraft/network/protocol/game/GameProtocols.java
.analysis/decompiled/server-26.1.2/net/minecraft/network/protocol/game/ClientboundCommandsPacket.java
.analysis/decompiled/server-26.1.2/net/minecraft/network/protocol/game/ClientboundSystemChatPacket.java
.analysis/decompiled/server-26.1.2/net/minecraft/network/protocol/game/ClientboundSetTimePacket.java
.analysis/decompiled/server-26.1.2/net/minecraft/commands/synchronization/ArgumentTypeInfos.java
.analysis/decompiled/server-26.1.2/net/minecraft/commands/synchronization/brigadier/StringArgumentSerializer.java
```

Verified packet/layout facts applied in `mc-protocol`:

- Play `CLIENTBOUND_COMMANDS` is id `0x10`; body is node list then root index.
- Command node layout is flags byte, VarInt child array, optional redirect,
  then root/literal/argument payload selected by `flags & 3`.
- `brigadier:string` is command argument type registry id `5`; string kind is
  a VarInt enum with `greedyString` ordinal `2`.
- Play `CLIENTBOUND_SYSTEM_CHAT` is id `0x79`; body is trusted text `Component`
  NBT followed by boolean `overlay`.
- Existing M34 facts for `SERVERBOUND_CHAT_COMMAND` (`0x07`) and command
  suggestions (`0x0F`) remain in use.

Implemented subset:

- Solaris sends a small command tree on Play entry for `/gamemode`, `/give`,
  `/kill`, `/save-all`, `/stop`, `/summon`, `/time`, `/tp`, and the existing
  `/debug ...` survival helpers.
- Player and console command execution share the same parser/dispatcher model.
  Console-only state commands that need a player source are rejected in logs;
  operational commands execute from both sources.
- Server config now exposes `[admin] operators = [...]` and
  `allow_local_dev_operators`. Operators may be player names or UUID strings.
  The local-dev fallback keeps fresh offline dev servers usable when the list is
  empty; configured operator lists reject non-matching players.
- Command suggestions are bounded and permission-aware for root commands and
  `/gamemode` modes.
- `/gamemode` uses existing game-mode event and abilities sync.
- `/give` resolves real item ids, merges into the authoritative inventory, and
  rejects unknown items or insufficient inventory space before mutation.
- `/tp` updates authoritative player pose, sends `SynchronizePlayerPosition`,
  updates visibility, and replans chunk streaming when the chunk center changes.
- `/summon` creates server-owned entities through `SessionRegistry` using the
  entity-type registry and existing visibility/spawn packet path.
- `/kill` routes through survival death state and inventory-drop handling.
- `/time set <ticks|day|noon|night|midnight>` mutates `SessionRegistry` world
  time and sends verified `ClientboundSetTime` (`0x71`) with an empty clock map
  to the command source. Entity/world metadata persistence then observes the new
  authoritative time.
- `/save-all` uses the existing shared persistence path for players, entities,
  world metadata, and dirty chunks.
- `/stop` runs the same save-all path and then signals the network listener to
  stop cleanly. The binary's Ctrl-C path remains intact.
- Player-visible command success and failure feedback uses `ClientboundSystemChat`
  with minimal text-component NBT.

Deferred from this slice:

- `/weather`, because Solaris still has no authoritative backed weather state.
- Rich Brigadier parser coverage, selectors, command blocks, functions, and
  plugin/API command registration.
- Broadcasting `/time` updates to all loaded players; the source receives the
  verified packet now, while world metadata stores the authoritative value.

Additional stabilization during closeout:

- `movement_across_chunk_boundary_replans_view_subscription` now waits until the

  the expected `ForgetLevelChunk(0, 0)` deterministic instead of racing the

  through the verified command surface instead of depending on opportunistic
  natural hostile herd timing. The test still exercises server-owned zombie
  combat, damage, loot, and pickup paths.

Remaining M35 gaps / follow-ups:

- `/weather` is still deferred because there is no authoritative weather state.
- `/time` updates the command source and persisted world time; broadcasting time
  changes to all loaded players is a future polish item.
- Console commands share parsing and operational execution, but player-scoped
  commands still require an online player source.
- The harness still has raw stream consumers that can accidentally drain frames
  needed by later assertions. M35 fixed the two observed races, but a future
  harness helper should buffer unmatched frames by packet id/entity id.
- M39 must carry a server-wide lock mitigation pass. `WorldStorage` is still
  globally mutexed, and other hot play/session/storage paths need the same
  audit: keep critical sections short, move blocking work out of shared locks,
  prefer queues/snapshots/actors where practical, and make the server as close
  to lock-free as the design allows.
