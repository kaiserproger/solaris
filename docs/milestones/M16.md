# M16 - Player presence and visibility

**Status:** code complete in the working tree on `dev/M16-player-presence`, cut
from `main` at tag `m15`. Automated gates are green; manual two-client gate
passed.
**Estimate:** large milestone, 25-45 h. This slice makes connected players
visible to each other as player entities when their views overlap, without adding
mobs, combat, AI, plugins, or a full ECS.
**Owning crates:** `mc-protocol` for verified player-info/entity packets,
`mc-net` for Play-session identity, visibility routing, and movement broadcasts,
and `mc-test-harness` for two-client wire coverage.

## Goal

After M16, two vanilla 26.1.2 clients connected to Solaris should be able to see
each other when their views overlap. Each client should receive the verified
player-info and entity packets needed to spawn, move, rotate, and remove nearby
connected players.

This milestone is intentionally narrow: connected players only. It should reuse
the M15 session registry, outbound command queues, and chunk subscription state
instead of introducing a general entity system.

## Strategy

1. **Oracle first.** Every new player-info or entity packet ID and field layout
   must be verified from `.analysis/protocol-dump.txt`, `javap`, and/or
   `wire-probe` before code or tests pin bytes.
2. **Reuse session ownership.** Each Play task still owns its socket writer,
   compression state, and outbound queue. Visibility decisions may be shared;
   writes must remain connection-owned.
3. **Add only player entity identity.** Extend session state with a stable runtime
   entity id and public pose/profile snapshot. Do not build a general ECS.
4. **Drive visibility from loaded views.** A player is visible to an observer when
   the observed player's position is inside or near chunks loaded for the
   observer. Movement and chunk lifecycle should converge on the same visibility
   graph.
5. **Keep ordering explicit.** Spawn should send the required player-info/entity
   packets before movement updates. Despawn/removal must be sent before stale
   queued updates can resurrect a disconnected or out-of-range player.
6. **Use bounded routing.** Cross-player spawn, despawn, and movement updates go
   through recipient outbound commands. Do not hold registry locks across awaits.
7. **Test real packet flow.** Harness tests should use two real clients and packet
   decoders, not manufactured packet facts.

## Target flow

```text
connection enters Play -> register session with entity id/profile/pose
  -> acquire chunks -> compute existing visible players -> queue spawn commands

movement -> update pose -> replan chunks if needed -> recompute visibility
  -> queue spawn/despawn/update commands for affected observers

disconnect -> unregister session -> queue removal for current observers
  -> release chunk tickets -> drop stale outbound commands
```

### M16.b - Player-visible protocol oracle

- Tests pin bytes only after the oracle pins the layout.
- Optional metadata/skin fields are omitted unless the oracle or client behavior

### M16.c - Session entity identity

Extend the Play session registry with a stable runtime entity id per connection
and a public snapshot containing UUID, game profile name, current pose, yaw,
pitch, and chunk position.

Important constraints:

- The local player keeps its existing Play login and movement handling.
- Runtime entity ids must be unique among active players and stable for the
  lifetime of a session.
- Offline-mode UUID/profile data should keep using the existing login source.

### M16.d - Visibility graph

Track which player entities each observer currently sees. Reuse M15 chunk-loaded
or subscription state to decide visibility instead of adding a separate spatial
index for this milestone.

Acceptance for this slice:

- Joining players see already-present nearby players after their initial view is
  ready.
- Existing nearby observers see newly joined players.
- Moving across visibility boundaries produces deterministic enter/leave diffs.

### M16.e - Spawn and despawn lifecycle

Route verified player-info/entity spawn and remove packets through outbound
commands owned by each recipient Play task.

This slice must handle disconnect and rapid movement. A despawned player must
not be resurrected by a queued movement update or a stale visibility result.

### M16.f - Movement and rotation broadcast

Broadcast verified movement, teleport, rotation, and head-rotation packets for a
moving player to current observers. Preserve the mover's local chunk replan and
do not change an observer's chunk center because another player moved.

   `.serena/` changes are not included in M16 commits.

   incremental-relight harness tests remain green.

   damage, redstone, fluids, plugin API, or full ECS.

## Harness plan

- Two clients connect near each other. Each receives the verified player-info and
  entity spawn packets for the other connected player.
- Client A moves or rotates while client B stays still. B receives the verified
  update packets for A and does not receive a center-chunk update caused by A.
- Client A moves out of B's visibility range or disconnects. B receives verified
  removal/despawn packets and no later stale update for A.
- The existing two-client block-edit test still confirms actor ack plus observer
  block/light delta while both players are visible.

## Out of scope

- Mobs, AI, combat, damage, survival mining timing, tool damage.
- Redstone, fluids, block physics.
- Plugin API, scripting, event bus, or public extension hooks.
- Full ECS, Folia-style region ownership, or a generalized entity tracker beyond
  connected-player visibility.
- Skin/session-server integration beyond minimal verified profile fields required
  by the vanilla client.
- Vanilla algorithm ports.

## Pitfalls

- **Guessed protocol.** Player-info/entity packets are version-sensitive and must
  be oracle-pinned before Rust packet types or byte tests land.
- **Bad packet ordering.** Movement before spawn, or removal before required
  player-info state, can produce invisible or stale clients.
- **Writer ownership leaks.** Cross-player visibility must not write directly to
  another connection's socket.
- **Locking across awaits.** Visibility snapshots should be computed under short
  locks and then routed through outbound queues.
- **Stale visibility.** Disconnect, rapid movement, and queued updates must not
  leave ghost players client-side.
- **Scope creep.** This is not the start of mobs, combat, survival timing, or a
  plugin/entity framework.

## Open questions

- What exact minimal packet sequence does a 26.1.2 vanilla client require to show
  another player?
  Default: verify from `.analysis/protocol-dump.txt` and `javap`; use
  `wire-probe` against vanilla if static metadata is insufficient.
- Should visibility be based on observer loaded chunks or desired chunks?
  Default: loaded chunks, so entity spawn does not precede the world area the
  observer can render.
- Are relative movement packets enough for normal walking, or should M16 always
  use teleport for simplicity?
  Default: use the smallest verified packet set that keeps tests and client
  behavior correct; teleport-only is acceptable if it is simpler and stable.
- How long should player-info remain after entity removal?
  Default: follow the verified vanilla/minimal sequence; remove promptly unless
  the client requires a grace period.

  - `CLIENTBOUND_ADD_ENTITY` = game-CB index 1, wire id `0x01`; body is VarInt
    entity id, UUID, registry entity type id, xyz doubles, `Vec3.LP_STREAM_CODEC`,
    packed x/y/head rotations, VarInt data.
  - `CLIENTBOUND_ENTITY_POSITION_SYNC` = game-CB index 35, wire id `0x23`; body

    yRot float, xRot float), onGround bool.

    a VarInt-counted UUID list.

    fixed 8-bit action EnumSet plus VarInt-counted entries. M16 uses

    hat actions; profile properties and chat session are empty.
  - `CLIENTBOUND_REMOVE_ENTITIES` = game-CB index 77, wire id `0x4D`; body is a
    VarInt-counted entity-id list.
  - `CLIENTBOUND_ROTATE_HEAD` = game-CB index 83, wire id `0x53`; body is VarInt
