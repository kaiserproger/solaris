# M1 — Network + handshake

**Status:** code-complete on `dev/M1-network-handshake`. All packet
IDs and field layouts in scope are cross-validated against two
independent sources: a live vanilla 26.1.2 server (via `wire-probe`)
and the unobfuscated jar's `*Protocols.class` registration tables
(via `javap`, per ADR 0002).
**Estimate:** 60-100h (PROJECT_SPEC §9 Phase 1).
**Owning crates:** `mc-protocol`, `mc-net`, `mc-data`, `mc-nbt`, with
hooks from `mc-server`.

## Goal

A binary that, when run, opens a TCP listener on the configured address and
walks a vanilla 26.1.x Java client through `Handshake → Status` (server list
ping works) and `Handshake → Login → Configuration → Play` (the client
reaches the Play state without a protocol-level disconnect). No world data,
no entities, no real gameplay — that is M2 and M3.

This is the foundation everything else stands on, so we invest in test
coverage and a clean type layout here even though it visibly produces
nothing.

## Strategy decision: roll-our-own protocol

Confirmed with the project owner: we do not depend on `valence-protocol`,
`azalea-protocol`, or any other Minecraft-specific upstream crate. The wire
format is small and stable enough that owning it is cheaper than living with
someone else's update schedule, and the protocol layer is too central to
delegate (per `docs/CLAUDE_CODE_PROMPTS.md` §4.1).

External *generic* crates we will pull in (already approved in
PROJECT_SPEC §2.4):

- `tokio` — async runtime, TCP
- `bytes` — `Buf`/`BufMut`/`BytesMut` for zero-copy buffer manipulation
- `flate2` — zlib compression (post-threshold packets)
- `aes` + `cfb-mode` — AES-128 / CFB8 stream encryption
- `thiserror` — error enums
- `tracing` — structured logging
- (dev) `proptest` — round-trip property tests
- (M1.5+) `fastnbt` for the Network NBT codec — rolling our own NBT is not
  in scope for M1; we use the spec-approved fallback (§2.4)

## Reference sources (read-only oracles)

Per PROJECT_SPEC §8.1 we do **not** ship code derived from decompiled Mojang
sources or Mojmap-informed designs. Allowed inputs:

- `wiki.vg` / `minecraft.wiki` "Java Edition protocol" articles (public
  reverse-engineering documentation)
- The bundled vanilla 26.1.2 server in `.analysis/server.jar` is used only
  as a **runtime oracle** — we connect a real vanilla client to it under
  Docker (per M2.5 plan) and capture wire traffic. We do not read its
  classfiles for naming or structural inspiration.
- Wire captures from our own debug logging once the server is up.

## Sub-milestone decomposition

Implemented as small, individually committable chunks so the diff stays
reviewable:

### M1.a — codec primitives in `mc-protocol`

Just enough to encode/decode every Minecraft primitive type that any 26.1
packet uses. No packet structures yet, no network code yet.

Public surface (under `mc_protocol::codec`):

- `VarInt(i32)`, `VarLong(i64)` newtypes with `encode` / `decode`
- Free functions for primitives: `bool`, `u8/i8`, `u16/i16`, `i32`, `i64`,
  `f32`, `f64`, `uuid`, `string` (with max-length parameter)
- `Identifier` (validated `namespace:path`) — light wrapper around `String`
- A `Reader<'a>` / `Writer` pair built over `bytes::Buf` / `bytes::BufMut`
- Error enum `CodecError` covering: buffer underflow, varint overflow,
  invalid UTF-8, string too long, invalid identifier
- A `read_varint_partial(&[u8])` API the framing layer can call without
  needing to consume bytes on `NeedMore`

Tests: exhaustive unit tests for boundary varint values (0, 1, 127, 128,
i32::MAX, i32::MIN, all-the-way-negative), proptest round-trip for every
primitive, golden vectors taken from the wiki.vg "Data types" page.

### M1.b — packet framing in `mc-protocol`

- Length-prefixed framing: parse `VarInt length + payload` out of a
  `BytesMut` ring; emit the same on write
- Optional zlib compression layer once the per-connection threshold is set
- Optional AES-128/CFB8 cipher layer applied before the framer
- A `tokio_util::codec`-style `FrameCodec` is convenient but we can also
  hand-roll for full control — pick during implementation
- Tests: simulated split-buffer reads (one byte at a time), compression
  on / off / threshold-edge, encryption round-trip

### M1.c — connection state machine + Status

- `ConnectionState` enum: `Handshake | Status | Login | Configuration | Play`
- Per-connection async task: read frame → dispatch packet by `(state, id)`
- Handshake packet (serverbound `0x00`, intent VarInt → Status or Login)
- Status state: respond to status request with a JSON document built from
  `ServerConfig` and the running server version; pong with the client's
  payload
- Acceptance: a vanilla 26.1.x client shows the server in its multiplayer
  list with the configured MOTD; `mcstatus`-style external tools also
  succeed

### M1.d — Login state (offline mode only)

- Receive `Login Start (name, uuid)`
- Offline UUID: `UUID v3` of `"OfflinePlayer:" + name` per common
  community convention; we'll switch to Mojang auth only when Configuration
  works end to end
- Send `Login Success` immediately, no encryption, no compression
- Receive `Login Acknowledged` → transition to Configuration
- Encryption (`Encryption Request` / `Encryption Response` / AES setup) is
  scaffolded but feature-gated behind `"online-mode"` and left untested in
  M1; full online-mode is its own milestone
- Acceptance: client transitions out of the "Logging in…" screen

### M1.e — Configuration state (wire mechanics only)

Scope deliberately narrowed after the implementation pass on the
sub-milestone — the full set of vanilla 26.1 registries is too large to
hand-author and too entangled with Mojang's data to dump out of the
server jar without crossing the legal-posture line in §8.1.

In scope for M1.e:

- Send `Clientbound Known Packs` advertising `{minecraft, core, 26.1.2}`
  to tell the client "use your built-in pack for all builtin registries".
- Read `Serverbound Known Packs` and verify the response shape.
- Send `Finish Configuration`; read `Acknowledge Finish Configuration`.
- Skip everything else the client may send in Configuration state
  (`Client Information`, plugin messages, resource pack responses, …) —
  read the frame, log the ID, drop it.

Deferred to M1.g (or later, may need its own milestone):

- `Registry Data` packets with actual entry lists. A real vanilla 26.1
  client will refuse to enter Play without them; our integration tests
  use a hand-rolled driver that does not need them, so the wire layer
  passes here but client compatibility is not yet proven.
- `Clientbound Plugin Message` "minecraft:brand". Nice to have, not on
  the critical path.
- `Update Tags`, `Feature Flags`, `Custom Report Details`,
  `Server Links` — all clientbound configuration packets we never send.

### M1.f — Minimal Network NBT in `mc-nbt`

- Just enough of the NBT codec to emit the registries in M1.e
- We add `fastnbt` as a dependency and write our own thin Solaris-side
  wrappers; rolling NBT fully from scratch is out of scope for M1 and would
  bloat the milestone past its 100h estimate

### M1.g — Play state entry

- Send `Login (Play)` with a stub entity ID, gamemode survival, single
  fake dimension, 0/0 spawn, view distance from config
- Send `Set Default Spawn Position` and `Synchronize Player Position` so
  the vanilla client unblocks its loading screen
- KeepAlive loop (server-initiated every 15 s, kick on no-response in 30 s)
- Acceptance: vanilla 26.1.x client reaches the Play state, stays
  connected for ≥ 60 s, no protocol disconnect, no crash. World will be
  black (no chunks) — that is intentional, chunk data is M2.

### M1.h — Wire-up in `mc-server` + integration test

- `mc-net::Server::run(config)` API
- The `mc-server` binary now actually serves: it parses the config, builds
  the server, awaits Ctrl-C
- Integration test in `crates/mc-server/tests/connect.rs` that drives a
  raw TCP client through a handshake + status request and asserts the
  status JSON shape — does not require a real Minecraft client and
  therefore runs in CI

## Acceptance criteria for M1 as a whole — status

1. ✅ `cargo test --workspace` passes (117/117 as of M1.g.3); high
   coverage on `mc-protocol::codec`. The 95% target is unmeasured in
   CI but the module has 21 unit tests + 5 proptest cases.
2. ⏳ A vanilla 26.1.x client lists the server in its server browser
   with the configured MOTD. The wire format is implemented and our
   own raw-TCP integration test (`tests/status.rs`) verifies the JSON
   the server emits. Validating with a real Mojang client is a manual
   step — see "Wire compatibility — open question" below.
3. ⏳ A vanilla 26.1.x client connects to `localhost:25565` and
   reaches the Play state. Our integration tests cover the full
   `Handshake → Login → Configuration → Play` traversal end-to-end
   with a raw-TCP driver. Real-client validation pending — depends
   on Play state packet IDs being correct for protocol 775, which we
   have not yet wire-captured.
4. ⏳ The connection survives ≥ 60 s in Play with KeepAlives. The
   handler runs on the documented 15-s / 30-s vanilla timing. Unit
   tests confirm the keepalive loop alives and handles spurious
   echoes; the 60-s longevity test needs to be run manually.
5. ✅ `cargo clippy --workspace --all-targets -- -D warnings` is green.
6. ✅ No `unsafe` anywhere (enforced by `unsafe_code = "forbid"` at
   the workspace lints level).
7. ✅ No Mojang code or Mojmap-informed mappings in our repo. Mojang
   *data files* are now allowed as runtime input per
   [ADR 0001](../decisions/0001-vanilla-data-as-runtime-input.md) but
   live in `data/vanilla/` outside git.

## Wire compatibility — validated and outstanding

`crates/mc-test-harness/src/bin/wire_probe.rs` is a small bot built on
top of our own `mc-protocol`. It connects to a target server, walks
Handshake → Login → Configuration → Play, and dumps every clientbound
frame as `(id, body_len, hex)`. It runs against either a live vanilla
26.1.2 server (extracted from `.analysis/server.jar` and started with
Java 25) or our own Solaris binary. M1.g.4 used both.

Cross-validated against vanilla 26.1.2 (`javap` + wire-probe):

| Packet | Vanilla constant | Vanilla ID | Solaris ID | Status |
|---|---|---|---|---|
| StatusResponse / PongResponse / requests | (Status state)              | per docs | matches | ✅ |
| Set Compression                          | CLIENTBOUND_LOGIN_COMPRESSION| 0x03 | 0x03 | ✅ |
| LoginSuccess                             | CLIENTBOUND_LOGIN_FINISHED   | 0x02 | 0x02 | ✅ |
| LoginStart                               | SERVERBOUND_HELLO            | 0x00 | 0x00 | ✅ |
| LoginAcknowledged                        | SERVERBOUND_LOGIN_ACKNOWLEDGED| 0x03 | 0x03 | ✅ |
| ClientboundKnownPacks                    | CLIENTBOUND_SELECT_KNOWN_PACKS | 0x0E | 0x0E | ✅ |
| ServerboundKnownPacks                    | SERVERBOUND_SELECT_KNOWN_PACKS | 0x07 | 0x07 | ✅ |
| RegistryData                             | CLIENTBOUND_REGISTRY_DATA    | 0x07 | 0x07 | ✅ |
| FinishConfiguration                      | CLIENTBOUND_FINISH_CONFIGURATION | 0x03 | 0x03 | ✅ |
| AcknowledgeFinishConfiguration           | SERVERBOUND_FINISH_CONFIGURATION | 0x03 | 0x03 | ✅ |
| **LoginPlay**                            | CLIENTBOUND_LOGIN            | 0x31 | 0x31 | ✅ |
| **SynchronizePlayerPosition**            | CLIENTBOUND_PLAYER_POSITION  | 0x48 | 0x48 | ✅ |
| **GameEvent**                            | CLIENTBOUND_GAME_EVENT       | 0x26 | 0x26 | ✅ |
| **ClientboundKeepAlive**                 | CLIENTBOUND_KEEP_ALIVE       | 0x2C | 0x2C | ✅ fixed from 0x27 |
| **PlayDisconnect**                       | CLIENTBOUND_DISCONNECT       | 0x20 | 0x20 | ✅ fixed from 0x1D |
| **SetDefaultSpawnPosition**              | CLIENTBOUND_SET_DEFAULT_SPAWN_POSITION | 0x61 | 0x61 | ✅ fixed from 0x5C |
| **ServerboundKeepAlive**                 | SERVERBOUND_KEEP_ALIVE       | 0x1C | 0x1C | ✅ fixed from 0x1A |
| **ConfirmTeleportation**                 | SERVERBOUND_ACCEPT_TELEPORTATION | 0x00 | 0x00 | ✅ |

Solaris' spawn-burst body for `GameEvent` is **bit-identical** to
vanilla. `SynchronizePlayerPosition` is the same 61-byte layout.
`LoginPlay`'s 11 fields (per `javap -p` of `ClientboundLoginPacket`
+ the inner `CommonPlayerSpawnInfo` record) all map 1-to-1 onto our
struct, including the `Optional<GlobalPos> lastDeathLocation` ↔
`Option<(Identifier, i64)>` mapping. Body sizes differ only because
we advertise 4 dimensions to vanilla's 3.

`SetDefaultSpawnPosition`'s wire layout was wrong in M1.g.3 (we had
`(i64 position, f32 angle)`; vanilla's `RespawnData` record is
`(GlobalPos{dim:Identifier, pos:i64}, f32 yaw, f32 pitch)`) — fixed
in M1.g.5 and round-trip tested. The packet is still NOT included
in the M1.g.3 spawn burst because vanilla's own server doesn't emit
it during initial spawn either; we just keep the type ready for
future use (respawn, world change).

How to repeat the validation:

```sh
# 1. Stand up the vanilla server in Java 25 (see .analysis/extracted/
#    for the bundled jar). Use a non-default port to avoid clashes.
java -Xmx1G -jar server.jar --nogui

# 2. Stand up Solaris on a different port (config: `data.vanilla_dir`
#    points at data/vanilla/).
cargo run --bin mc-server -- --config solaris.toml

# 3. Probe each:
cargo run -p mc-test-harness --bin wire-probe -- \
    --addr 127.0.0.1:25566 --play-seconds 60   # vanilla
cargo run -p mc-test-harness --bin wire-probe -- \
    --addr 127.0.0.1:25567 --play-seconds 60   # Solaris

# 4. Diff the two dumps. Any (id, body_len) pair we emit that vanilla
#    does not, or vice versa, is a place to investigate.
```

## Out of scope (recorded so it does not creep)

- Online-mode authentication against Mojang's session server (own milestone
  later; the spec puts auth concerns in M22 anti-cheat work)
- Encryption transport beyond a code stub
- World data, chunk streaming, entities, inventories — all M2+
- Custom protocol extension (`solaris:*` namespaces) — M10
- Per-player permissions, ops, commands — later
- Server list favicon — trivial but not load-bearing for acceptance

## Open questions — answered along the way

- ✅ Exact 26.1.x protocol version: **775** (26.1.2). Recorded as
  `mc_protocol::PROTOCOL_VERSION`, sourced from the bundled
  `version.json`.
- ✅ Framing implementation: rolled our own pure-logic
  `try_decode_frame` / `encode_frame` over `bytes::BytesMut`. Tokio
  io wrappers live in `mc-net::connection`. Decision: tokio_util's
  `Framed` was rejected because the bind/encryption layering needs
  full control over the buffer state.
- ⏳ `Identifier` string interning — still deferred to M9, no
  pressure to do it earlier.
