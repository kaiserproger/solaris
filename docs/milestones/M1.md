# M1 — Network + handshake

**Status:** in progress on `dev/M1-network-handshake`.
**Estimate:** 60-100h (PROJECT_SPEC §9 Phase 1).
**Owning crates:** `mc-protocol`, `mc-net`, with light hooks from `mc-server`.

## Goal

A binary that, when run, opens a TCP listener on the configured address and
walks a vanilla 26.1.x Java client through `Handshake → Status` (server list
ping works) and `Handshake → Login → Configuration → Play` (the client
reaches the Play state without a protocol-level disconnect). No world data,
no entities, no real gameplay — that is M2 and M3.

This is the foundation everything else stands on, so we invest in test
coverage and a clean type layout here even though it visibly produces
nothing.

## Strategy decision: roll-our-own protocol

Confirmed with the project owner: we do not depend on `valence-protocol`,
`azalea-protocol`, or any other Minecraft-specific upstream crate. The wire
format is small and stable enough that owning it is cheaper than living with
someone else's update schedule, and the protocol layer is too central to
delegate (per `docs/CLAUDE_CODE_PROMPTS.md` §4.1).

External *generic* crates we will pull in (already approved in
PROJECT_SPEC §2.4):

- `tokio` — async runtime, TCP
- `bytes` — `Buf`/`BufMut`/`BytesMut` for zero-copy buffer manipulation
- `flate2` — zlib compression (post-threshold packets)
- `aes` + `cfb-mode` — AES-128 / CFB8 stream encryption
- `thiserror` — error enums
- `tracing` — structured logging
- (dev) `proptest` — round-trip property tests
- (M1.5+) `fastnbt` for the Network NBT codec — rolling our own NBT is not
  in scope for M1; we use the spec-approved fallback (§2.4)

## Reference sources (read-only oracles)

Per PROJECT_SPEC §8.1 we do **not** ship code derived from decompiled Mojang
sources or Mojmap-informed designs. Allowed inputs:

- `wiki.vg` / `minecraft.wiki` "Java Edition protocol" articles (public
  reverse-engineering documentation)
- The bundled vanilla 26.1.2 server in `.analysis/server.jar` is used only
  as a **runtime oracle** — we connect a real vanilla client to it under
  Docker (per M2.5 plan) and capture wire traffic. We do not read its
  classfiles for naming or structural inspiration.
- Wire captures from our own debug logging once the server is up.

## Sub-milestone decomposition

Implemented as small, individually committable chunks so the diff stays
reviewable:

### M1.a — codec primitives in `mc-protocol`

Just enough to encode/decode every Minecraft primitive type that any 26.1
packet uses. No packet structures yet, no network code yet.

Public surface (under `mc_protocol::codec`):

- `VarInt(i32)`, `VarLong(i64)` newtypes with `encode` / `decode`
- Free functions for primitives: `bool`, `u8/i8`, `u16/i16`, `i32`, `i64`,
  `f32`, `f64`, `uuid`, `string` (with max-length parameter)
- `Identifier` (validated `namespace:path`) — light wrapper around `String`
- A `Reader<'a>` / `Writer` pair built over `bytes::Buf` / `bytes::BufMut`
- Error enum `CodecError` covering: buffer underflow, varint overflow,
  invalid UTF-8, string too long, invalid identifier
- A `read_varint_partial(&[u8])` API the framing layer can call without
  needing to consume bytes on `NeedMore`

Tests: exhaustive unit tests for boundary varint values (0, 1, 127, 128,
i32::MAX, i32::MIN, all-the-way-negative), proptest round-trip for every
primitive, golden vectors taken from the wiki.vg "Data types" page.

### M1.b — packet framing in `mc-protocol`

- Length-prefixed framing: parse `VarInt length + payload` out of a
  `BytesMut` ring; emit the same on write
- Optional zlib compression layer once the per-connection threshold is set
- Optional AES-128/CFB8 cipher layer applied before the framer
- A `tokio_util::codec`-style `FrameCodec` is convenient but we can also
  hand-roll for full control — pick during implementation
- Tests: simulated split-buffer reads (one byte at a time), compression
  on / off / threshold-edge, encryption round-trip

### M1.c — connection state machine + Status

- `ConnectionState` enum: `Handshake | Status | Login | Configuration | Play`
- Per-connection async task: read frame → dispatch packet by `(state, id)`
- Handshake packet (serverbound `0x00`, intent VarInt → Status or Login)
- Status state: respond to status request with a JSON document built from
  `ServerConfig` and the running server version; pong with the client's
  payload
- Acceptance: a vanilla 26.1.x client shows the server in its multiplayer
  list with the configured MOTD; `mcstatus`-style external tools also
  succeed

### M1.d — Login state (offline mode only)

- Receive `Login Start (name, uuid)`
- Offline UUID: `UUID v3` of `"OfflinePlayer:" + name` per common
  community convention; we'll switch to Mojang auth only when Configuration
  works end to end
- Send `Login Success` immediately, no encryption, no compression
- Receive `Login Acknowledged` → transition to Configuration
- Encryption (`Encryption Request` / `Encryption Response` / AES setup) is
  scaffolded but feature-gated behind `"online-mode"` and left untested in
  M1; full online-mode is its own milestone
- Acceptance: client transitions out of the "Logging in…" screen

### M1.e — Configuration state

- Send `Clientbound Plugin Message` "minecraft:brand" = "Solaris"
- Send the minimum registry payloads the client requires to advance
  (dimension types, biomes, damage types, …). For M1 we send a single
  stub dimension/biome — the goal is *the client accepts it*, not parity.
  This needs Network NBT, so M1.e depends on M1.f.
- Send `Finish Configuration`; await `Acknowledge Finish Configuration`
- Transition to Play

### M1.f — Minimal Network NBT in `mc-nbt`

- Just enough of the NBT codec to emit the registries in M1.e
- We add `fastnbt` as a dependency and write our own thin Solaris-side
  wrappers; rolling NBT fully from scratch is out of scope for M1 and would
  bloat the milestone past its 100h estimate

### M1.g — Play state entry

- Send `Login (Play)` with a stub entity ID, gamemode survival, single
  fake dimension, 0/0 spawn, view distance from config
- Send `Set Default Spawn Position` and `Synchronize Player Position` so
  the vanilla client unblocks its loading screen
- KeepAlive loop (server-initiated every 15 s, kick on no-response in 30 s)
- Acceptance: vanilla 26.1.x client reaches the Play state, stays
  connected for ≥ 60 s, no protocol disconnect, no crash. World will be
  black (no chunks) — that is intentional, chunk data is M2.

### M1.h — Wire-up in `mc-server` + integration test

- `mc-net::Server::run(config)` API
- The `mc-server` binary now actually serves: it parses the config, builds
  the server, awaits Ctrl-C
- Integration test in `crates/mc-server/tests/connect.rs` that drives a
  raw TCP client through a handshake + status request and asserts the
  status JSON shape — does not require a real Minecraft client and
  therefore runs in CI

## Acceptance criteria for M1 as a whole

1. `cargo test --workspace` passes; ≥ 95% line coverage on the
   `mc-protocol::codec` module (measured locally with `cargo-llvm-cov`,
   not enforced in CI yet)
2. A vanilla 26.1.x client lists the server in its server browser with the
   configured MOTD
3. A vanilla 26.1.x client connects to `localhost:25565` and reaches the
   Play state with no protocol-level disconnect
4. The connection survives ≥ 60 s in the Play state with the server
   sending KeepAlives and the client responding
5. `cargo clippy --workspace --all-targets -- -D warnings` stays green
6. No `unsafe` (enforced by workspace lint)
7. No Mojang code in our repo; no use of Mojmap mappings to inform our
   design (PROJECT_SPEC §8.1)

## Out of scope (recorded so it does not creep)

- Online-mode authentication against Mojang's session server (own milestone
  later; the spec puts auth concerns in M22 anti-cheat work)
- Encryption transport beyond a code stub
- World data, chunk streaming, entities, inventories — all M2+
- Custom protocol extension (`solaris:*` namespaces) — M10
- Per-player permissions, ops, commands — later
- Server list favicon — trivial but not load-bearing for acceptance

## Open questions

- Exact 26.1.x protocol version number is locked at start of M1.a once we
  read it off `.analysis/server.jar`'s `version.json`. Stored in
  `mc_protocol::PROTOCOL_VERSION`.
- Whether to use `tokio_util::codec::Framed` for the framing layer or roll
  our own — decide in M1.b.
- Whether `Identifier` should intern strings — defer until M9 (data pack
  loader), where it actually matters.
