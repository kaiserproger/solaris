## Goal

Make the vanilla 26.1.2 client render the entire 21×21 view-distance
window around spawn fully lit when connecting to
`solaris --config example.toml` against `.analysis/test-world/`,
instead of the current "player's chunk only" lit island. Concretely:
each `LevelChunkWithLight` packet emitted by `mc_net::play` carries a
non-empty `LightData` payload with per-section sky-light and
block-light nibble arrays that match what a vanilla server would
emit for the same chunk. The acceptance gate is a manual vanilla-
client connect (now seeing a fully lit world); the regression gate
is an extension of M3.g's raw-TCP harness asserting non-empty
light masks and nibble invariants on streamed chunks.

This is the first milestone where Solaris owns the lighting
computation, not just the wire transport. M3 left the data plane
shaped right (`LightData` struct exists, encode/decode round-trip
tested) and stubbed it with `empty()`; M4 fills in the values.

## Strategy

Same posture as M1 / M2 / M3 (PROJECT_SPEC §8.1, ADR 0001, ADR 0002).

- The lighting model is 4-bit per cell (0..=15), separate sky and
  block channels, propagation rule "value − 1 per step, blocked at
  opaque cells". This is the *vanilla wire shape* (the nibble
  arrays the client expects), not a translation of Mojang's
  propagation algorithm. We implement our own BFS that produces the
  same observable values; we do *not* read decompiled vanilla
  source for the algorithm.
- Two complementary sources of light values:
  1. **Baked Anvil light arrays.** Every chunk in
     `.analysis/test-world/` already has `BlockLight` / `SkyLight`
     nibble arrays on disk — vanilla wrote them. M2's codec
     deliberately dropped them (open follow-up #2, "extras
     channel"); M4 reads them back into `Chunk` as the cheap path.
  2. **Solaris-computed light.** For chunks that lack baked data
     (the air-placeholder slots `emit_chunks_around` ships when
     `WorldStorage` returns `None`, plus any future worldgen-
     emitted chunks in later milestones), we run a propagation
     pass that produces the same nibble shape.
- Both paths feed the same `mc_world::wire::encode_chunk_light`
  function; the wire output is indistinguishable.
- For the propagation pass we need per-block-state metadata that
  the Mojang `--reports` dump *doesn't* include: `light_emission`,
  `light_block` (opacity), and `occludes_neighbour_signals_for_sky`
  (whether sky-light is fully blocked above this state). The
  cleanest extraction path is a small Java helper that iterates
  the `Blocks` registry against the bundled jar and writes a JSON
  table — same posture as `tools/extract-vanilla-data.sh`. Treated
  as ADR 0001 data (block-state metadata, not code).
- The lighting engine runs at *chunk-emit time*, not at chunk-load
  time, and operates over a `3×3` chunk neighbourhood window so
  values across chunk seams converge. Per-chunk caches in
  `WorldStorage` are M5 territory; M4 is allowed to recompute on
  every emit as long as the 441-chunk spawn burst still finishes
  inside the M3.g harness time bound.

## Sub-milestone decomposition

Tentative ordering. M4.a–M4.c are foundational and serial; M4.d–M4.e
can overlap; M4.f is the CI gate; M4.g is the manual gate +
closeout.

### M4.a — Anvil light decode

In `mc_world::anvil::chunk_nbt`:

- Extend section NBT decoding to read `BlockLight` and `SkyLight`
  `ByteArray(2048)` fields when present. Both are 4-bit-per-cell
  nibble arrays in the same `(y, z, x)` linear order as the section
  block container; vanilla writes them post-lighting-pass.
- New `mc_world::chunk::SectionLight { block: Option<[u8; 2048]>,
  sky: Option<[u8; 2048]> }` (or equivalent — final shape decided
  in M4.a). Attached per-section, alongside the existing 24
  `ChunkSection`s. Same Y-indexing.
- Vanilla also writes section indices outside the `0..24` range
  for the empty above/below layers (Y=-5 and Y=20 in our scheme);
  surface them too so the wire encoder has the full 26-section
  light column (per `LightData`'s 26-bit Y mask).
- `M2 follow-up #2` ("extras opaque channel") stays out of scope —
  M4.a touches *only* the two light arrays. Other dropped fields
  (block/fluid ticks, structures, PostProcessing, InhabitedTime,
  …) wait for M5.
- Tests: decode r.0.0.mca chunk (0,0); assert both arrays present,
  2048 bytes each, sky-light at (x=0, top-section, top-cell) is
  `0xF`, sky-light deep underground (Y=-60 inside bedrock) is `0`.
- Tests: a chunk in `Status: empty` mode (the placeholder slots
  beyond view-distance-2 of the test-world generator) returns
  `None` for both arrays — placeholder, no lighting baked.

### M4.b — block-state light table

Per-block-state metadata we need:

- `emission: u8 (0..=15)` — torches=14, glowstone=15, soul_lantern=10, etc.
- `opacity: u8 (0..=15)` — how much sky/block light each step loses
  passing through. Vanilla mostly uses 0 (transparent) or 15
  (opaque) with a handful in between (water/ice=1, slime/honey=0).
- `occludes_sky: bool` — whether this state blocks sky-light pass-
  through entirely. Distinct from `opacity` because some blocks are
  visually transparent but still cast skylight shadow (leaves with
  certain configs).

Extraction: extend `tools/extract-vanilla-data.sh` (or add a
sibling `tools/extract-block-light.sh`) with a small Java helper
that:

1. Loads the bundled `.analysis/server.jar` classpath.
2. Iterates `BuiltInRegistries.BLOCK` → for each `Block`, iterates
   `block.getStateDefinition().getPossibleStates()`.
3. For each `BlockState`, reads `getLightEmission()`,
   `getLightBlock()`, and the sky-occlusion predicate (the exact
   API name is verified against the javap dump in M4.b's first
   commit — likely `propagatesSkylightDown(level, pos)` evaluated
   at a sentinel position).
4. Writes JSON keyed by global state-id, identical schema to what
   `--reports blocks.json` would produce if Mojang exported these.

Output: `data/vanilla/reports/block_light.json` (gitignored under
the existing `data/vanilla/data/**` rule; check the .gitignore and
add a pattern if needed). The .sh script is the tracked artifact;
the JSON is not.

In `mc-data`:

- `mc_data::BlockLightTable { emission: Vec<u8>, opacity: Vec<u8>,
  occludes_sky: BitVec }` indexed by `BlockStateId.0` (the same
  global state-id `mc-data::BlockRegistry` already uses).
- `mc_server::main` loads `block_light.json` next to
  `blocks.json` at startup, same error posture (clear "did you run
  the extract script?" message on miss).
- Tests: ASCII fixtures for ~5 known blocks (air, stone, torch,
  glass, glowstone) pinning the table values against expected
  numbers. Pinned to the *script output*, not from memory (see
  [[feedback-terse-no-stalls]] — capture truth first, then pin).

### M4.c — propagation engine

New module `mc_world::light`:

- Pure function `compute_light(neighbours: &ChunkNeighbourhood,
  table: &BlockLightTable) -> ChunkLight` over a 3×3 column window
  centred on the chunk being emitted, returning the centre's
  per-section nibble arrays.
- Block-light pass: BFS seeded from every cell whose state has
  non-zero `emission`. Each step decrements by 1, clipped at 0,
  capped at `15 − opacity` per traversed cell (matches vanilla's
  "soft" opacity semantics for blocks like water).
- Sky-light pass: top-of-world cells outside the chunk's
  `MOTION_BLOCKING` heightmap start at 15. Vertical propagation
  through transparent columns is `O(1)` per (x, z) via the
  heightmap shortcut; horizontal/diagonal propagation is BFS like
  block-light.
- Output: per-section `[u8; 2048]` nibble arrays for block and sky,
  Y-indexed `-1..=24` (26 sections; outside-world layers are
  always `15` for sky, `0` for block).
- Determinism: the BFS order does not affect the final values
  (max-of-sources), but we still iterate in a fixed (y, z, x)
  order for byte-stable test pinning.
- No threading inside the engine in M4. If profiling shows the
  441-chunk emit budget blowing past M3.g's harness timeout, fall
  back to "Anvil-only for baked chunks, engine only for
  placeholders" (see M4.e).

Tests:

- A single isolated air-filled chunk: sky-light is 15 everywhere.
- A chunk with one `glowstone` block at (8, 64, 8) surrounded by
  air: block-light at (8, 64, 8) = 15, at (9, 64, 8) = 14, …, at
  (8+15, 64, 8) = 0.
- A 1×1 vertical bedrock column at (8, _, 8) from Y=0 to Y=319,
  air elsewhere: sky-light at (8, -60, 8) = 0; at (9, -60, 8) > 0
  (lateral leak); at (8, 64, 8) = 0 still (blocked).
- 3×3 neighbourhood seam test: a glowstone in centre chunk at
  (15, 64, 15) lights cell (0, 64, 0) of the (+x, +z) neighbour
  at value 12 (15 − 3 Chebyshev steps).
- Engine output for a fully-baked Anvil chunk equals the baked
  arrays to within the engine's epsilon (vanilla's own engine has
  iteration order quirks that produce occasional 1-off
  discrepancies; M4.c records the observed tolerance and we
  tolerate it in tests rather than chase byte parity).

### M4.d — `mc_world::wire::encode_chunk_light`

In `mc_world::wire`:

- `encode_chunk_light(light: &ChunkLight) -> LightData` produces
  the `mc_protocol::packets::play::LightData` payload:
  - `sky_y_mask` / `block_y_mask`: 26-bit BitSet (one `i64`) with
    bits set for every section that has *any* non-zero nibble.
  - `empty_sky_y_mask` / `empty_block_y_mask`: bits set for every
    section that has *only* zeros.
  - `sky_updates` / `block_updates`: one 2048-byte layer per
    section flagged present in the corresponding mask, in
    ascending Y order.
- Tests: round-trip a synthetic `ChunkLight` through encode +
  decode (`LightData::decode`), assert byte equality and that
  masks add up to 26 bits across present+empty (a section
  appearing in neither is illegal — every Y slot is either
  populated or explicitly empty).
- Tests: feed the M4.a-decoded baked nibbles for chunk (0, 0)
  through `encode_chunk_light`, decode via `LightData::decode`,
  assert it produces the same byte stream.

### M4.e — wire path in `mc-net::play`

Replace `LightData::empty()` in `build_chunk_packet`:

- `build_chunk_packet` takes a new `&ChunkLight` parameter.
- The chunk fetcher in `mc_net::play::emit_chunks_around` resolves
  light per chunk: if the chunk has baked light from M4.a, use it
  directly; otherwise compute via M4.c over the chunk's 3×3
  neighbourhood (requires `WorldStorage` to be able to surface
  neighbour chunks — that API exists today via `ensure_chunk`).
- Placeholder air chunks (the "missing → single-state air"
  fallback) get engine-computed light, since baked nibbles do not
  exist for them. Result: sky-light 15 everywhere, block-light 0;
  client sees them as fully lit empty air. Avoids the seam between
  "lit baked chunk" and "dark placeholder".
- `LightData::empty()` is removed from the Play hot path. The
  function stays in `mc-protocol` as a convenience for tests but
  ceases to be reachable from production code; we add a lint check
  via `cargo deny` or a `#[deny(dead_code)]` annotation if convenient,
  otherwise just delete the call site and move on.

### M4.f — harness assertion (extend M3.g)

In `crates/mc-test-harness/tests/chunk_stream.rs`:

- For each received `LevelChunkWithLight`, parse `LightData` and
  assert:
  - `sky_y_mask | empty_sky_y_mask` covers all 26 section slots.
  - `sky_updates.len() == popcount(sky_y_mask)`; same for block.
  - For the spawn chunk specifically: top section's sky nibbles are
    all `0xF` (open sky); ground section's sky nibbles are mostly
    `0` (under bedrock/grass).
  - At least one chunk in the 441-burst carries non-zero block
    light (subject to the test world actually containing a
    luminous block — verify in M4.f's first commit; if it doesn't,
    add a hand-placed torch via the world-gen script).
- Existing M3.g assertions stay; M4 is additive.

## Out of scope (so it does not creep)

- **Dynamic light updates.** When a block break/place changes
  light, vanilla re-runs propagation in a chunk-window and emits
  `ClientboundLightUpdate` packets. We don't break/place blocks
  yet (M3 left chunk modification to a future milestone, see
  scope option C in the session kick-off). M5/C — when interaction
  lands.
- **Standalone `ClientboundLightUpdate` packet type.** Lives in
  `mc-protocol` as a future addition; not needed when light only
  ships bundled inside `LevelChunkWithLight`. Add when M5/C arrives.
- **Worldgen-emitted chunks.** M4 lights what the Anvil reader
  produces (real chunks) or the placeholder filler (air chunks).
  Once worldgen exists (later M4-rebadge / M5 / M6), its output
  feeds the same lighting engine; no engine work needed.
- **Heightmap recompute** (M2 follow-up #5). Sky-light's heightmap
  shortcut reads `MOTION_BLOCKING` from the chunk; for baked
  chunks this is correct on disk, for placeholder chunks it is
  trivially `MIN_Y` everywhere. No mutation = no recompute.
- **Direct-mode palette growth past 256 states** (M2 follow-up #3),
  **LZ4 read path** (#4), **`extras` opaque channel** for *non-
  light* dropped chunk fields (#2). All still open and untouched
  by M4. Documented as carry-over.
- **Region-level caching of computed light.** The engine recomputes
  on every emit. If profile shows it's too slow we cache; that
  knob lands in M4.c only if the M3.g-style harness timeout fails.
- **Spiral chunk-iteration order.** Independent perf tweak, not
  load-bearing on lighting. Carry-over from M3.
- **`Set Compression`.** Still off; chunk packets now grow by ~96
  KiB worst case per chunk (26 sky + 26 block × 2048 B), so
  enabling zlib will become much more attractive — but only if
  the 441-burst trips a wire-throughput problem. Decision deferred
  until measured; M4 ships uncompressed.
- **Coloured / volumetric light, Beta-era smooth lighting.** Not
  in scope. Ever.

## Open questions to resolve along the way

- **`occludes_sky` API name.** The `propagatesSkylightDown` method
  evaluates against a `Level` + `BlockPos`; the helper has to feed
  it a sentinel position. Some BlockState predicates depend on
  block properties (waterlogged variants) — verify whether the
  predicate is constant per state. Fall back to inferring from
  `opacity == 0 ? true : false` if the runtime call is hostile.
- **Engine vs baked divergence.** Vanilla's own propagation has
  iteration-order artefacts and chunk-relight quirks. M4.c may
  produce values 1 nibble apart at some seams. Decision: pin our
  engine against itself, *not* against vanilla's baked output, and
  log the divergence count for the test world in the appendix.
- **Placeholder chunk treatment.** Air-placeholder slots
  currently exist because `WorldStorage` returns `None` past r.0.0.
  Lighting them as "all sky-15, all block-0" is correct for an
  infinite-sky air world; the player can still see the world end
  visually because there's no terrain past r.0.0. That's a
  worldgen problem, not a lighting one — flag in the appendix
  rather than fix here.
- **Engine perf for 441 chunks.** Each chunk runs a 3×3
  neighbourhood propagation. If the harness latency budget
  (~2 s for the full burst in M3.g) blows out, the cheap fix is
  to run the engine *once per region* and cache nibbles per chunk.
  Hold off until measured.
- **Block-light extraction reproducibility.** The extraction
  script must produce byte-identical JSON across runs for clean
  CI. Vanilla's `BlockState` iteration order is registry insertion
  order — stable, but verify by running twice and diffing.

## Pitfalls (carry-over from M2 + M3 + light specifics)

- **Nibble packing.** Vanilla packs two 4-bit values per byte;
  the *low* nibble is the cell at even index, *high* is odd. Easy
  to invert on first cut; the M4.a unit test decoding a known cell
  catches this immediately if pinned against a real Anvil byte.
- **Section Y indexing for light.** Light masks are 26 bits wide
  (`-1..=24`), wider than the 24-section block column. Off-by-one
  on the mask vs. the block column is the most likely first-day
  bug. M3.a's `LightData` round-trip test already pinned the bit
  count; reuse the same Y mapping.
- **Light data does not cross block-entity boundaries.** Some
  block entities (sea_lantern, etc.) emit light via *block* state,
  not *entity* state. M4.b's table indexes by `BlockStateId`, not
  by block-entity NBT — confirm the emission is on the block
  state for the M4 in-test luminous block. If a future block needs
  entity-driven emission, lighting becomes block-entity-aware in
  M5 alongside dynamic updates.
- **Mojang `--reports` blocks.json doesn't carry light data.**
  Validated above. M4.b's helper has to actually load the Java
  classes; do not look for a pre-existing JSON field. (Caught
  early during planning — saves a half-day of "where's the
  luminance column".)
- **Engine recursion vs. BFS.** Sky-light propagation can chain
  hundreds of cells horizontally under glass; a naive recursive
  implementation will stack-overflow on a real chunk. Use an
  explicit queue from the start.
- **Per-cell opacity clip.** Vanilla's `getLightBlock` returns
  values >0 for "soft" attenuators (water = 1, ice = 1, slime = 0,
  honey = 0). Don't shortcut to "opaque vs. transparent": always
  decrement by `max(1, opacity)` per step, cap at 15.
- Per [[feedback-no-external-artifacts]], the `block_light.json`
  output and any captured Anvil light bytes used as fixtures stay
  in `.analysis/` / `data/vanilla/data/` (git-ignored). Anything
  checked into `tests/` is synthesised in-code or read at test
  time.
