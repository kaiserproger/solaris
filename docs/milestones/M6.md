# M6 — Persistence + Inventory

**Status:** plan only, on `dev/M6-persistence-inventory` (0
commits ahead of `main` at `4e3cfec`, tag `m5`).
`cargo test --workspace` baseline is 217 tests green,
`clippy --workspace --all-targets -- -D warnings` and
`cargo fmt --all -- --check` clean.
**Estimate:** 60–100 h. Option **A** of the M6 kick-off menu —
the natural follow-on to M5: now that the player can edit the
world, the edits should *stick*, and they should be edits of the
block the player actually holds (not always stone). After M6
Solaris is "alpha-shaped": a session can be paused, the server
restarted, and the same world re-loaded with its modifications
intact.
**Owning crates:** `mc-world` (Anvil writer + dirty-chunk
tracking + flush API), `mc-server` (Ctrl-C signal handler →
flush before exit), `mc-protocol` (six new packet types — four
inventory-side, plus the `ItemStack` wire codec), `mc-net::play`
(per-connection inventory state, hotbar dispatch, place uses
held item, seed-kit on login), `mc-test-harness` (integration
test that round-trips edits across a server restart).

## Goal

After M6 a vanilla 26.1.2 player on the test world must be able to:

1. Connect, see a non-empty hotbar (server seeds a small starter
   kit: stone, dirt, oak planks, torch — slots 0–3).
2. Scroll the hotbar — the server tracks the selected slot.
3. Right-click → place the **selected item** (not always stone).
   Block placement decrements the slot; emptying a slot leaves
   the slot empty.
4. Break a few blocks, place a few. Disconnect.
5. Restart the server (`cargo run --bin mc-server -- --config
   example.toml`). Reconnect. The modifications are still there.

Concretely, M6 wires three new things into the existing
M5 interaction loop:

- **Persistence.** `Chunk → NBT → zlib → .mca` write path,
  hooked into a graceful-shutdown signal handler. The M5.c
  extras channel already keeps the round-trip lossless across
  the unmodelled root fields.
- **Inventory model.** Per-connection `PlayerInventory` (46
  slots: 36 main + 9 hotbar overlap on slots 36..44 + offhand
  on 45 + 4 armor on 5..8 per vanilla's window-0 layout) plus a
  `selected_hotbar_slot: u8` (0..8). Held-item lookup =
  `inventory.main[36 + selected_hotbar_slot]`.
- **Hotbar wire flow.** Server emits
  `ClientboundSetHeldSlot` + `ClientboundContainerSetContent`
  on login to seed the kit; reads `ServerboundSetCarriedItem` to
  track scroll; uses the held item in `handle_use_item_on` to
  pick the block; emits `ClientboundContainerSetSlot` on
  place to decrement the slot.

The acceptance gate has two parts:

- **Mechanical (M6.g harness):** integration test boots
  `mc_net::run`, places a known block, disconnects, asserts the
  on-disk `.mca` now decodes a chunk with that block at the
  expected position. Bonus leg: re-boot the server in the same
  process (or read the `.mca` back directly) and confirm the
  read path returns the modified value.
- **Manual:** a PrismLauncher 26.1.2 client connects, sees the
  starter kit in hotbar, scrolls to dirt, places dirt, breaks
  some grass, disconnects. Server stops (Ctrl-C). Server
  restarts. Client reconnects — modifications are present, the
  starter kit is fresh again (per-session inventory; persistent
  inventory is M7+).

## Strategy

Same posture as M1–M5 (PROJECT_SPEC §8.1, ADR 0001, ADR 0002).

- **Packet IDs and record layouts** come from `javap -p` of the
  unobfuscated 26.1.2 jar, cited inline as comments per ADR 0002.
  IDs are *positions* in `GameProtocols`'s registration table
  (`.analysis/protocol-dump.txt:68`). Counting from the
  table:
  - `CLIENTBOUND_CONTAINER_SET_CONTENT` at table index 18 (0x12).
  - `CLIENTBOUND_CONTAINER_SET_SLOT` at index 20 (0x14).
  - `CLIENTBOUND_SET_HELD_SLOT` at index 105 (0x69).
  - `CLIENTBOUND_SET_PLAYER_INVENTORY` at index 108 (0x6C).
  - `SERVERBOUND_SET_CARRIED_ITEM` at index 53 (0x35) within
    the serverbound block.
  Confirm each against `wire-probe`'d real traffic before
  shipping the packet.
- **`ItemStack` wire codec.** Modern protocol encodes an item
  stack as `(count: VarInt)` followed by — if `count > 0` —
  `(item_id: VarInt, components_to_add: VarInt, components_to_remove: VarInt, [DataComponentPatch entries…])`.
  For M6 we emit only `count == 0` (empty) or `count > 0` with
  `0` add/remove patches and item-registry id resolved from
  `data/vanilla/data/minecraft/registries/item.json`. We **do
  not** model data components in M6 — the kit is plain stacks
  of vanilla items. The decoder must still be tolerant of
  non-zero patch counts (consume + drop the bytes) for the eventual
  ServerboundContainerClick / SetCreativeModeSlot path; M6.c.4
  ships a minimal "skip components" decoder used only as a
  sentinel.
- **Item registry.** `mc-data` already loads block-registry
  JSON for `BlockStateId`. M6 extends the loader to read
  `data/vanilla/data/minecraft/registries/item.json` (or
  `.../item/data.json` — check actual path under `data/vanilla/`)
  into a `ItemRegistry { id: u32 → name: Identifier }` lookup,
  symmetric with `BlockRegistry`. Optional cross-reference for
  the few items that correspond to placeable blocks: a
  `item_to_block(item_id) -> Option<BlockStateId>` helper that
  resolves e.g. `minecraft:stone` (item) → `minecraft:stone`
  (default block state). Initial table can be hard-coded for the
  M6 starter kit (4 entries) and grown opportunistically;
  full coverage is M7+.
- **Anvil writer.** The decoder side already has every piece
  needed:
  - `chunk_to_nbt(&Chunk, &BlockRegistry) -> Tag` already
    exists (`crates/mc-world/src/anvil/chunk_nbt.rs:326`) and
    round-trips through `round_trip_real_vanilla_chunks`
    against modelled state + extras.
  - `mc_nbt::write_named(buf, name, &Tag::Compound)` already
    exists (`crates/mc-nbt/src/lib.rs:388`).
  - `write_region(path, &[ChunkPayload])` already exists
    (`crates/mc-world/src/anvil/region.rs:223`) and handles
    sector layout, compression header byte, padding to 4096.
  - All M6.a adds is the *glue* layer that converts a
    `&Chunk` plus a `u32` timestamp into a `ChunkPayload`, plus
    the dirty-chunk tracking on `WorldStorage` and a
    `WorldStorage::flush_dirty()` API that batches by region.
- **Dirty tracking.** `WorldStorage` grows a
  `dirty: HashSet<ChunkPos>` (or per-chunk `dirty: bool`). Every
  `set_block_at` that actually changes a state marks the chunk
  dirty. Eviction of a dirty chunk from the LRU must flush it
  first (otherwise the player edits get silently dropped when
  the cache fills). For M6 we ship a *simple* eviction-flush
  ("evict-then-write, synchronously, holding the storage lock")
  rather than an async background writer; M5's load posture is
  already synchronous and the LRU is small (16 chunks by
  default). Async write-back is M7+ perf work.
- **Shutdown hook.** `mc-server::main` grows a
  `tokio::signal::ctrl_c()` arm in a `select!` against the
  long-lived `mc_net::run` future. On Ctrl-C: stop accepting
  new connections, cancel the listener, take the
  `Arc<Mutex<WorldStorage>>` exclusively (the listener task
  drop should already do this), call `flush_dirty()`,
  print a one-line "flushed N chunks" log, exit. We do **not**
  attempt to gracefully disconnect existing clients in M6 — they
  see a TCP close, which is what vanilla also does on `/stop` if
  the connection isn't cooperating. Client-coordinated shutdown
  is M7+.
- **Per-connection inventory.** `InteractionState` (current
  `crates/mc-net/src/play.rs:225`) grows two fields:
  `inventory: PlayerInventory` and
  `selected_hotbar_slot: u8`. `PlayerInventory` is a plain
  struct (`main: [ItemStack; 36]`, `armor: [ItemStack; 4]`,
  `offhand: ItemStack`) with helpers `held(&self) -> &ItemStack`
  and `held_mut(&mut self)`. On login the play handler
  initialises the kit and emits two packets:
  `ClientboundSetHeldSlot { slot: 0 }` then
  `ClientboundContainerSetContent { container_id: 0, state_id:
  1, items: <46-element list>, carried_item: empty }`. The
  `state_id` counter increments per inventory mutation; the
  client uses it to detect desync.
- **Place uses held item.** `handle_use_item_on` resolves
  `state.inventory.held()`, calls
  `state.items.item_to_block(item_id)` (new), and:
  - If no mapping (or empty held): no-op, still ack the
    sequence. (Vanilla animates the player swing client-side;
    server side it's silent.)
  - If mapping: apply that block instead of hardcoded stone,
    decrement the held stack's count, emit
    `ContainerSetSlot { container_id: 0, state_id: N+1, slot: 36
    + selected, item_stack: <new state> }`. The existing
    `apply_block_edit` already handles the BlockUpdate + Light
    + Ack ripple.
- **Hotbar scroll.** `ServerboundSetCarriedItem { slot: i16 }`
  arrives whenever the client scrolls. Server clamps to `0..9`,
  updates `selected_hotbar_slot`. No ack: the client is
  authoritative on its own hotbar selection. (Server-side
  authority is M22+.)
- **Authority for inventory mutations.** Server is
  authoritative on item counts and which blocks may be placed,
  but does **not** mutate inventory based on
  `ServerboundContainerClick` in M6 — clicks are read off the
  wire and discarded with a trace log; the only mutation paths
  in M6 are (a) login seeding and (b) place-decrement. This
  intentionally keeps M6 small; full container click handling
  is its own milestone.

## Sub-milestone decomposition

Tentative ordering. M6.a/M6.b are mc-world-only and run first.
M6.c–M6.f are protocol + net work and can interleave once the
inventory model lands. M6.g is the integration gate, M6.h is
the closeout.

### M6.a — chunk_to_payload + Anvil region writer integration

In `crates/mc-world/`:

- New `Chunk::to_payload(&self, &BlockRegistry, timestamp: u32)
  -> Result<ChunkPayload, ChunkNbtError>` in
  `src/anvil/chunk_nbt.rs`. Calls the existing
  `chunk_to_nbt`, serialises through `mc_nbt::write_named`
  into a fresh `Vec<u8>`, packages into a `ChunkPayload`. The
  `name` byte sequence for `write_named` is empty (Anvil chunks
  are stored unnamed under their region slot — verify against
  the M2 decoder).
- New `WorldStorage::flush_chunk(&mut self, pos: ChunkPos) ->
  Result<(), WorldError>` in `src/storage.rs`. Resolves the
  region, loads the existing region payload list (uses the
  existing region-cache path if hot), replaces the slot's
  payload with the new one (preserving timestamps for other
  slots, bumping the modified slot's timestamp to "now"),
  writes the region back via `write_region` to a temp file
  next to the target, then `fs::rename` atomically. (POSIX
  rename is atomic *if* same filesystem — the test world is
  always on the same FS as the temp file by construction.)
- New test in `src/anvil/chunk_nbt.rs`:
  `round_trip_modified_chunk_through_disk`. Decodes a chunk
  from the test world, sets one block, flushes to a temp
  `.mca`, decodes again, asserts the block change is visible
  *and* all other modelled fields plus `extras` round-trip
  byte-stable.

### M6.b — dirty tracking + shutdown flush

In `crates/mc-world/`:

- `Chunk` grows `dirty: bool` (default `false`). `set_block`
  sets `dirty = true` whenever the stored state-id actually
  changes. `flush_chunk` clears it on success.
- `WorldStorage::flush_dirty(&mut self) -> Result<usize,
  WorldError>` walks the chunk LRU, calls `flush_chunk` on each
  dirty entry, returns the count flushed.
- LRU eviction (`evict_oldest`) must call `flush_chunk` on the
  victim before dropping it from the cache. Errors here are
  *not* silently dropped — they propagate up. (For M6 we accept
  that an I/O failure during eviction crashes the player's
  edit path; safer is M7+.)

In `crates/mc-server/`:

- `main.rs`: wrap the `mc_net::run(config).await` call in a
  `tokio::select!` against `tokio::signal::ctrl_c()`. On Ctrl-C
  break out, drop the listener future, acquire the world
  mutex, call `flush_dirty`, log
  `"shutdown: flushed {n} chunk(s)"`, return.

Tests: a unit-level `flush_dirty_writes_modified_chunks` in
`mc-world` over a temp world dir (copy the M2 test region into
a `tempfile::TempDir` so we don't pollute the bundled world).

### M6.c — ItemStack wire codec + ItemRegistry

In `crates/mc-data/`:

- New `ItemRegistry` mirroring `BlockRegistry`: load

In `crates/mc-protocol/`:

  `Default` is "empty stack".
- Codec functions `encode_item_stack(buf, &ItemStack)` and
  `decode_item_stack(buf) -> ItemStack`.
- Round-trip tests over synthetic stacks (empty, non-empty

### M6.f — wire it together in `play::handle`

In `crates/mc-net/src/play.rs`:

- After the spawn burst (`init_play_packets`), emit
  `SetHeldSlot { slot: 0 }` and a seed
  `ContainerSetContent` with the M6 starter kit (`state_id =
  1`). Increment `inventory_state_id` past 1 so the next
  mutation uses `2`.
- In the keepalive loop dispatch, decode `SetCarriedItem` (id
  0x35) into `selected_hotbar_slot`. Clamp to 0..8.
- Rewrite `handle_use_item_on`:
  - resolve held item via `state.inventory.held()`,
  - look up `item_to_block`,
  - on miss: ack sequence, return,
  - on hit: call existing `apply_block_edit` with the
    resolved state, then decrement the held stack's count
    (clears the slot if count hits 0), bump
    `inventory_state_id`, emit `ContainerSetSlot` for the
    affected hotbar slot.

### M6.g — integration test: persistence + inventory round-trip

In `crates/mc-test-harness/tests/`:

New `tests/persistence_inventory.rs`. Two scenarios:

- **`hotbar_place_persists_through_flush`** — Bootstrap an
  on-disk **copy** of `.analysis/test-world` into a
  `tempfile::TempDir`, boot `mc_net::run` against it on
  `127.0.0.1:0`, walk to Play, drain the spawn burst, send
  `ServerboundSetCarriedItem { slot: 1 }` (= dirt), send

  dirt state id and `ContainerSetSlot` decrements the slot.
  Then send a disconnect / drop the client, await flush via

## Out of scope (so it does not creep)

- **Persistent player inventory across reconnects.** The
  starter kit is re-seeded every connection. Persistent
  per-UUID inventory is M7+ (it needs a separate `playerdata/`
  level subdirectory and a UUID→file mapping; not for M6).
- **Container click handling.** Drag, shift-click, swap,
  double-click, drop — all M7+. M6 reads
  `ServerboundContainerClick` off the wire and discards it
  (still ack-ing the request id field).
- **Creative-mode set-slot.** `ServerboundSetCreativeModeSlot`
  is decoded only enough to be skipped; we never apply it
  (game mode is fixed to creative or whatever the LoginPlay
  packet currently announces, but inventory is server-
  authoritative against the seed kit).
- **Async / background flush.** Flush runs synchronously on
  the Ctrl-C path and on LRU eviction. Background writer is
  M7+ perf work.
- **Multi-region atomicity.** A flush of N chunks across M
  regions does M sequential region writes; if the process
  crashes mid-flush, some regions are updated and others are
  not. Vanilla has the same property. M22+ anti-corruption is
  not M6 work.
- **Data components on item stacks.** M6 emits stacks with
  zero patches. Full DataComponentPatch support is M7+ (or
  M12+, paired with the client mod for custom items).
- **Item-to-block coverage beyond the kit.** Hard-coded 4
  entries. Comprehensive item→block table comes with
  `mc-data`'s wider registry work in M9+.
- **`PlayerLoaded` / spawn-loaded acknowledgement.** Vanilla
  expects a `ServerboundPlayerLoaded` once the client has
  digested the spawn burst; M5 already ignores it, M6 keeps
  the same posture (ignored, no reply).
- **Worldgen.** Still next; tentatively M7 per the M6 kick-off
  prompt.

## Open questions to resolve along the way

- **`ClientboundSetHeldSlot.slot` width.** Javap shows `int`,
  but the field is a hotbar index 0..8; on the wire it might
  be VarInt or i32. Pin via `wire-probe` capture of a real
  vanilla server's login flow before shipping the codec.
- **`ContainerSetContent.state_id` semantics on first emit.**
  Vanilla seems to start at 1 (incrementing on every subsequent
  mutation). Confirm via wire-probe; if vanilla resets to 0
  per-window, we follow.
- **Item registry source path.** Under
  `data/vanilla/data/minecraft/registries/`, vanilla 26.1+
  publishes JSON registry dumps. The exact filename for items
  is to be confirmed by `ls data/vanilla/data/minecraft/registries/`
  during M6.c; older versions used `item.json`, current may be
  `item/data.json` or per-namespace listing. The
  `tools/extract-vanilla-data.sh` script is the upstream; M6.c
  doesn't add a new extraction step, just consumes what's
  already there.
- **`item_to_block` for torches.** `minecraft:torch` (item)
  could resolve to `minecraft:torch` (free-standing) or
  `minecraft:wall_torch` depending on the face the player
  clicks. M6 always emits the free-standing variant; wall-torch
  selection is M7+ block-property routing.
- **Flush on eviction vs. flush on shutdown only.** The
  eviction-flush path is the more complex of the two (it
  needs to hold the storage lock while writing). The simpler
  alternative: never flush on eviction, only on Ctrl-C. The
  cost is that edits to a chunk that gets evicted *between*
  Ctrl-C presses are lost. For a 16-chunk LRU vs. ~441-chunk
  spawn burst this is realistic. Decide during M6.b based on
  whether the test world's chunk count can fit in the LRU; if
  not, ship eviction-flush. Either way, document the choice in
  the closeout.

## Pitfalls (carry-over from M1 + M2 + M3 + M4 + M5)

- **Packet ID volatility across patch releases.** Cite the
  javap source for every new ID; don't copy from older
  wire-probe captures. `SetHeldSlot` was a different ID in
  pre-26 versions.
- **Anvil rename atomicity.** `fs::rename` is atomic on POSIX
  *if* source and destination are on the same filesystem. The
  temp file must live in the *same* directory as the target
  `.mca`, not `/tmp/`.
- **`ItemStack` empty-stack encoding.** Modern protocol uses a
  leading `VarInt count`. `count == 0` means "no item", the
  rest of the fields are absent. Easy to off-by-one when
  encoding a list of 46 stacks where most are empty.
- **Slot index conventions.** Window-0 in modern protocol:
  slots 0–8 are crafting (output + 2×2 input + nothing? —
  verify), 9–35 are main inventory rows, 36–44 are hotbar,
  45 is offhand. Some references count from a different
  origin. Pin against a wire-probe capture.
- **LRU eviction during the spawn burst.** A 441-chunk spawn
  burst against a 16-slot LRU evicts most of itself; with the
  M6.b eviction-flush path, every eviction is a disk write.
  This could turn the spawn burst into an I/O storm if the
  burst chunks are all "dirty" — they shouldn't be (read-only
  load), but the dirty flag must default-clear on
  `decode_chunk`. Pin this in a test (`spawn_burst_does_not_flush`).
- **Player inventory desync.** If the server's
  `inventory_state_id` falls out of sync with the client's,
  the client rolls back to an earlier inventory snapshot.
  Always bump `state_id` *before* emitting the mutation packet.
- **Concurrent `WorldStorage` access during flush.** The
  Ctrl-C path takes the `Arc<Mutex<WorldStorage>>` exclusively.
  Any other tokio task still holding the mutex (a slow relight
  midway through, say) blocks the shutdown. Acceptable for M6
  (relight is fast); document the bound in the closeout.
- **`MAX_INDIRECT_BITS` removed in M5.c.3.** Don't accidentally
  re-introduce the 256-entry cap during the writer work. The
  encoder branches on `bits_per_entry >= 9` and switches to
  `GlobalPalette` on the wire; on disk we still encode the
  same palette+indices shape (vanilla doesn't have an on-disk
  direct format).
- Per [[feedback-no-external-artifacts]], any captured wire
  blobs and any modified `.mca` files stay in `.analysis/`
  (git-ignored).
