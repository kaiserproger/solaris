# M15 - Multiplayer chunk tickets

**Status:** code complete on `dev/M15-multiplayer-tickets`, cut from `main` at
tag `m14`. Automated gates are green; manual PrismLauncher two-client gate is
pending owner run.
**Estimate:** large milestone, 30-50 h. This slice turns M14's per-player moving
view subscription into a multiplayer-aware lifecycle: shared chunk demand,
verified unloads, disconnect cleanup, and block-edit visibility for nearby
subscribers.
**Owning crates:** `mc-protocol` for verified unload and any other new packet
types, `mc-net` for Play-session registry, ticket lifecycle, scheduling, and
broadcast routing, and `mc-test-harness` for two-client wire coverage.

## Goal

After M15, multiple Play connections should hold independent moving views while
sharing server-side chunk demand where safe. A chunk that leaves one player's
view should be unloaded only for that player, a disconnect should release all of
that player's tickets, and block edits should be broadcast to every subscribed
player that can currently see the affected chunk and relight region.

M14 deliberately kept ownership per connection. M15 adds the smallest shared
server state needed for multiplayer correctness without introducing a plugin
system, entity tracker, region scheduler, or full gameplay layer.

## Strategy

1. **Plan first, oracle before packet code.** Clientbound chunk unload must be
   verified from `.analysis/protocol-dump.txt`, regenerated `javap`, or a
   wire-probe capture before implementation. Do not infer the ID or `ChunkPos`
   encoding from memory.
2. **Keep socket writes connection-owned.** Shared state may decide who should
   receive an event, but each Play task owns its writer, framing/compression
   boundary, and per-connection `LightCache` mutation.
3. **Introduce a small session registry, not an event bus.** Track active Play
   sessions by server-assigned id with profile, current center, view distance,
   loaded/subscribed chunks, and an outbound command channel.
4. **Separate desired, prepared, loaded, and subscribed.** A chunk can be wanted
   by multiple players, prepared by worker code, loaded in one client's view, and
   absent from another. Tests should catch unload/load flaps caused by collapsing
   these states.
5. **Share only where the boundary is honest.** Chunk load/generate/light/encode
   work may be reused when one prepared result is valid for multiple subscribers.
   Framing and compression may remain per connection if policy or state makes
   sharing unsafe; document that boundary instead of faking dedupe.
6. **Broadcast edits after one world mutation.** The acting Play task applies the
   edit once, then routes block and light deltas to all current subscribers. Only
   the actor receives the block-change acknowledgement.
7. **Prefer bounded stale-result drops over cancellation.** Movement and
   disconnect cleanup must reject stale worker results before socket writes,
   loaded-set insertion, ticket resurrection, or `LightCache` pollution.

## Target flow

```text
connection enters Play -> register session -> acquire view tickets -> workers prepare
chunk result -> shared ready state or per-session command -> Play task writes + caches

movement -> diff old/new view -> acquire new tickets + send center -> unload old-only
chunks -> reject stale completions for dropped subscriptions

block edit -> mutate world + relight -> find subscribers -> actor ack + everyone gets
block/light deltas through their own Play task

disconnect -> unregister session -> release all tickets -> drop queued commands
```

## Sub-milestone decomposition

### M15.a - Plan

Add this milestone document only. Confirm the branch starts from `main` at tag
`m14`, then commit the plan before code.

### M15.b - Chunk unload protocol oracle

Verify the clientbound Play chunk-unload packet ID and layout from the protocol
oracle. Add the minimal `mc-protocol` packet type only after the oracle pins the
wire ID and body encoding.

Acceptance for this slice:

- The packet ID, vanilla metadata name, and field order are cited from the oracle
  in code comments or commit body.
- If the body uses a packed position, the exact encoding path is verified before
  tests pin bytes.
- No player-list, entity, or tablist packet is added unless M15 proves it is
  required and verifies it first.

### M15.c - Play session registry and outbound commands

Introduce a small server-owned registry of active Play sessions. Each session
should have a stable internal id, profile identity, current chunk center, view
distance, subscription/loaded sets, and a bounded outbound command channel owned
by that connection's Play task.

The first command surface should cover only what M15 needs: prepared chunk send,
unload, block delta, light delta, and cleanup. Avoid plugin-style events or a
general-purpose command bus.

### M15.d - Global chunk ticket graph

Add a shared chunk ticket map keyed by `ChunkPos` with subscriber sets and ref
counts. View acquisition should add the player to each desired chunk; movement
and disconnect should release only that player's tickets.

Important constraints:

- A chunk remains globally ticketed while any player still subscribes.
- Per-player loaded/subscribed state remains separate from the global ref count.
- Logs or metrics should expose requested chunks, subscribers, and shared hits or
  reuse opportunities.

### M15.e - Shared preparation boundary

Route chunk preparation through the ticket graph so overlapping views do not
blindly enqueue duplicate load/generate/light/encode work when a current prepared
result can serve multiple subscribers.

The implementation may keep final framing or compression per connection if the
existing pipeline makes that the safe boundary. The milestone should still make
the sharing decision explicit in code and logs.

### M15.f - Verified unload lifecycle

When movement removes chunks from one player's view, send the verified unload
packet for chunks that were actually loaded for that player and are no longer in
that player's desired set. Release that player's tickets and clear the relevant
per-connection loaded/cache state without affecting other subscribers.

This slice must handle rapid movement and stale worker results: a prepared result
for an old subscription must not re-load a just-unloaded chunk or resurrect a
released ticket.

### M15.g - Subscriber block-edit broadcast

Change break/place handling from actor-only updates to subscriber broadcasts.
After applying the world mutation and relight once, route `BlockUpdate` or
`SectionBlocksUpdate` plus any relevant `LightUpdate` packets to every active
session subscribed to the affected chunks.

The actor still receives `BlockChangedAck`; observers do not. Each recipient's
Play task updates its own `LightCache` consistently with the light packets it
writes.

### M15.h - Backpressure and disconnect cleanup

Bound outbound command queues and define disconnect behavior. Disconnecting or
rapidly moving players must release tickets, unregister subscribers, drop stale
queued commands, and avoid leaking prepared results or keeping chunks globally
ticketed with an empty subscriber set.

### M15.i - Harness, validation, and closeout

Add two-client wire-level coverage and close out with the standard gates:

```sh
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

Manual gate: run the debug server with `example.toml`; the owner connects two
PrismLauncher 26.1.2 clients, walks them apart/together, breaks and places a

## Acceptance criteria

1. Start point is `main` at tag `m14`; any pre-existing local config diff is not
   included in M15 commits.
2. Clientbound chunk unload ID and layout are verified by oracle before code.
3. Two clients can connect concurrently and receive their own Play login,
   position sync, center chunk, inventory seed, keepalive, and chunk stream.
4. Overlapping views share chunk tickets/preparation where the implementation
   boundary permits it; logs or metrics expose requested, subscriber, and shared
   counts.
5. Moving one client across a chunk boundary updates only that client's center,
   sends unloads for chunks leaving that client's view, and keeps the other
   client's view stable.
6. Disconnect releases that player's tickets and leaves no stale subscribers or
   empty ticket entries.
7. A block edit by client A is visible to client B when B subscribes to the
   affected chunk, including light updates when relight changes.
8. The actor receives the edit acknowledgement; observers do not.
9. Existing one-client movement, block-edit, persistence, and incremental-relight
   harness tests remain green.
10. No global gameplay systems sneak in: no AI, mobs, redstone, fluids, survival
    timing, plugin API, or entity tracker beyond what the ticket/view lifecycle
    requires.
11. `cargo test --workspace` is green.
12. `cargo clippy --workspace --all-targets -- -D warnings` is clean.
13. `cargo fmt --all -- --check` is clean.

## Harness plan

- Two clients connect with a small configured view distance and both receive the
  expected initial chunks without one connection starving the other.
- Client A crosses a chunk boundary while client B stays still; A receives
  `SetCenterChunk`, new chunks, and verified unloads for old-only chunks, while B
  receives no center update caused by A.
- Client A edits a block in a chunk visible to B; A receives the acknowledgement
  and both clients receive the matching block delta. If the edit changes light,
  both subscribed clients receive the relevant light update.
- A disconnect after initial subscription releases tickets; follow-up movement or
  chunk completion does not route commands to the dropped session.

## Out of scope

- Entity visibility/tracking, player-list polish, tablist, skins, or nameplates
  unless the vanilla client proves a minimal packet is required for connection
  stability.
- Full gameplay systems: mobs, AI, combat, survival mining timing, tool damage,
  redstone, fluids, or block physics.
- Folia-style region ownership or a general region scheduler.
- Plugin API, scripting, event bus, or public extension hooks.
- Disk-persistent light arrays.
- Vanilla algorithm ports.

## Pitfalls

- **Guessed unload protocol.** The unload packet must be oracle-pinned before it
  appears in code or tests.
- **Writer ownership leaks.** Cross-player broadcasts must not write to another
  connection's socket directly or mutate its `LightCache` off-task.
- **State collapse.** Desired, loaded, prepared, and globally ticketed chunks have
  different lifetimes; merging them risks unload flaps and stale cache writes.
- **Duplicate expensive work.** Overlapping views should not schedule identical
  preparation forever when a valid prepared result can serve both subscribers.
- **Deadlocks under locks.** Do not hold world/session/ticket locks across awaits
  or socket writes.
- **Disconnect leaks.** Bounded queues and subscriber maps must be cleaned when a
  Play task exits.
- **Fake multiplayer tests.** Two-client tests must use real harness clients and
  real server packets, not manufactured packet facts.

## Status / validation appendix

- Clientbound chunk unload is verified against `.analysis/protocol-dump.txt` and
  `javap`: `CLIENTBOUND_FORGET_LEVEL_CHUNK` is game-CB index 37, wire id `0x25`.
  The body is `FriendlyByteBuf.writeChunkPos`, one raw `i64` from
  `ChunkPos.pack(x, z) = (x & 0xffffffff) | ((z & 0xffffffff) << 32)`.
- `mc-net` now owns a server-wide Play session registry per `BoundServer`.
  Sessions track current center, view distance, desired chunks, loaded chunks,
  outbound command channel, and chunk-ticket subscriber sets.
- Socket writes remain Play-task-owned. Cross-player block/light broadcasts are
  routed through bounded per-session outbound channels; recipient tasks update
  their own `LightCache` before writing light packets.
- Movement replans diff the loaded set against the new desired view, send
  verified `ForgetLevelChunk` packets for old-only loaded chunks, release that
  player's tickets, and clear per-connection light cache entries without
  touching other subscribers.
- Prepared chunk frames are cached globally while at least one ticket remains for
  the chunk. Overlapping views can reuse a prepared result instead of repeating
  load/generate/light/encode work after the first preparation. Cache entries are
  removed when the last ticket releases and invalidated on block/light edits.
- Block edits mutate the world once. The actor gets block/light deltas directly
  followed by `BlockChangedAck`; other loaded subscribers receive matching
  block/light deltas through their outbound queues and do not receive the ack.
