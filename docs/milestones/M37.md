# M37 - Performance and scale

**Status:** plan on `dev/M37-performance-scale` from local M36 head
`3da5624` (`feat: M36 multiplayer hardening`). Local tag `m36` was not present
when this branch was created.
**Owning crates:** `mc-server` for runtime wiring and config, `mc-net` for
session/network pressure and packet batching, `mc-world` for storage/chunk/light
hot paths, `mc-worldgen` for generation cost visibility, and
`mc-test-harness` for load-oriented scenarios.

## Goal

Keep the expanded survival server usable under real load by adding explicit
measurements, budgets, batching, and targeted optimizations.

M37 is not a rewrite of the server architecture and is not the M39 lock-free
pass. The target is to make current costs visible, stop any one subsystem from
monopolizing ticks, and tighten the most obvious measured hot paths without
sacrificing correctness.

## Current Foundation

- M36 hardened multi-player lifecycle, admission, reconnect, shared pickup, and
  container mutation ordering.
- The project still uses debug builds for the dev loop; performance claims must
  be measured on real server paths rather than synthetic fixtures.
- M39 remains reserved for broad lock mitigation. M37 may expose lock pressure
  through metrics, but should avoid turning into a global ownership rewrite.
- Local-only files under `.serena/`, `work/`, `YOLO_MODE.md`, `opencode.json`,
  `.analysis/`, `data/vanilla/`, and manual config/tool edits remain outside the
  milestone unless explicitly requested.

## Strategy

1. Add low-overhead debug metrics around existing runtime boundaries before
   optimizing anything.
2. Measure real hot paths with focused tests, benches, harness scenarios, or
   debug logs that exercise the same code used by a client session.
3. Add configurable budgets where work can naturally spill across ticks without
   changing gameplay correctness.
4. Batch network and world-update work only where protocol ordering and
   per-viewer state remain correct.
5. Optimize storage and generation paths based on observed pressure, preferring
   small data-structure or scheduling fixes over broad rewrites.
6. Close out with raw enough numbers to verify before/after claims.

### M37.c - Load and benchmark harness

Add focused load scenarios that drive real code paths.

Acceptance:

- Scenarios cover at least spawn/login, exploration, block edit storms, fluid or
  scheduled-tick pressure, entity crowds, and multiple clients where feasible.
- Each scenario reports elapsed time and enough counts to compare future runs.
- Harnesses avoid manufactured world state that bypasses the subsystem being
  measured.

### M37.d - Simulation budgets

Cap work that can be fairly deferred across ticks.

Acceptance:

- Configurable budgets exist for at least two high-pressure categories such as
  scheduled block/fluid ticks, entity AI, chunk sends, or save flushes.
- Backlog processing is fair enough that old work does not starve behind new
  work.
- Logs expose budget overruns and backlog size when pressure persists.
- Gameplay correctness is preserved; deferred work must reschedule rather than
  disappear.

### M37.e - Packet and broadcast batching

Reduce avoidable packet-write pressure without breaking per-viewer correctness.

Acceptance:

- Block/entity/container updates are batched where the vanilla protocol and
  current viewer state make that safe.
- Ordering-sensitive packets remain ordered, and tests assert from the receiving
  clients' streams.
- Batching preserves packet ids, container ids, entity ids, positions, and
  visibility rules per viewer.

### M37.f - Storage and generation hot-path tightening

Acceptance:

- Improvements are either landed with before/after numbers or explicitly

- Region cache, dirty flush, player/entity save, generated chunk, and light paths

### M37.g - Config policies

Acceptance:

## Risks / Pitfalls

- Performance logs without raw counts can become unverifiable anecdotes.
- Synthetic benchmarks can reward code paths that real clients never use.
- Budgeting can create invisible gameplay bugs if deferred work is dropped or
  reordered incorrectly.
- Packet batching is protocol-sensitive; correctness beats fewer writes.
- M37 should expose global lock pressure but leave broad lock replacement to M39.

## M37 Implementation Notes

Initial metrics slice:

- Added a runtime metrics policy with hard-coded debug defaults for now: log every
  100 entity/simulation ticks and warn when a tick takes at least 50 ms. Config
  wiring remains in M37.g so this first slice does not force fixture churn across
  existing tests.
- The entity/simulation loop now measures world-time advancement, entity goal
  tick, entity physics, entity dispatch, persisted entity/world-metadata save,
  random ticks, scheduled fluid ticks, and total tick duration.
- Runtime logs include pressure counts for active sessions, ticketed chunks,
  prepared chunks, server entities, and open furnace/chest viewer sets.
- Random tick and scheduled fluid tick runners now return real counters instead
  of only logging internally, so future load harnesses can compare work done per
  tick without bypassing production paths.
- Scheduled fluid ticks now use the normalized simulation budget from config
  instead of a hard-coded per-tick cap. Runtime metrics include the active fluid
  budget and whether it was exhausted, and pressure logs warn when due fluid work
  spills into a later tick instead of being dropped.
- `[simulation].scheduled_fluid_tick_budget` joins the existing
  `random_tick_chunk_budget` as a second configurable deferred-work limit. Zero
  values normalize to one at the runtime boundary to preserve correctness.
- Outbound play-session block-delta and light-update commands now coalesce only
  adjacent same-kind commands before writing to the socket. The first different
  command is retained in a local pending queue, preserving ordering-sensitive
  entity/container/player packets while reducing avoidable write pressure during
  edit and relight bursts.
- `mc-world` exposes `WorldStorageStats` and save-all logs chunk-cache,
  region-cache, dirty-count, and flush elapsed pressure. Dirty flush now reuses
  already-decoded region-cache payloads when available instead of re-reading the
  same `.mca` before rewriting dirty chunks.
- M37 load scenarios live in
  `crates/mc-test-harness/tests/load_scenarios.rs` and are ignored by default
  because they are timing/report probes. They drive real login/config/play,
  chunk streaming, movement, creative block placement, entity summon visibility,
  and four-client pressure against an in-process server.
- Config policies now cover view distance, simulation distance as a parsed
  operator knob, worker percentages, chunk queue/cache limits, compression
  threshold and compression level, random tick chunk budget, scheduled fluid tick
  budget, and save interval ticks. Runtime simulation remains ticket/view-driven;
  a separate simulation-radius ownership model is left as a future architecture
  pass rather than hidden in M37.

Closeout notes:

- M37 intentionally did not replace broad shared locks; the metrics now make
  pressure visible, and M39 remains the lock-free ownership pass.
- Packet batching is limited to block/light update commands because those are
  already semantically unordered within a same-tick world-delta burst. Container,
  entity, and player visibility packets remain explicitly ordered.
- Storage tightening is conservative: it removes an avoidable decoded-region
  reread on dirty flush when the region cache already holds payloads, while
  preserving the existing atomic rewrite path.
