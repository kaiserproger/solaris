# M39 - Lock-free server hardening

**Status:** plan draft on `dev/M37-performance-scale` from local M38 head
`6d5add5` (`feat: M38 compatibility polish`). The expected reviewed `m38` tag
and `dev/M39-lock-free-hardening` branch were not present locally when this
document was written.
**Owning crates:** `mc-net` for session ownership, play-state lock boundaries,
save/admin routing, and runtime metrics; `mc-world` for storage snapshot/flush
boundaries; `mc-test-harness` for buffered frame helpers and race-oriented
coverage; `mc-server` only where runtime wiring is required.

## Goal

Remove or narrow the server's hot global locks so interactive play, chunk
streaming, command dispatch, `save-all`, and shutdown do not hold shared mutexes
across disk I/O, world generation, packet writes, command execution, or long
player/session scans.

M39 is not a new gameplay milestone and not a broad async/runtime rewrite. The
target is a practical ownership pass: identify the long-held locks that can stall
the scoped replacement server, replace them with snapshots, queues, sharded
ownership, or bounded per-resource locks, and leave only locks whose hold time is
small and observable.

## Current Foundation

- M35 added operational `/save-all` and `/stop`; its closeout reserved server-wide
  lock mitigation for M39.
- M36 hardened multiplayer ordering without hiding races behind broader mutexes.
- M37 added metrics, budgets, conservative packet batching, and storage pressure
  logs, but intentionally left the global ownership model unchanged.
- M38 completed compatibility polish and kept M39 as the remaining readiness risk.
- Current hotspots include `WorldHandle = Arc<tokio::sync::Mutex<WorldStorage>>`,
  the monolithic `SessionRegistry` mutex, nested player persistence locks, dirty
  chunk flushes that rewrite region files, and harness drains that can consume
  frames later needed by race assertions.
- Existing local-only worktree changes (`example.toml`, `tools/*`, `.serena/`,
  `YOLO_MODE.md`, `log.log`, `opencode.json`) are outside M39 unless the owner
  explicitly pulls them in.

## Strategy

1. Measure and document lock boundaries first; do not replace locks blindly.
2. Move expensive work outside locks before introducing new abstractions.
3. Prefer immutable snapshots, narrow mutation commits, queues, and per-chunk or
   per-session ownership over replacing every mutex with a different primitive.
4. Keep protocol ordering and authoritative mutation semantics from M36 intact.
5. Add tests around real server paths changed by the ownership pass; avoid tests
   that only assert manufactured data structures.
6. Close out with before/after lock-hold evidence and any remaining justified
   locks.

### M39.b - Lock timing and ownership inventory

Acceptance:

- Metrics can report hold or wait pressure for the world storage lock, session
  registry lock, save-all flush path, chunk prepare/commit path, and selected

### M39.c - World storage lock narrowing

Restructure `WorldStorage` usage so disk I/O, region rewrites, chunk generation,
and long sampling work are not performed while the shared world mutex is held.

Acceptance:

- Chunk read/prepare paths can clone or build an immutable chunk snapshot outside
  the global storage critical section where correctness allows it.
- Generated chunks are prepared outside the storage lock and committed with a
  short validation/mutation step.
- Dirty chunk flush creates a bounded flush plan or payload snapshot under the
  storage lock, writes region files outside that lock, then commits clean/dirty
  state only after successful writes.
- Eviction of dirty chunks cannot synchronously rewrite region files while holding
  the global storage lock for unrelated readers.
- Existing persistence tests still prove block edits, block entities, scheduled
  ticks, player data, entities, and world metadata survive restart.

### M39.d - Chunk streaming and simulation snapshots

Keep chunk streaming, lighting preparation, entity physics sampling, and scheduled
simulation work from monopolizing the shared world handle.

Acceptance:

- Chunk streaming requests use snapshots or prepare jobs instead of repeatedly
  taking the world lock for each expensive stage.
- Entity physics and collision sampling never load/generate chunks while holding
  a shared server lock; missing samples degrade through the existing safe fallback.
- Scheduled block/fluid tick draining uses bounded per-tick work without scanning
  unrelated loaded chunks under one long lock.
- Metrics show chunk/simulation backlog and lock pressure separately, so a slow
  generator is distinguishable from lock contention.
- Focused tests cover exploration/chunk streaming and scheduled tick behavior
  through the real play path.

### M39.e - Session registry and player state snapshots

Split long session scans and nested player persistence access away from the
monolithic session registry critical section.

Acceptance:

- Broadcast, visibility, container viewer, entity snapshot, and persistence reads
  collect small immutable dispatch plans under the registry lock, then send or
  perform expensive work after releasing it.
- Nested locks between `SessionRegistry` and `PlayerPersistedState` are ordered or
  removed so save, disconnect, death/respawn, and command mutations cannot form a
  lock-order hazard.
- Session lifecycle cleanup remains idempotent for disconnect, kick, shutdown,
  duplicate profile admission, and reconnect.
- Multi-client tests still prove shared block edits, container updates, pickups,
  command feedback, and player visibility are per-viewer correct.

### M39.f - Save, shutdown, and admin command hardening

Make operational paths bounded and non-blocking from the perspective of active
play sessions.

Acceptance:

- `/save-all`, console save, Ctrl-C, and `/stop` share one bounded save pipeline
  instead of directly performing all persistence under hot locks.
- Save reports still include players saved, entities saved, chunks flushed, world
  metadata status, and errors.
- A slow chunk flush or playerdata write does not block command dispatch,
  keepalive handling, chunk streaming, or unrelated player packets longer than the
  documented critical section budget.
- Shutdown waits for an explicit bounded persistence phase and then tears down
  sessions cleanly without leaking viewer/container registrations.
- Tests cover save request routing and shutdown signaling without terminating the
  test process.

### M39.g - Harness frame buffering for race tests

Replace ad-hoc raw drains where they can hide or create races in M39 validation.

Acceptance:

- `mc_test_harness::client::Client` or test support exposes buffered frame helpers
  that can wait for packet ids without discarding unrelated frames needed later.
- Existing chunk, block edit, command, mob, persistence, and multiplayer tests are
  migrated only where raw drains intersect M39 lock/race validation.
- Buffered helpers preserve packet order for later assertions and keep timeouts
  explicit.
- Tests continue to speak the real TCP protocol; no in-memory shortcut replaces
  wire-level coverage.

### M39.h - Regression and load validation

Prove that lock narrowing did not weaken the replacement server behavior shipped
through M38.

Acceptance:

- Focused tests cover at least chunk streaming under exploration, concurrent block

- The ignored M37 load scenarios still compile and can report lock pressure when

- Before/after notes include enough raw timing or counter data to justify each

- Any remaining global lock is listed with why it is safe enough to keep.

## Risks / Pitfalls

- Moving work outside locks can introduce stale snapshot bugs. Every commit phase
  must validate that the target chunk/session/entity still matches the expected
  version or state.
- Async tasks can hide ordering bugs if mutation results race with authoritative
  tick-thread state. Queue ordering must stay explicit.
- Lock-free is a direction, not a slogan. A small per-resource lock may be safer
  than a complicated actor graph with unclear failure modes.
- Save pipelines can report success too early if dirty state is marked clean
  before disk writes complete.
- Harness buffering can accidentally mask protocol ordering bugs if helpers match
  packets too broadly.
- Instrumentation can become its own performance problem if it allocates or logs
  per packet, per block, or per entity.

  session registry, save-all dirty flush, chunk prepare, and player persistence
  locks.

  do not log local world paths, player secrets, or packet bodies.

  sampling, bind/save-all root lookup, save-all dirty flush, chunk prepare
