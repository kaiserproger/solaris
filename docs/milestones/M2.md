# M2 — World representation

**Status:** code-complete on `dev/M2-world-representation`. All
seven acceptance criteria are met, including the round-trip oracle:
loading every chunk in a real vanilla 26.1.2 region file, re-encoding
it, decoding it again, and asserting block states, biomes,
heightmaps, and block-entity NBT all match between the two decoded
copies. 151 workspace tests, clippy + fmt green, no `unsafe`.
**Estimate:** 80–120 h (PROJECT_SPEC §9 Phase 1).
**Owning crate:** `mc-world` (currently a placeholder). Tooling
extensions touch `mc-data` (block registry loader) and
`tools/extract-vanilla-data.sh` (additional inputs).

## Goal

Stand up the in-memory and on-disk world model the server will use
from M3 onward: a global block-state registry, a palette-based chunk
representation, and an Anvil-compatible region-file codec. By the end
of M2 we can open a vanilla-generated `.mca` file, parse every chunk
section into our types, walk it via the public API, write it back out,
and observe a semantically equivalent round-trip — but nothing in
`mc-server` is yet wired to *use* this (no chunk packets, no
worldgen). That is M3.

This milestone is library work, not protocol work. The acceptance
oracle is a vanilla `.mca`, not a vanilla client.

## Strategy

Same posture as M1 (PROJECT_SPEC §8.1, ADR 0001, ADR 0002):

- We do **not** copy Mojang source or Mojmap-informed naming into our
  code.
- Mojang's data files in `data/vanilla/` are runtime input only —
  block-state IDs come from a generated report we extract locally
  from the same `server.jar` M1 already uses, not from hand-authored
  tables.
- The Anvil format is documented publicly (`minecraft.wiki`,
  `wiki.vg`); we work from those docs, then verify against real `.mca`
  files produced by the bundled vanilla server.
- NBT for disk uses the *Java standard* (named-root) flavour. Our
  `mc-nbt` already exposes `read_named` / `write_named` (M1.f); no
  protocol-NBT changes here.

## Reference sources (read-only oracles)

- `minecraft.wiki` "Anvil file format" and "Chunk format" pages.
- `minecraft.wiki` "Block states" and "Java Edition data values".
- The bundled vanilla `26.1.2` server in `.analysis/server.jar` —
  used to *generate* the block-state report (`--reports`) and to
  *produce* baseline `.mca` files we can diff against. We do not
  decompile it.
- Our own M1 tooling: `wire-probe` may incidentally help in M3 when
  chunks go on the wire, but is not needed for M2.

## Sub-milestone decomposition

Implemented as small, individually committable chunks so the diff
stays reviewable. Tentative ordering — may be reshuffled as we
discover dependencies.

### M2.a — extract block-state report

Extend `tools/extract-vanilla-data.sh` (or add a sibling script) to
run `java -jar .analysis/server.jar --reports` once and copy the two
artefacts we need out of `generated/reports/`:

- `blocks.json` — the canonical mapping
  `block-id → { properties: { name: [values…] }, states: [ { properties, id, default? } ] }`.
- `registries.json` — clientbound registry IDs we may want later for
  cross-checks.

These join the existing `data/vanilla/` sidecar, still git-ignored.
The extraction script's output stays deterministic for a given
`server.jar`. Update `data/vanilla/README.md` to list the new files.

Out of scope here: pulling the full `generated/data/` tree or
worldgen JSON — only what M2 needs.

### M2.b — block + block-state types in `mc-world`

Public surface (under `mc_world::block`):

- `BlockStateId(u32)` newtype. Vanilla's protocol-level ID is a
  `VarInt`; we keep `u32` in memory and convert at the codec
  boundary. Document the stability requirement: the same
  `server.jar` ↔ same ID mapping; we do not invent our own numbering.
- `Block` — a registered block kind, identified by `Identifier`
  (`minecraft:stone`), carrying its property definitions
  (`name → ordered values`). Default state ID, full state list.
- `BlockState` — a single concrete state: `Arc<Block>` + a small
  property-value vector. Equality by `BlockStateId` once registered.
- `BlockRegistry` — built from `blocks.json` at startup, exposes
  `by_id(BlockStateId) -> &BlockState` and
  `by_name_and_props(&Identifier, &[(name, value)]) -> Option<BlockStateId>`.
  Frozen after construction.

Construction lives in `mc-data` (alongside the registry indexer from
M1.f) so `mc-world` does not depend on filesystem IO. `mc-world`
takes a built `BlockRegistry` by `Arc`.

Tests: load the real `blocks.json` from `data/vanilla/`, count blocks
and total states, assert known cardinals (e.g. air = state 0,
specific stone variants), proptest `by_id` ↔ `by_name_and_props`
round-trip.

### M2.c — palette + chunk section

A chunk section is `16×16×16` block states. Storage:

- `Palette` — small inline vector of `BlockStateId`s. Single-value
  optimisation when the whole section is one state (very common for
  air or stone). Grow into a `HashMap`-backed indirect mode when the
  palette exceeds a threshold (per vanilla's heuristic — pick the
  cutoff after measuring).
- `PackedBitArray` — bit-packed indices into the palette, bit-width
  matching `ceil(log2(palette.len()))`, recomputed on grow.
- `ChunkSection { palette, indices, block_count }` — `block_count`
  cached for the "is this section all air?" fast path vanilla also
  uses.

Public ops: `get(x,y,z) -> BlockStateId`, `set(x,y,z, id) -> old`,
iterators. SoA experiment deferred — start AoS, profile in M21.

Tests: round-trip random sets, palette grow/shrink boundary cases,
proptest invariant that `block_count` matches a linear scan.

### M2.d — chunk + heightmaps + biome storage

`Chunk` aggregates 24 sections (vanilla's `-64..320` Y range, 24×16),
plus per-chunk side data:

- `ChunkPos(i32, i32)`.
- Sections: `[ChunkSection; 24]` (or `Box<[…; 24]>` if stack pressure
  matters).
- `Heightmaps` — `MOTION_BLOCKING`, `WORLD_SURFACE`, etc. Same
  packed-bit storage as palette indices. Recomputed lazily.
- `Biomes` — per-section biome palette, 4×4×4 resolution (vanilla
  packs biomes coarser than blocks). Same palette machinery as
  blocks, indexed by a small biome-registry id from `mc-data`.
- Block entities — `HashMap<BlockPos, BlockEntityNbt>`. We store raw
  NBT here for M2; typed block-entity structs come when an actual
  consumer (M3+) needs them.

No worldgen here. Construct empty/test chunks programmatically.

### M2.e — Anvil region-file codec

Read + write `.mca` files (`region/r.X.Z.mca`):

- 4096-byte sector layout, header tables for chunk offsets and
  timestamps, per-chunk compressed NBT payload (gzip / zlib /
  uncompressed / LZ4 — vanilla actually emits zlib by default;
  support read for all four, write only zlib).
- Use `mc_nbt::read_named` / `write_named` for the inner payload.
- Map the NBT chunk tag onto our `Chunk`:
  `Level → sections[].block_states.palette/data`, biomes, heightmaps,
  block entities, `Status`, `xPos`/`zPos`/`yPos`.

Acceptance test: take a real `.mca` from a vanilla world we generate
under `.analysis/` (one-time, scripted), decode every chunk, re-encode
it, and assert:

1. Every `BlockStateId` survives the round-trip identically.
2. Heightmaps recomputed from the decoded chunk match the input
   heightmaps. (Catches bit-packing bugs.)
3. Block-entity NBT round-trips byte-identically.
4. Re-encoded region file is structurally valid: header offsets
   land on real sector boundaries, decoded a second time yields the
   same `Chunk`.

We do **not** require byte-for-byte file equality with vanilla —
zlib compression level, palette ordering, and free-sector packing
are non-canonical. Semantic equivalence is the bar.

### M2.f — minimal world-storage façade

Just enough to glue regions into a queryable world:

- `WorldStorage` — opens a world directory, lazy-loads regions on
  demand, evicts under a small LRU. Read-only in M2; write-back is
  M3 when modifications start happening.
- `World::get_block(BlockPos) -> Option<BlockStateId>` — the API
  M3's chunk-packet emitter will call.
- Errors surface via `thiserror`; no panics on malformed input.

Tests: open `.analysis/test-world/`, read a known column, assert
expected blocks at known coordinates.

### M2.g — wire-up in `mc-server` (smoke only)

The binary does not yet *send* chunks (M3), but on startup it should
construct the block registry and a `WorldStorage` rooted at a
configured path, fail loudly if either is broken, and log totals
(block count, world directory, region file count). This catches the
"data/vanilla is missing" and "world path is wrong" failures at
startup rather than first chunk request.

Extend `[server]` config with `world_dir: PathBuf`. Default behaviour
when the directory is empty / missing: server still starts, logs a
warning, `World::get_block` returns `None` everywhere. This keeps
M1-style "empty world" behaviour intact until M3 hooks up streaming.

## Out of scope (recorded so it does not creep)

- Sending chunk data over the wire — M3.
- Worldgen, biome generation, structure placement — M4–M6.
- Typed block entities (chests, signs, …) — added as their consumers
  appear, not in M2.
- Lighting (block + sky light) — protocol requires it from M3 when we
  start sending chunks; M2 stores the bytes if vanilla put them in
  the file but does not propagate.
- Tick scheduling / random ticks / fluid flow — `mc-physics`, later.
- Modifications, save-back, journaling — M3.
- ECS integration — M2 deliberately does not touch `bevy_ecs`. The
  world lives outside ECS per PROJECT_SPEC §3.3.

## Open questions to resolve along the way

- **Section Y range stability.** Vanilla currently uses `-64..320`
  (24 sections). Hard-coding the constant in M2 is acceptable; if
  the Overworld dimension type ever advertises a different range we
  re-shape. Note the assumption in code with a `// TODO(M5):` if we
  later support custom dimensions.
- **Palette growth threshold.** Vanilla uses 4-bit indices when the
  palette ≤ 16, then 5..8 bit, then global-palette ("direct") when
  exceeding 8. We mirror this; confirm exact cutoff via a sample
  scan over a generated region.
- **Block-entity decode strategy.** Store opaque NBT in M2 (above) or
  decode-on-load into typed structs. Decision: opaque now, typed
  when M3 needs the data. Costs: one extra parse per access in M3,
  but the API stays unblocked.
- **LZ4 read path.** Vanilla supports it as a compression option for
  region payloads; rarely emitted by default. Decide whether to pull
  in the `lz4_flex` crate or skip and error cleanly until needed.

## Pitfalls (carry-over from M1 review)

- `tools/extract-vanilla-data.sh` does NOT currently produce the
  block-state report. M2.a adds it. Do **not** start M2.b before
  that lands or you will hand-author what should be generated.
- Anvil NBT uses *Java standard* named-root NBT; do not reach for the
  Network-NBT path (`read_unnamed` / `write_unnamed`) we use in
  protocol packets — it will look correct on small chunks and break
  on real ones.
- Block-state IDs must be stable across server restarts and across
  hosts running the same `server.jar`. The mapping is the report's,
  not ours — never sort or renumber.
- Heightmap bit-packing in Anvil packs 9 bits per entry across
  `i64[]` *without* crossing element boundaries (per the wiki). Easy
  to get subtly wrong; have a focused unit test before tackling a
  full chunk.

## Open follow-ups (handed to M3)

- **Region-level read cache.** `WorldStorage::ensure_chunk` currently
  re-reads the entire `.mca` for every cache-miss; loading 32 chunks
  out of one region therefore re-decompresses 32 times. A region-
  level payload cache (keyed by `(rx, rz)`) eliminates that and is
  the most obvious M3 perf win once chunks start flowing on the
  wire.
- **Lossy chunk fields.** Decode currently drops `structures`,
  `block_ticks`, `fluid_ticks`, `PostProcessing`, per-section
  `SkyLight` / `BlockLight`, `InhabitedTime`, `LastUpdate`,
  `DataVersion`. Round-trip still works because we only require
  the modelled subset to survive, but writing a chunk and feeding
  it back to vanilla would lose game-state continuity. M3 introduces
  an `extras` channel (opaque NBT) so the chunk's full content
  passes through.
- **Direct mode.** Section storage caps growth via `set()` at 8-bit
  indirect; vanilla 1.18+ always uses an indirect palette, so the
  cap is fine on the read/write path we have, but the section type
  cannot grow past 256 distinct states via post-load mutation
  (relevant when M3 starts modifying chunks).
- **LZ4 read path.** Vanilla rarely emits it but the option exists.
  Currently we return `RegionError::Lz4Unsupported`; pulling in
  `lz4_flex` is a one-line change when a real chunk shows up.
- **Heightmap recompute.** We preserve the on-disk heightmap but do
  not regenerate it from block data. M3 needs this when modifications
  start happening.
