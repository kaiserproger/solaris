# M26 - Block simulation ticks and interactions

**Status:** in progress on `dev/M26-block-simulation` from `main` at local tag
`m25`; M26.a-M26.h have landed locally.
**Owning crates:** `mc-world` for scheduled tick storage and Anvil round-trip,
`mc-data` for block behavior facts, `mc-net` for the world-owned tick driver,
edit broadcast, and interaction paths, and `mc-test-harness` for survival-visible
wire tests.

## Goal

Add the first real block-simulation backbone: deterministic scheduled block
ticks, random ticks for active chunks, and a small set of common survival block
interactions. M26 is not a redstone milestone. It should create reusable seams
for later fluids/redstone work while landing visible crops, farmland, simple
natural updates, and common toggle blocks.

The focused win is a world-owned simulation path that can mutate blocks outside a
single player click, mark chunks dirty, invalidate prepared chunk caches, relight
affected areas once, and broadcast client-visible block updates to subscribers.

## Strategy

1. Model scheduled ticks in `mc-world` before gameplay consumes them. Today
   `block_ticks` and `fluid_ticks` survive only as opaque Anvil extras; M26 must
   decode the verified block tick shape before rewriting those root keys.
2. Extract a batch block-edit backend from the current single-cell player edit
   path. Simulation, support cascades, two-block doors, and random ticks need one
   mutation transaction followed by one cache invalidation, relight, and broadcast
   pass.
3. Keep behavior facts data-backed where practical. Prefer sidecar reports,
   tags, and repo-owned fallback fixtures over new string arrays in `mc-net`.
4. Implement independent approximations for simulation behavior. Use vanilla
   oracles to verify data and storage shapes, not to copy decompiled algorithms.
5. Scope interactions narrowly and record gaps. Simple toggles and survival block
   updates are in; broad redstone propagation, piston behavior, comparator logic,
   and fluid parity are out.

## Risks / Pitfalls

- The exact `block_ticks` NBT shape and tick-time semantics must be verified
  before modeling. If M26 cannot verify them quickly, keep tick persistence
  narrow and do not destroy opaque data.
- Current block mutation, relight, ack, and broadcast logic is centered on one
  player edit. Extracting it too broadly risks regressions; preserve the existing
  single-edit tests while adding batch coverage.
- Random tick behavior can sprawl into vanilla parity. M26 should prefer stable,
  playable approximations over copying exact vanilla odds or algorithms.
- Interaction handling can become redstone by stealth. Only visible state toggles
  needed for survival interactions are in scope.
- Block facts should not recreate the pre-M25 problem with hardcoded arrays in
  `mc-net`; repo-owned fallback data belongs in `mc-data`.

## Oracle Notes

M26.c verified the scheduled tick storage shape from local 26.1.2 metadata:

- Source: `javap -c -p net.minecraft.world.ticks.SavedTick` against
  `.analysis/extracted/META-INF/versions/26.1.2/server-26.1.2.jar`.
- Root key: `block_ticks`, a list of compounds.
- Entry fields: `i: String` block identifier, `x/y/z: Int` world position,
  `t: Int` saved delay, and `p: Int` priority.
- `SavedTick.unpack(long, long)` adds `delay` to the current tick, so Solaris
  stores runtime `trigger_tick` and writes `t = trigger_tick - current_tick`.
  The M26.c codec uses current tick `0`; the later simulation driver must pass
  the real save/load tick.
- `TickPriority` values are metadata-pinned as `EXTREMELY_HIGH=-3`,
  `VERY_HIGH=-2`, `HIGH=-1`, `NORMAL=0`, `LOW=1`, `VERY_LOW=2`,
  `EXTREMELY_LOW=3`.
- `fluid_ticks` uses the same metadata shape, but M26.c intentionally leaves it
  opaque in `Chunk::extras` until fluids are in scope.

M26.e keeps random tick eligibility in `mc-data` via `BlockFactsTable`, built
from the block report state ids with repo-owned classification for the first
families: crops, farmland, leaves, grass block, fire, and saplings. Runtime
sampling is deterministic from `(seed, world_tick, chunk, sample_index)`, scoped
to sorted ticketed chunks, and capped by `[simulation].random_tick_chunk_budget`.
M26.e only samples and filters eligible states; actual crop/fire/grass/leaves
mutations attach in M26.f/M26.g.

M26.f scopes crop/farmland simulation intentionally narrowly: wheat seeds place
`minecraft:wheat[age=0]` only on top-clicked farmland; wheat random ticks advance
one age at a time up to age 7; farmland random ticks hydrate to moisture 7 near
water, dry by one moisture step without water, and revert dry uncropped farmland
to dirt. Trampling is limited to a survival player landing transition that turns
the farmland block under the player's feet into dirt.

M26.g keeps natural ticks conservative: non-persistent leaves at `distance=7`
decay to air, grass blocks decay under opaque coverage or spread to the first
nearby dirt column with air/passable vegetation above, and fire increments age
until age 15 before extinguishing. Random-tick edits invalidate prepared chunks
and broadcast full recomputed light for touched chunks when the block-light table
is available.

M26.h covers visible non-redstone interaction only: right-click toggles `open`
or `powered` while preserving other state properties, doors toggle both halves
when the paired half is present, door placement writes lower+upper halves through
the batch path, and breaking either door half removes the other half.

## Scope Drift / Follow-ups

- Fluids remain out of scope unless the scheduled tick model needs opaque
  preservation fixes.
- Redstone propagation, pistons, comparators, observers, and wire power networks
  remain future milestones.
- Exact vanilla random-tick probabilities and full crop/fire parity remain future
  oracle-backed refinements.
- M26.f does not model vanilla crop growth probability, light checks, biome
  effects, or entity-weight-sensitive trampling odds; it lands deterministic
  visible behavior on the shared mutation path first.
- M26.g does not copy vanilla leaf-distance recomputation, exact grass/fire odds,
  rain checks, or flammability tables; those remain future data-backed refinements.
- M26.h does not propagate redstone power or schedule button/pressure-plate reset
  ticks yet; it only mutates the visible block state.
