# M61 - Sugar cane and cactus growth

**Status:** In progress; M61.a through M61.c landed. Branch:
`dev/M61-sugar-cane-cactus-growth`, stacked after local M60 closeout.
**Owning crates:** `mc-net` for random-tick growth planning, support checks,
multi-block edits, and focused tests; `mc-test-harness` for any stable survival
coverage that fits without new protocol claims; `docs` for readiness updates at
closeout.

## Goal

Make the existing survival support-block behavior for sugar cane and cactus more
useful by allowing planted columns to grow visibly over time.

M60 added deterministic multi-block plant growth for saplings through existing
block-edit paths. M61 applies the same replacement-readiness style to vertical
plants that already have support-break cascade behavior in Solaris: start with
small, local, registry-driven random-tick growth and keep vanilla RNG/effect
parity out of scope.

## Scope

- Add random-tick growth for `minecraft:sugar_cane` and `minecraft:cactus`.
- Grow only by placing one matching block above the top of a valid column.
- Cap generated columns at three blocks tall for the first slice.
- Require the block above the column to be air.
- Reuse the existing random-tick sample path, block-edit batch path, relight, and
  client block delta broadcasting.
- Resolve block states from the loaded block registry by namespaced id; do not
  hardcode numeric block state ids.
- Keep existing sugar cane/cactus support-break cascade behavior unchanged.

## Non-Goals

- Exact vanilla growth age counters, RNG probability, or tick-rate parity.
- Bonemeal support for sugar cane or cactus.
- Exact placement survivability parity beyond the existing local support checks.
- Growing above height three, interacting with neighbor-block updates beyond the
  existing cascade logic, or broad plant physics parity.
- Particles, sounds, statistics, advancements, game events, or level events.
- New packet IDs, packet layouts, entity metadata, or guessed client effects.

## Strategy

1. Extend the random-tick planner with an explicit vertical-plant branch for
   sugar cane and cactus after ordinary age-based crops stay unchanged.
2. For a sampled sugar cane or cactus block, find the bottom and top of its
   contiguous same-block column in loaded storage.
3. If the column height is already three or the block above the top is not air,
   return no edit.
4. If the sampled column is supported, place one matching plant block above the
   top through the existing block-edit path.
5. Keep the implementation deterministic and local. The random sampler decides
   when the plant gets a chance; the growth helper only decides whether the
   current sampled column can grow.
6. Add focused unit tests for sugar cane growth, cactus growth, max-height no-op,
   obstructed no-op, unsupported no-op, and preservation of existing cascade
   tests.
7. Add harness coverage only if a stable, non-flaky survival observation is cheap;
   otherwise document unit-only coverage at closeout.

## Sub-Milestones

### M61.a - Sugar cane random-tick growth

Acceptance:

- Random ticks can grow a clear supported sugar cane column from one to two and
  two to three blocks tall.
- Three-block sugar cane columns do not grow further.
- Obstructed or unsupported sugar cane columns do not mutate.
- Existing sugar cane support-break cascade behavior remains green.
- Focused tests pass.

Suggested focused gate:

```sh
cargo test -p mc-net sugar_cane -- --nocapture
cargo test -p mc-net random_tick -- --nocapture
```

Landed locally:

- Sugar cane random ticks can grow a supported clear column by one block up to
  height three.
- Samples from the bottom or middle of the column grow only above the top of the
  contiguous sugar cane column.
- Unsupported, obstructed, or max-height sugar cane columns remain no-ops.
- Existing random-tick age crop behavior remains the first branch and is
  unchanged.
- Focused gates passed: `cargo test -p mc-net sugar_cane -- --nocapture` and
  `cargo test -p mc-net random_tick -- --nocapture`.

### M61.c - Harness coverage decision

Acceptance:

- Either add a stable Solaris harness test for at least one vertical plant growth
  path, or explicitly document why focused unit coverage is the correct gate for
  M61.
- If added, the harness must observe server-visible block deltas/final state only
  and must not depend on particles, sounds, or vanilla timing parity.

Decision:

- M61 stays unit-covered for vertical plant growth. The landed behavior is driven
  by random ticks, so a wire harness would either wait on probabilistic timing or
  force an artificial tick path that no longer adds meaningful protocol coverage.
- Focused `mc-net` tests directly exercise the deterministic planner, including
  top-of-column growth, max-height no-op, obstruction, unsupported support, and
  existing cascade regressions.
- Existing harness coverage still exercises the same block delta machinery for
  block edits broadly, and M61 adds no new packet IDs, layouts, metadata, sounds,
  particles, or client effects.

## Protocol and Data Oracles

- M61 must not add new packet IDs or field layouts. It should reuse existing
  random-tick, block update/ack, relight, registry, and world-storage paths.
- No `wire-probe` or `javap` oracle is required if particles, sounds,
  statistics, game events, level events, new metadata, and new clientbound
  effects remain deferred.
- Vanilla data sidecar is required for block registries. Sugar cane, cactus, and
  air states must be resolved from namespaced block ids, not numeric state ids.
- Growth rules in M61 are Solaris-owned deterministic support rules, not a
  translation of Mojang random-tick age algorithms.

## Risks

- `RandomTickFamily::Crop` currently includes both age crops and vertical plants;
  keep age-crop behavior unchanged while adding a fallback vertical-plant branch.
- Random-tick samples may hit any block in a column. The planner must grow only
  above the top of the contiguous column.
- Support checks can become expensive if they scan unloaded chunks. Keep M61.a/b
  same-column and immediate-neighbor reads only, and treat missing data as no-op.
- Cactus has stricter vanilla neighbor rules than sugar cane. M61 should start
  with the support rules already represented locally and avoid claiming full
  cactus placement parity.
