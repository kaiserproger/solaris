# M25 - Data-driven items and recipes

**Status:** planned on `dev/M25-data-driven-items-recipes` from `main` at local tag
`m24`.
**Owning crates:** `mc-data` for sidecar loaders and repo-owned fallbacks,
`mc-server` for startup wiring, `mc-net` for Play call-site cleanup, and
`mc-test-harness` for wire-level survival coverage.

## Goal

Replace the remaining narrow survival constants with reusable data-driven item,
recipe, tag, and loot foundations. M25 should not chase broad vanilla gameplay
parity; it should make later milestones consume facts through `mc-data` instead
of growing more hardcoded arrays in `mc-net`.

The focused win is a small set of loaders and service seams that are useful
immediately for M24 behavior: food values, stack limits, durability/tool hints,
equippable slot where present, crafting-table recipes through sidecar recipes
and tags, and a first simple loot-table evaluator shape.

## Strategy

1. Keep Mojang bytes local. Extend scripts/loaders to read sidecar data, but
   commit only code, tests, docs, and repo-owned fallback fixtures.
2. Start with an oracle pass over the local 26.1.2 sidecar and `javap` metadata
   for item component shapes. Document what is available before adding loaders.
3. Add narrow `mc-data` indexes before changing Play behavior. Call sites should
   ask data services for item, food, recipe, and loot facts instead of peeking at
   JSON or hardcoded tables.
4. Preserve current M24 behavior with explicit fallback paths only where the
   local sidecar lacks payloads. Tests must prove the sidecar path and the
   fallback path separately.
5. Move recipe, tag, component, and loot data to startup-owned shared state so
   Play connections do not lazily load sidecar files or construct private copies.

## Risks / Pitfalls

- The current extractor does not include `data/minecraft/recipe` or
  `data/minecraft/loot_table`; M25 must update extraction or keep explicit
  fallback tests rather than pretending the sidecar always has them.
- Item components can look protocol-adjacent. Component IDs and shapes must come
  from local reports, `javap`, or wire oracles, never memory.
- A loader that returns vanilla-looking defaults for missing data will hide
  extraction bugs. Prefer `Option` plus an explicit fallback branch.
- Recipe matching can drift into UI/recipe-book parity. Keep M25 scoped to
  server-authoritative matching for current inventory and crafting-table flows.
- Loot tables can balloon quickly. Parse only the simple subset needed for block
  and entity drops, and record unsupported constructs as follow-ups.
- Shared startup data must not reintroduce per-connection sidecar reads in Play.

## Item Component Oracle Notes

M25.b checked the local 26.1.2 sidecar and permitted metadata before loader work:

- `data/vanilla/reports/registries.json` contains the item registry and the
  `minecraft:data_component_type` registry. The component type registry exposes
  ids for the relevant component kinds, including `minecraft:max_stack_size`,
  `minecraft:max_damage`, `minecraft:food`, `minecraft:consumable`,
  `minecraft:tool`, and `minecraft:equippable`.
- Per-item default component payloads are not stored under `data/minecraft`, but
  vanilla datagen exposes them through the `Default Components` provider at
  `reports/minecraft/components/item/*.json`. M25 updates
  `tools/extract-vanilla-data.sh` to run `--server --reports` and copy that
  gitignored report subtree into the local sidecar.
- The bundled server jar contains `data/minecraft/recipe` and
  `data/minecraft/loot_table`; M25 updates `tools/extract-vanilla-data.sh` to
  copy them into the local sidecar. The generated JSON remains gitignored.
- Food values for apple and bread are sidecar-backed through those component
  reports after extraction. Local `javap` metadata against
  `.analysis/extracted/META-INF/versions/26.1.2/server-26.1.2.jar` still pins
  the shape: `FoodProperties` has `nutrition`, `saturation`, and
  `canAlwaysEat` fields. The report values are apple `4` / `2.4` and bread `5`
  / `6.0`.
- Use duration/action are metadata-backed for now: `Consumable` has
  `consumeSeconds`, `animation`, `sound`, `hasConsumeParticles`, and
  `onConsumeEffects`; `Consumable$Builder` defaults food consumption to
  `1.6f` seconds and `ItemUseAnimation.EAT`.
- Max stack and durability are metadata-backed for now. Common item components
  set max stack size to `64`; durability overrides set max stack size to `1`.
  Apple and bread do not register durability overrides.
- Tool and equipment facts are only partially sidecar-backed through tags such
  as `tags/item/pickaxes.json`, `tags/item/head_armor.json`, and block mining
  tags. Full tool/equippable component payloads still require a sidecar shape or
  a narrow metadata-derived fallback.
