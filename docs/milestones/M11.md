# M11 - Compression, LZ4, and bulk block updates

**Status:** code complete on `dev/M11-compression-lz4-bulk-edits`, 6
commits ahead of `main` at tag `m10`. Awaiting owner review, optional
manual gate, merge, and `m11` tag.
**Estimate:** medium milestone, 18-32 h. This bundles three focused
carry-overs in the requested order: login compression, LZ4 region
reads, then section-level block update batching.
**Owning crates:** `mc-net` and `mc-protocol` for protocol framing and
packets, `mc-world` for Anvil LZ4 reads, `mc-test-harness` and
`mc-server` tests for wire coverage.

## Goal

After M11, Solaris negotiates vanilla-style login compression, can read
vanilla LZ4-compressed region chunks, and has the protocol/test
foundation for emitting `SectionBlocksUpdate` when a server-side batch
changes multiple blocks in the same section.

The milestone is ordered from highest protocol risk to smallest storage
slice, then back to edit batching. Each slice must leave the workspace
green before the next starts.

## Strategy

1. **Thread compression state once.** Send `SetCompression` during
   Login, flip the server connection state at the exact protocol
   boundary, and carry the negotiated `Compression` through
   Configuration and Play instead of hard-coding disabled framing.
2. **Validate LZ4 against a real region.** Add the decoder only after
   confirming the exact vanilla LZ4 container with a local
   `.analysis/` oracle world. Keep writes zlib-only unless a later
   milestone explicitly expands the scope.
3. **Add section update packets before batching.** Implement
   `SectionBlocksUpdate` from the javap dump, cover its packing with
   unit tests, then use it only where Solaris actually has a batch of
   changed blocks.
4. **Batch conservatively.** Preserve single-edit behaviour and acks.
   Defer invasive multi-edit relight changes unless the packet slice
   exposes a small, safe batching seam.

## Oracles

- `SetCompression`: `.analysis/protocol-dump.txt` lists
  `CLIENTBOUND_LOGIN_COMPRESSION` as login clientbound ID `0x03` and
  `ClientboundLoginCompressionPacket` as one `int compressionThreshold`
  field.
- `SectionBlocksUpdate`: `.analysis/protocol-dump.txt` lists
  `CLIENTBOUND_SECTION_BLOCKS_UPDATE` as game clientbound ID `0x54` and
  fields `SectionPos sectionPos`, `short[] positions`, `BlockState[]
  states`.
- LZ4 region reads: a local vanilla-generated world under `.analysis/`
  with `region-file-compression=lz4`. The region bytes are never
  committed; tests should skip or clearly fail with setup instructions
  when the local oracle is absent.

## Sub-milestone decomposition

### M11.a - Set Compression at login

Enable compression with a fixed positive threshold, likely `256`, after
the login handshake starts and before `LoginSuccess`. `SetCompression`
itself is sent with disabled framing; `LoginSuccess`,
`LoginAcknowledged`, Configuration, and Play use the negotiated
threshold framing.

Required touch points:

- `crates/mc-net/src/login.rs` sends `SetCompression` and returns the
  negotiated `Compression` with the profile.
- `crates/mc-net/src/server.rs`, `configuration.rs`, and `play.rs`
  accept the per-connection compression state.
- Raw TCP tests in `crates/mc-server/tests/` learn the compression
  boundary instead of assuming disabled frames forever.
- Harness clients that already detect `SetCompression` stay compatible
  with the server flip.

### M11.b - LZ4 Anvil region reads

Add an LZ4 dependency to `mc-world` and implement compression type `4`
in the Anvil region reader. Do not change the write path: dirty chunks
may still flush as zlib in this milestone.

Validation should include a minimal unit-level decoder test and a real
local oracle test that proves the fixture actually contains compression
byte `4` before asserting successful NBT decode.

### M11.c - SectionBlocksUpdate packet

Add a typed clientbound Play packet for `SectionBlocksUpdate` with
tests for:

- game packet ID `0x54`;
- packed section position as a `long`;
- VarInt entry count;
- repeated VarLong entries combining block-state ID and section-local
  position.

The packet implementation lands before any server edit-path batching,
so protocol mistakes are isolated from gameplay behaviour.

### M11.d - Conservative bulk edit emission

Introduce a small internal representation for a batch of changed blocks
and group clientbound deltas by section. Single break/place interactions
continue to emit the existing `BlockUpdate` response; multi-block server
operations can emit one or more `SectionBlocksUpdate` packets.

Relight may initially loop over the current single-edit incremental
path and defer packet emission until after the batch. A true multi-edit
light BFS is only in scope if it is small and keeps the M9/M10 parity
tests straightforward.

### M11.e - Closeout and manual gates

Close out with this document's status appendix, README/memory updates if
the user-facing run status changes, and the standard gates:

```sh
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

If compression changes the real-client login path, run the debug server
manual gate and say `готов, подключайся`.

## Acceptance criteria

1. Existing integration tests pass with compression enabled after Login.
2. Raw TCP tests assert the `SetCompression` boundary and no longer rely
   on disabled framing after that packet.
3. `mc-world` reads at least one real local LZ4-compressed region chunk
   and decodes its NBT through the normal Anvil path.
4. Missing LZ4 oracle data produces an explicit skip/setup message, not
   a manufactured passing fixture.
5. `SectionBlocksUpdate` has unit coverage for ID and byte layout based
   on the protocol dump.
6. Single block break/place behaviour and `BlockChangedAck` ordering stay
   compatible with the existing harness tests.
7. Multi-block same-section updates can be encoded and exercised without
   committing Mojang bytes or generated worlds.
8. `cargo test --workspace`, clippy, and fmt are green at closeout.

## Out of scope

- Compression threshold configuration in `example.toml`.
- Compression during Status; the status state remains uncompressed.
- Writing LZ4-compressed region chunks.
- Custom Anvil compression byte `127`.
- Full same-tick edit queueing for all inbound player actions.
- Multi-edit light propagation algorithm redesign.
- Survival reach validation, break timing, or tool durability.

## Pitfalls

- **Compression boundary.** If the server flips before sending
  `SetCompression`, or forgets to flip before `LoginSuccess`, vanilla
  clients and raw tests desync immediately.
- **Hidden disabled framing.** Play keepalive/read loops are easy to
  miss because login and configuration may appear healthy first.
- **LZ4 format ambiguity.** Use the local vanilla oracle to choose the
  correct `lz4_flex` API; do not assume block vs frame format from
  memory.
- **Oracle hygiene.** The LZ4 world and any region bytes stay under
  `.analysis/` and out of git.
- **Section coordinate packing.** `SectionBlocksUpdate` packs section
  coordinates and section-local block coordinates differently from
  `BlockUpdate`; byte-layout tests should pin this.
- **Ack ordering.** Client prediction still expects block-change acks;
  batching must not reorder or drop the existing acknowledgements.

## Open questions

- Should compression threshold be hard-coded to `256` for now or exposed
  through config in a later milestone? Default: hard-code for M11.
- Should the LZ4 oracle be produced by extending
  `tools/generate-test-world.sh` or by documenting a one-off local
  vanilla-server invocation? Default: script if it stays small.
- Should single edits also use `SectionBlocksUpdate` for consistency?
  Default: no; preserve current wire shape unless there is a real batch.
- What first server-side multi-block operation should exercise bulk
  emission? Default: a test-only harness hook or a minimal internal batch
  helper, not player break/place semantics.
