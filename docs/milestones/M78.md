## Scope

- Design a local-only automation architecture: MCP server, wrapper, or
  equivalent harness.
- Launch or attach to a real vanilla/PrismLauncher client.
- Scenario v1: connect, wait for chunks, move, break/place one block,
  open/close one simple container, disconnect.
- Capture scenario file, client logs, server logs, screenshots or
  structured observations, commit id, toolchain, config, and failure
  notes.

## Acceptance

- Evidence can be reproduced from a scenario file or exact command list.
- Closeout labels the client gate `agent-run real-client`, `prepared
  owner-run`, or `blocked`.
- M78 evidence does not claim M100 coverage beyond the scenario actually
  observed.

### Architecture

M78 now has a tracked scenario manifest and preparation wrapper:

| File | Purpose |
|---|---|
| `tools/client-automation/scenarios/m78_smoke.json` | Scenario v1 manifest for join, chunk wait, movement, block break/place, simple container open/close, and disconnect, with explicit setup preconditions. |
| `tools/prepare-real-client-scenario.sh` | Creates a local-only evidence directory under `.analysis/client-automation/runs/`, records git/toolchain/config metadata, and writes owner-run steps for a real vanilla 26.1.2 or PrismLauncher-launched client. |
| `crates/mc-test-harness/tests/real_client_scenario_manifest.rs` | Focused guard that the tracked scenario still names the required steps and evidence files. |

The wrapper rejects `wire-probe`/`mc-test-harness` style commands
case-insensitively because protocol bots are harness evidence, not real-client
evidence. When `M78_CLIENT_COMMAND` is unset or does not look like a
vanilla/PrismLauncher launch command, `--check` fails and reports degraded;
with a plausible command it reports prepared, not full client evidence.

### Scenario Preconditions

The M78 smoke manifest is reproducible only when these setup facts are true
before the client connects:

| Requirement | Value |
|---|---|
| World/config | Start Solaris with `example.toml` against `.analysis/test-world`. |
| Spawn prep | Player can stand at `(0, 64, 0)`. |
| Gamemode | `survival`. |
| Hotbar block | Selected hotbar slot `0` contains at least one `minecraft:dirt`. |
| Block-edit target | `minecraft:dirt` at `(0, 64, 1)` with air clear at `(0, 65, 1)`; break and place back at `(0, 64, 1)`. |
| Simple container | Openable `minecraft:chest` at `(2, 64, 0)` with air above it. |

The focused manifest guard asserts these fields so the scenario cannot drift
back to an optional or ambiguous hotbar/container setup.

### Prepared Owner-Run Path

```sh
bash tools/prepare-real-client-scenario.sh --prepare
cargo run --bin mc-server -- --config example.toml 2>&1 | tee .analysis/client-automation/runs/<run>/server.log
M78_CLIENT_COMMAND='<real PrismLauncher or vanilla client command>' \
  bash tools/prepare-real-client-scenario.sh --check
```

Before the client run, prepare the world/player state from the scenario
preconditions: survival mode, spawn access at `(0, 64, 0)`, hotbar slot `0`
containing `minecraft:dirt`, a dirt edit target at `(0, 64, 1)`, and an
openable chest at `(2, 64, 0)`. After the client run, copy the client log to
the prepared run directory, copy screenshots into `screenshots/`, and fill
`observations.md` with the exact scenario step results. These artifacts remain
local-only under `.analysis/`.
