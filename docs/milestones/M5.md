## Goal

After connecting to `solaris --config example.toml`, a vanilla
26.1.2 player on the test world must be able to:

1. Look at a block and break it. The block disappears, neighbouring
   columns relight, and the change persists across the rest of the
   session — both for the player who broke it and (architecturally)
   for any future player connecting before shutdown.
2. Look at the air column above ground and place a block. The block
   appears, neighbouring columns relight, persists for the session.

Concretely: M5 wires `ServerboundPlayerAction` and
`ServerboundUseItemOn` into the Play state, mutates the in-memory
`WorldStorage` chunk, recomputes light for the affected
neighbourhood, emits `ClientboundBlockUpdate` +
`ClientboundLightUpdate` to the connected client, and acks the
client's predicted action with `ClientboundBlockChangedAck`.

The acceptance gate is a manual vanilla-client connect (visibly
break + place blocks, see the world stay coherent); the regression
gate is a `mc-test-harness` integration test that drives a break
through the protocol and asserts the post-edit chunk stream
reflects the change.

Persistence to disk is *out of scope* — edits live in the
`WorldStorage` LRU and disappear on shutdown. The opaque "extras"
channel lands in M5.c so that the on-disk round-trip stays
*lossless when persistence does ship* (M6+), but M5 itself does
not write modified chunks back to `.mca`.

## Strategy

Same posture as M1 / M2 / M3 / M4 (PROJECT_SPEC §8.1, ADR 0001,
ADR 0002).

- Packet IDs and record layouts come from `javap -p` of the
  unobfuscated 26.1.2 jar, cited inline as comments per ADR 0002.
  The relevant classes are
  `ServerboundPlayerActionPacket(.Action)`,
  `ServerboundUseItemOnPacket`, `ClientboundBlockUpdatePacket`,
  `ClientboundLightUpdatePacket`, and
  `ClientboundBlockChangedAckPacket`. The shared
  `ClientboundLightUpdatePacketData` shape is already implemented
  by `mc_protocol::packets::play::LightData` from M3.a — M5 reuses
  it untouched.
- Block-state-id semantics: the wire uses *global* block-state
  ids (the same `BlockStateId.0` mc-data's `blocks.json` loader
  produces). The same id space the M4 light table is indexed by,
  no remapping needed.
- Lighting on edit re-runs the existing `mc_world::light` engine
  (M4.c) over the affected chunk's 3×3 neighbourhood. M5 does not
  attempt incremental relight — the engine is fast enough on a
  single chunk with the M4 fast paths, and a per-edit recompute
  keeps the code path identical to the spawn-burst path.
- "Extras" opaque channel — M2 follow-up #2 — stores the chunk
  NBT fields the M2 codec dropped (PostProcessing, block ticks,
  fluid ticks, structures, InhabitedTime, LastUpdate, DataVersion).
  When `chunk_from_nbt` decodes a chunk, it parks these
  byte-for-byte in `Chunk.extras: BTreeMap<String, Tag>` (or
  similar). `chunk_to_nbt` re-emits them. M5 doesn't *use* the
  extras for anything — it just preserves them so that when M6+
  starts writing chunks back, the lossy round-trip becomes
  lossless. Per-section sky/block light from M4.a stays on
  `section_lights` (separate field, separate semantics).
- Heightmap recompute — M2 follow-up #5 — runs on every
  `set_block` that changes the top non-air column. Cheap: one
  walk down the column from MAX_Y to find the new top.
- Direct-mode palette growth — M2 follow-up #3 — is closed by
  switching `ChunkSection::set` over to the `BlockStorage::Direct`
  variant when the indirect palette would exceed `MAX_INDIRECT`.
  The protocol already supports it (`encode_block_palette`
  branches on `bits_per_entry >= 9` per vanilla's threshold).
- Per-connection sequence tracker — vanilla's break/place flow
  carries a `sequence` int that the server must echo back via
  `ClientboundBlockChangedAck`. Without the ack the client
  rolls back its predicted state. M5 adds a tiny per-connection
  `last_seen_sequence: AtomicI32` that's bumped on every accepted
  action and ack'd in the BlockChangedAck packet.
- Authority model: server is authoritative. The client predicts
  the edit locally (visually), the server validates + applies +
  acks. M5's validation surface is intentionally small:
  - target chunk must exist in `WorldStorage` (no edits to
    out-of-world or absent chunks).
  - `pos.y` in `MIN_Y..MAX_Y`.
  - no anti-cheat / reach / item-stack checks — those are M7+.
- Inventory model: M5 has no inventory yet. To stay focused, **the
  place-block handler always places `minecraft:stone`** regardless
  of what the client thinks it's holding. The vanilla client sees
  whatever it predicted; the server overwrites with stone via the
  `BlockUpdate` packet. The client snaps to the server's value
  visually. Inventory + item-stack handling is its own milestone.

## Sub-milestone decomposition

Tentative ordering. The first three are foundational packet +
mc-world work and run serial; M5.d / M5.e share infrastructure but
can land in either order; M5.f is the integration test; M5.g is
the manual gate + closeout.

### M5.a — serverbound `PlayerAction` + `UseItemOn` packets

In `mc-protocol::packets::play`:

- Add `ServerboundPlayerAction` (decode only — server never sends
  it). Fields:
  - `action: PlayerActionKind` (VarInt; enum mirroring vanilla's
    8 variants in registration order so the wire byte matches).
  - `pos: BlockPos` (8 bytes packed `i64` per vanilla's
    `BlockPos.toLong`: 26-bit x, 12-bit y, 26-bit z, signed).
  - `direction: Direction` (VarInt; 6 face enum).
  - `sequence: VarInt` (per-action int the server echoes).
- Add `ServerboundUseItemOn`. Fields:
  - `hand: InteractionHand` (VarInt; 0 = main, 1 = off).
  - `block_hit: BlockHitResult`:
    - `pos: BlockPos` (packed i64).
    - `direction: Direction` (VarInt).
    - `cursor: Vec3` (3× `f32`, position within the clicked face,
      0..1).
    - `inside: bool` (one byte).
    - `world_border_hit: bool` (one byte; new in 26.1 per the
      javap shape — verify the byte exists in the captured wire).
  - `sequence: VarInt`.
- IDs verified via `javap -p` on
  `net.minecraft.network.protocol.game.GameProtocols`; cite the
  `PacketType` name in a comment exactly like the M1.g.2 / M4
  packets do.
- Tests: synthesise byte streams matching captured wire frames
  and assert round-trip parity.

Out of scope: actually *acting* on these packets — M5.a is the
wire layer, M5.d / M5.e wire them to the handler.

### M5.b — clientbound `BlockUpdate`, `LightUpdate`, `BlockChangedAck` packets

In `mc-protocol::packets::play`:

- `BlockUpdate` — `pos: BlockPos` + `state_id: VarInt`. Single-
  block edit, the most common case for M5's handlers. Encode only.
- `LightUpdate` — `chunk_x: VarInt`, `chunk_z: VarInt`,
  `light: LightData`. Same `LightData` shape as
  `LevelChunkWithLight` — re-use the type, no new codec work.
- `BlockChangedAck` — single `sequence: VarInt`. Server echoes
  every accepted action's sequence so the client can release its
  prediction state.
- IDs from javap. Tests: encode a known-good byte stream and
  assert equality.

Out of scope: `SectionBlocksUpdate` (the multi-block optimisation
the lighting engine could occasionally produce on a cascade) —
single `BlockUpdate` per modified position is fine for M5's
one-block-at-a-time interaction.

### M5.c — `mc-world` mutation hardening

This sub-milestone closes three M2 follow-ups that turn from
"optional" to "load-bearing" the moment chunks get mutated.

- **Heightmap recompute** (M2 follow-up #5). New helper
  `Chunk::recompute_heightmap(name: &str)` walks each `(x, z)`
  column top-down to find the highest Y matching the heightmap's
  predicate (`MOTION_BLOCKING`, `WORLD_SURFACE`, etc.). Called
  from a new `Chunk::set_block_and_update` that wraps `set_block`
  + recomputes the affected three (or four) client-usage
  heightmaps. Tests pin: setting `(8, 100, 8)` to stone in an
  air chunk updates `WORLD_SURFACE` from `MIN_Y` to `101`;
  setting back to air drops it back to whatever the next-lower
  non-air is.
- **Direct-mode palette growth past 256** (M2 follow-up #3).
  `ChunkSection::set` currently caps at `MAX_INDIRECT_BITS = 8`
  (= 256 entries). Add a `BlockStorage::Direct(PackedBitArray)`
  variant indexed by raw global state id; switch over when the
  indirect palette overflows. The wire encoder
  (`encode_block_palette`) already handles direct mode in its
  `>= 9` branch; the disk encoder (`encode_block_section`) does
  not — extend it for round-trip parity. Test: insert > 256
  distinct synthetic state ids into one section and assert
  storage transitions to Direct cleanly + round-trips through
  the disk codec.
- **Opaque "extras" channel** (M2 follow-up #2). Add
  `Chunk.extras: BTreeMap<String, Tag>` (or a typed struct if a
  small set of fields stabilises). `chunk_from_nbt` collects
  every root-level NBT key the M2 codec currently drops
  (PostProcessing, block_ticks, fluid_ticks, structures,
  InhabitedTime, LastUpdate, DataVersion). `chunk_to_nbt`
  re-emits them. The existing M2 round-trip test
  `round_trip_real_vanilla_chunks` becomes strictly stronger:
  the modelled subset already byte-matches, and now the
  unmodelled-but-preserved subset round-trips too. Per-section
  sky/block light from M4.a stays on `section_lights` (different
  field, different semantics) — extras only carries the *other*
  dropped fields.

Three logical units, three commits — keeps the M2 follow-up trio
each in its own reviewable diff.

### M5.d — break-block flow

In `mc-net::play`:

- Read serverbound frames in the keepalive loop. Currently only
  `ServerboundKeepAlive` is handled; M5.d adds dispatch for
  `ServerboundPlayerAction` (and ignores everything else for now,
  same posture as today's movement-packet-ignoring code path).
- Per-connection state grows a small `InteractionState {
  next_ack: i32, world: WorldHandle, block_light:
  Option<Arc<BlockLightTable>>, light_workspace: LightWorkspace }`
  carried through the keepalive loop.
- On `START_DESTROY_BLOCK`: in creative-mode-style behaviour we
  apply the break immediately (no `STOP_DESTROY_BLOCK` needed).
  In survival the client also sends `STOP_DESTROY_BLOCK` after
  the destroy animation finishes; honour either as long as the
  server hasn't already applied the break.
- Apply: lock `WorldStorage`, resolve the target chunk, call
  `chunk.set_block_and_update(x, y, z, air_state)`, drop the
  lock. Out-of-world `y`, missing chunk, or already-air → log
  and ignore but still ack the sequence.
- Emit `ClientboundBlockUpdate(pos, air_state)`,
  `ClientboundBlockChangedAck(sequence)`, then a
  `ClientboundLightUpdate` for the chunk + each lateral
  neighbour whose light might have been affected (4 neighbours
  in the manhattan sense — `(-1,0)`, `(+1,0)`, `(0,-1)`,
  `(0,+1)`). M5 conservatively re-emits all 4 even if some
  weren't actually changed; the alternative (diffing) is M6 perf
  work.
- Pace: write packets back-to-back; the keepalive scheduler
  must continue to tick. The interaction handler is short
  (~milliseconds) so it doesn't block the loop.

### M5.e — place-block flow

In `mc-net::play`:

- Dispatch `ServerboundUseItemOn` in the same loop.
- Always place `minecraft:stone` at `pos + direction.normal`
  (the cell adjacent to the clicked face). Validate that the
  target cell is currently air; otherwise drop the action
  silently and still ack the sequence.
- Emit `BlockUpdate`, `BlockChangedAck`, and light updates for
  the same 4-neighbour ring as the break flow.
- The hand / cursor / inside / sequence fields are read off the
  wire but mostly ignored — we record them in trace logs for
  future inventory work but don't gate placement on them.

### M5.f — integration test

In `crates/mc-test-harness/tests/`:

- New `tests/block_edit.rs`. Boots `mc_net::run` on
  `127.0.0.1:0` against the test world, walks Handshake →
  Login → Configuration → Play just like the M3.g harness, waits
  for the spawn burst to finish, then:
  1. Sends `ServerboundPlayerAction{ action: START_DESTROY_BLOCK,
     pos: (0, -61, 0), direction: Up, sequence: 1 }` to break
     the grass at `(0, -61, 0)`.
  2. Asserts the server emits `BlockUpdate(pos=(0,-61,0),
     state=air_id)`, then `BlockChangedAck(sequence=1)`, then a
     `LightUpdate` for chunk `(0, 0)` whose `LightData` is
     well-shaped (same M4.f-style invariants).
  3. Issues a fresh `LevelChunkWithLight` request indirectly by
     hopping the player into the chunk again (or via a second
     connection in a follow-up burst — TBD on cleanest reset)
     and asserts the chunk's `data` blob no longer contains the
     grass state at the expected nibble. Falls back to inspecting
     the `WorldStorage` cache directly if a re-fetch round-trip
     proves awkward.

If the second-fetch path proves clumsy, M5.f drops the
re-fetch leg and asserts only on the live wire packets — the
ground truth (`WorldStorage` post-edit state) is exercised by
M5.d's unit tests.

### M5.g — manual gate + closeout

Boot the server with `cargo run --bin mc-server -- --config
example.toml` (debug build per the session prompt's rule).
Connect via PrismLauncher 26.1.2 vanilla client. Acceptance:

- Break the grass cell directly under the player. The block
  visually disappears, the column reveals dirt; lighting on
  adjacent chunks stays visually consistent (no flashing dark
  patches).
- Right-click on the dirt face to place a block (server places
  stone regardless of held item). The block appears at the
  correct face-adjacent cell, lighting re-flows.
- Disconnect and reconnect — the modified blocks **revert** to
  the on-disk state. (M5 is in-memory only; persistence is M6+.)

Closeout commits: this doc gets the "What landed where" table
and a status / validation appendix; README's status paragraph

## Out of scope (so it does not creep)

- **Inventory / item-stack model.** Place always emits stone.
  Held-item, hotbar, slot, click handlers — all M6+.
- **Persistence of edits to `.mca`.** Edits live in the
  `WorldStorage` cache for the session and disappear on
  shutdown. The extras channel lands here so persistence
  *can* be lossless when it arrives, but M5 doesn't write
  chunks back.
- **Survival-mode block-break timing / mining speed / tool
  damage.** Server applies the break on `START_DESTROY_BLOCK`
  immediately. The client predicts and animates; the server
  catches up via the ack.
- **`SectionBlocksUpdate` multi-block packet.** Single-block
  `BlockUpdate` per edit is enough for M5's interactive flow.
  Multi-block becomes interesting when worldgen / explosions /
  bulk physics start moving lots of blocks at once (M6+).
- **`ClientboundLightUpdate` from non-edit sources.** Day/night
  cycle, dimension change, etc. all need light updates eventually.
  M5 only emits `LightUpdate` as a side-effect of `BlockUpdate`.
- **Anti-cheat / reach validation / sequence-out-of-order
  handling.** Server trusts the client's `sequence`. A
  reordered or stale sequence is ack'd-and-ignored.
- **Multi-player physics consistency.** Only one connection at a
  time is meaningfully tested. The handler design (per-connection
  state, atomic edits to the shared `WorldStorage`) is
  multi-player-shaped, but two-client testing is M8.
- **Worldgen.** Still the next big milestone (M6 in PROJECT_SPEC §9).
- **Spiral chunk-iteration order, Set Compression, LZ4 read
  path, SetDefaultSpawnPosition.** M3 carry-overs that stay
  carried over.

## Open questions to resolve along the way

- **`BlockHitResult.world_border_hit` byte presence.** The
  javap dump shows two constructors for `BlockHitResult`, only
  one with the `worldBorderHit` flag. The wire stream codec
  serialises one of these; capture a real `UseItemOn` from the
  bundled vanilla server first to pin the byte count. Default
  assumption: the field is on the wire and we read it.
- **`set_block_and_update` lock granularity.** The world is
  behind `tokio::sync::Mutex<WorldStorage>`; acquiring per-edit
  is fine for one player, but the design needs to extend to
  many. Decision: keep the mutex for M5; switch to `RwLock` or
  a sharded per-region lock when M8 introduces multi-player.
- **Light recompute scope.** A single block break can affect
  light in chunks beyond the immediate 3×3 neighbourhood (e.g.
  removing the top of a tall column lets sky-light cascade down
  for hundreds of blocks of neighbours). M5 ships "recompute
  centre + 4 lateral neighbours" — accept the occasional
  visible artefact at distance, address with diff-based
  incremental relight in M6.
- **Vanilla `sequence` 0 semantics.** The wire VarInt is
  zero-able; a client may send `sequence=0` for un-tracked
  actions. Confirm whether the server should ack 0 explicitly
  (vanilla does) or silently drop. Default: ack everything we
  receive.
- **`Chunk.extras` shape.** A `BTreeMap<String, Tag>` keeps the
  M5.c diff small but is awkward to navigate; a typed struct
  reads better long-term. Decide during M5.c on the first
  unmodelled field that actually needs typed access (probably
  `block_ticks` for M6's physics).

## Pitfalls (carry-over from M1 + M2 + M3 + M4 review)

- **Packet ID volatility across patch releases.** Cite the
  javap source for every new ID; don't copy from older wire-probe
  captures.
- **Network NBT vs Anvil NBT.** Block-state-id and `BlockPos` are
  protocol primitives, not NBT, so M5 mostly avoids the M2 trap.
  But the extras channel touches Anvil NBT directly — same
  named-root vs unnamed-root pitfall the M2 doc already warned
  about.
- **`Mutex` deadlock during chunk-edit + light-recompute.** The
  light engine reads chunks via the same `WorldStorage` handle.
  If the edit holds the mutex while spawning the relight, we
  deadlock. Hold the lock only long enough to apply the
  mutation; clone the chunk + neighbours out, then drop the
  lock before running `compute_chunk_light_in`.
- **Sequence ack ordering.** Vanilla expects the ack to land
  *after* the update packet, not before. Server must serialise
  `BlockUpdate` → `LightUpdate` → `BlockChangedAck`. Easy to
  shuffle accidentally.
- **Direct-mode disk encode.** The current
  `encode_block_section` always emits an indirect palette
  ("palette" tag with list of `Compound { Name, Properties? }`).
  Direct mode on disk uses *no* palette (or a single-entry one,
  per vanilla); pin the M2 round-trip oracle against a section
  in direct mode synthetically built in tests, since the bundled
  test world doesn't contain one naturally.
- **Heightmap key set.** Different vanilla generators produce
  different subsets of heightmaps (`*_WG` worldgen variants are
  present only mid-generation). `set_block_and_update` should
  recompute *every* heightmap currently present on the chunk,
  not a hard-coded list, so partially-generated test-world
  chunks survive an edit cleanly.
- Per [[feedback-no-external-artifacts]], any captured wire
  blobs and any modified .mca files stay in `.analysis/`
  (git-ignored).

## Open follow-ups (handed to M6+)

- **Persistence of edits to `.mca`.** M5 keeps mutations in the
  `WorldStorage` LRU and discards them on shutdown / eviction.
  The extras channel landed in M5.c.2 specifically to make
  persistence lossless when it arrives in M6+.
- **Inventory + held-item / hotbar.** Place always emits stone
  regardless of `UseItemOn.hand`. The packet's cursor / inside /
  world-border-hit fields are decoded into the wire struct and
  logged but otherwise ignored.
- **Survival break-timing / tool damage / mining speed.** Server
  applies on `START_DESTROY_BLOCK` regardless of timing; the
  client's destroy-animation is decorative on our side. Real
  mining speed lands with the inventory + item model.
- **`SectionBlocksUpdate` multi-block packet.** Each edit ships
  one `BlockUpdate`. Bulk edits (explosions, fluid flow, paste
  ops) will want the multi-block packet.
- **Incremental relight.** Every edit recomputes the centre + 4
  manhattan-neighbour chunks in full. A diff-based relight
  (process only cells whose source value changed) would cut the
  ~150 ms edit latency in debug builds.
- **Reach / sequence-out-of-order validation.** Server trusts
  the client's `sequence` and `pos`. Tighten when the M22
  anti-cheat pass arrives.
- **M3-carryover M4/M5 didn't touch:** spiral chunk-iteration
  order, Set Compression, LZ4 read path,
  `SetDefaultSpawnPosition` re-introduction.
- **Worldgen.** Still the next big spec-milestone — M6 in
  PROJECT_SPEC §9. Scope re-negotiated at the start of the M6
  session (see `work/M6-session-prompt.md`).
