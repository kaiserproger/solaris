# M9 — Incremental relight

**Status:** plan only, on `dev/M9-incremental-relight` (0 commits
ahead of `main` at the M8 merge, tag `m8`). `cargo test --workspace`
baseline 240 tests green.
**Estimate:** scope-bounded — 15–25 h. Single perf item carried
over from M5 follow-ups and M8 out-of-scope. The cost path that
this milestone targets is the per-edit relight in
`mc-net::play::send_relight_around`, which currently rebuilds the
full 24-section sky+block grid for **five** chunks on every break
or place — measured ~150 ms in debug for a single dirt-place at
the M5 manual-gate session.
**Owning crates:** `mc-world` (light engine + cache), `mc-net`
(Play state + edit hook).

## Goal

After M9 a single block edit emits **only** the `LightUpdate`
packets whose stored arrays actually changed (typically 1, never
more than 9), and each packet is produced by a bounded BFS
confined to the 3×3 chunks around the edit cell — no full
24-section recompute. Target: edit-side relight ≤ 10 ms in debug.

Crucially: the result must be **bit-identical** to the current
full-recompute path on every input, so the existing M4.f harness
parity tests and any new M9 unit tests both pin the equivalence.

## Strategy

The full `compute_chunk_light` is a removal-free addition-only BFS
seeded from sky tops and block emitters. The incremental variant is
the same algorithm restricted to a window around an edit:

1. **Cache per-chunk computed light.** A `LightCache` keyed by
   `ChunkPos`, owned by `InteractionState`, seeded during the
   spawn-burst `build_chunk_packet` call so each chunk's light is
   computed exactly once at login. Memory budget: with view
   distance 10 and ~21×21 emit, the upper bound is ~17 MB per
   connection (≈200 KB × ~85 cached non-air chunks). All-air
   chunks the fast path returned for stay uncached — they're
   reconstructable on demand.

2. **Bounded-radius diff BFS.** Light propagates at most 15
   cells from any source, so a single edit's effect is confined
   to the 3×3 chunks around `centre_pos`. On every edit:
   a. Pull the post-edit 3×3 `Chunk` refs from storage.
   b. Pull the 3×3 `ChunkLight` slots out of the cache (each
      `Option<ChunkLight>` — missing slots stay missing, same
      boundary truncation as the full path).
   c. Run removal+addition BFS for block-light and for sky-light
      over the 31×31×384 window, mutating the cached arrays in
      place.
   d. Put the slots back; collect the positions whose arrays
      were actually mutated and emit one `LightUpdate` per
      touched chunk.

3. **Sky-column re-seed.** Sky-light's "source" is the top of
   every open column. If the edit cell's `propagates_sky` flag
   flipped, columns above/below within the 31×31 footprint need
   their direct-15 status recomputed. Handled by an explicit
   column walk anchored at the edit cell — walk down from the
   edit cell, set each open cell to 15 (column still open) or 0
   (column just closed), stop at the first opaque cell or no-op.

4. **Like-for-like short-circuit.** If `prev_state` and
   `new_state` share opacity, emission, and `propagates_sky`,
   return immediately with an empty touched-list. Cache and
   wire untouched.

## Sub-milestone decomposition

### M9.a — `LightCache` + spawn-burst seed

Add `LightCache` (a `HashMap<ChunkPos, ChunkLight>`) to
`mc-world::light` with `insert`/`get`/`contains`/`remove`. Wire
it into `mc-net::play::InteractionState`: thread a `&mut
LightCache` through `emit_chunks_around` and `build_chunk_packet`
so the spawn burst seeds the cache. No behaviour change at the
edit path yet — `send_relight_around` keeps running the full
5-chunk recompute.

### M9.b — `apply_block_change_to_light` + BFS

In `mc-world::light`: add `apply_block_change_to_light(cache,
chunks, table, centre_pos, lx, world_y, lz, prev_state,
new_state) -> Vec<ChunkPos>`. The function:

1. Reads emission/opacity/`propagates_sky` for both states.
2. Like-for-like short-circuit if they all match.
3. Pulls the 3×3 `ChunkLight` slots out of the cache.
4. Runs `incremental_block_light` (removal+addition BFS).
5. Runs `incremental_sky_light` (removal+addition BFS + column
   re-seed if `propagates_sky` flipped).
6. Puts the slots back; returns the touched-position vec.

Unit tests in `light.rs`:

- like-for-like no-op (empty touched, cache untouched);
- place glowstone in air (cache equals full recompute);
- remove glowstone (cache equals full recompute);
- place opaque stone (sky column closes, cache equals full);
- break stone column top (sky pocket opens, cache equals full);
- chunk-seam edit (light ripples into east neighbour, both
  cache slots equal full);
- **random edit sequence vs full recompute** — 40 deterministic
  pseudo-random edits, parity asserted after each.

### M9.c — wire into edit path

In `mc-net::play`: replace `send_relight_around` with
`send_incremental_relight`. New flow:

1. Pull the 3×3 post-edit chunks from storage (vs current 5×5).
2. Seed the cache for the centre chunk if it's not present
   (rare: edit before spawn burst reached it) via a single full
   recompute.
3. Call `apply_block_change_to_light`.
4. Emit one `LightUpdate` per returned touched position
   (typically just the centre; up to 9 worst case).

### M9.d — harness CI gate (parity-on-the-wire)

`mc-test-harness/tests/incremental_relight.rs`: spin a server,
drive a place + break sequence through the typed `Client`, dump
the `LightUpdate` payloads, recompute the expected light via
`compute_chunk_light_in` on the same post-edit chunks, and assert
byte-for-byte equality of the wire arrays. Pins the M9.b BFS
against the M4 reference engine end-to-end.

### M9.e — closeout

Status appendix in this doc, README status paragraph,
`project-status` memory update. Owner merges to main + tags
`m9`.

## Out of scope

- **Block emission table tweaks.** M9 only re-uses
  `BlockLightTable` as-is — adding new entries (glowstone
  variants, lava emissive etc.) is M10+ data work.
- **Multi-edit batching.** If a tick contains N edits in the
  same 3×3 neighbourhood, M9 still runs N independent BFS
  passes. A merged `SectionBlocksUpdate`-driven batch relight
  is a separate follow-up.
- **Cache eviction.** With view distance 10 the upper bound is
  ~17 MB per connection; on disconnect the cache drops with
  `InteractionState`. No LRU pressure modelled in M9.
- **Async/background relight.** Edit path stays synchronous;
  M9's win is from doing 15×-less work, not from offloading.
- **Lighting persistence to `.mca`.** Sky/block arrays still
  re-derive on chunk load. M5/M6 follow-up.

## Pitfalls

- **Sky column edge cases.** The column-re-seed walk must stop
  at the first opaque cell *or* at any cell whose new value
  matches its old — otherwise we'd wipe legitimately direct-sky
  cells below an unrelated opaque cell.
- **3×3 boundary truncation.** A chunk-seam edit propagates light
  into neighbouring chunks; the BFS must handle `None`
  cache/chunk slots gracefully (treat as boundary, don't panic).
  Same posture as the full path's neighbourhood `None`
  handling.
- **Edit cell on the receiving side of removal.** When removal
  BFS hits the edit cell's neighbours, the edit cell itself was
  just overwritten with `new_emit`, not the pre-edit value —
  treat it as an independent source on the receiving side.
- **Cache miss at edit time.** If an edit lands on a chunk
  whose light wasn't seeded (rare race between spawn burst and
  early interaction), full-recompute the centre chunk before
  the incremental pass — never feed `apply_block_change_to_light`
  a cache with the centre chunk missing.
- **Wire-light invariants.** The M4.f harness pins `sky_y_mask`
  and `block_y_mask`; the cache stores `ChunkLight` (per-section
  arrays) and the wire encoder derives the masks from non-zero
  sections. Mutating in place must preserve the section-emptiness
  bookkeeping.

## Open follow-ups (handed to M10+)

- **Multi-edit batching.** N edits in one tick still drive N
  independent BFS passes. A `SectionBlocksUpdate`-driven merge
  is a separate milestone.
- **Cache eviction.** Long sessions with large view distance
  could climb the ~17 MB / connection bound; no LRU pressure
  yet. Not urgent at the current view distance of 10.
- **Set Compression at login + LZ4 chunk read.** Deferred from
  M8; still on the polish backlog.
- **`SetDefaultSpawnPosition` re-introduction.** Wire-probe
  verification needed against a real vanilla server.
- **Reach validation / anti-cheat.** Edits accept any reach
  distance from the client; cheap exploit surface.
- **Async / background relight.** Edit path stays synchronous;
  M9's win is from doing 15× less work, not offloading.

## Open questions

- **`SectionBlocksUpdate`-driven batch.** Worth wiring even at
  M9 cost? Probably not — adds packet handling work and the
  edit cadence in normal play is low. Stays open for M10+.
- **Lava emission.** Currently `BlockLightTable` may not have
  lava emission entries (data report dependent). If a manual
  gate near lava shows darkening, ticket separately — M9 is
  about the engine, not the table content.
