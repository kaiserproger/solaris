# Solaris 1.0 "Pauline" RC1

Release candidate 1 of Solaris 1.0, the first stable release of the Solaris
Minecraft Java Edition server (written in Rust) and the Solaris native client.
Target: Minecraft Java Edition **26.3** (protocol 777). 26.1.2 (protocol 775)
clients can still join. Report problems before 1.0 final on October 31.

## Minecraft 26.3

- The server speaks 26.3 (protocol 777): packet ids and layouts, the 14 new
  item components (they round-trip through give, the creative inventory and
  saves), every 26.3 tag the 26.3 registries refer to, slime/magma-cube
  metadata, and decorated-pot sherds in the 26.3 format (existing pots are
  converted on load).
- `content import`/`content verify` refuse a cache whose tags don't cover
  the registries clients receive. Re-import a cache made by an earlier build.
- Gameplay still uses the 26.1.2 data pack (worldgen, loot, recipes,
  advancements). The new 26.3 mobs and blocks exist in the registries but have
  no behaviour yet; the two new biomes are not generated.
- 26.1.2 (775) clients are translated per session at the edge. Blocks that are
  new in 26.3 are shown to them as the nearest 26.1.2 block. This needs a
  second, 26.1.2 content cache: see `docs/OPERATING.md`.
- Legacy level-event translation consumes the packet's global flag, preserving
  splash-potion, jukebox and other level events instead of rejecting a trailing byte.
  Invalid player-command ordinals remain rejected and are reported as enum errors,
  not oversized strings.
- Vanilla 26.3 worlds (DataVersion 5023) import through `world import-anvil`.
- Trial spawners and vaults send clients vanilla's client data instead of the
  saved server state.
- The native client's 26.3 block facts approximate one new 26.3 rule: whether
  a block blocks the view is decided by its full shape, as in 26.1.2. Smooth
  lighting and ambient occlusion can differ from vanilla 26.3 on such blocks.
  The client's composter prediction uses the normal fill chance at level 0
  (the server's result is shown right after).

## Highlights

### Settlements

- Villages are autonomous settlements: a planner builds certified buildings
  (house, workshop, storage, mine, camp) from real materials, villagers take
  building jobs, miners and lumberjacks gather resources.
- Builders level hillside sites (up to 3 blocks of height difference) with
  real dirt from storage instead of refusing every non-flat site, and a mine or
  lumber camp is only certified once a villager can actually walk to it.
- Settlements raise an army and run an economy. Players manage them through a
  server-driven dialog UI.

### Native client

- Low, Medium and High graphics presets. Medium adds HDR, bloom, atmosphere,
  shadows, god rays and water; High adds three shadow cascades, TAA and
  screen-space reflections.
- Far terrain beyond the view distance in biome colours, with 1-block finest
  detail, filled from the server's LOD channel; on operator opt-in the client
  generates unexplored land on its GPU.
- Hi-Z culling and multi-draw-indirect terrain.
- Answers keepalive promptly during large block-update bursts (a big `/fill`
  no longer disconnects the client) and accepts any server tick rate.
- Starts on AMD/RADV under native Wayland.

### Multiplayer and plugins

- Proximity voice chat (Opus relay) and screen sharing to in-world monitors
  with owner-granted, look-gated delivery.
- Carrier-backed custom blocks for plugin Loader bundles.
- Fail-closed authentication gate with a native password API for login
  plugins.
- Opt-in in-game computer terminal block.
- Distant Horizons support.

### Gameplay

- Server-driven dialogs (show/clear, custom click actions).
- Mob capabilities as blueprint data; mob step-up; village terrain fit.
- Integrated anvil, maps, datapacks, combat, redstone, Nether, End and jigsaw
  structure generation work.
- Natural mob caps exclude retained entity rows from unloaded chunks, so old
  populations do not starve distant players; both global and per-player caps
  still apply.
- Firework rockets launch when used on a block, and banners can decorate
  shields in either crafting grid.
- Crafter and sculk-shrieker level events reach only nearby players in the
  same dimension.
- Generated stronghold portal frames each have a seeded 10% chance of an
  inserted Eye of Ender.
- Bed interaction checks reach to both halves, so clicking the head works when
  only the foot is within sleeping range.
- Scaffolding permits side entry, climbing and sneaking down through its
  platforms while still supporting a player standing on top.
- Client-steered boats accept collision-checked movement without correction
  feedback or a duplicate physics step; boat and raft rider positions use their
  passenger attachment points.
  Unsupported client motion cannot suppress native boat gravity; persistent
  airborne hovering is corrected and disconnected after the vanilla
  gravity-scaled floating allowance (160 ticks for an ordinary boat).
- Soul sand and magma create upward and downward bubble columns through source
  water; columns update when their support changes.
- Planting pitcher pods preserves the supporting farmland.
- Copper bulbs toggle on rising redstone edges, retain their light when power
  falls, and provide comparator strength 15 while lit, including waxed and
  oxidized variants.

### Performance

- Section-granular checkpoints, delta chunk fan-out and a bounded WAL.
- Worldgen evaluates the density graph in 8-column fp32 batches, fills each
  chunk in two passes (cell corners, then a compiled per-block program),
  skips off-chunk ore work and samples biomes per column, parsing each biome
  once. Generated terrain and biomes are unchanged.
- Chunk admission uses the tick's spare time instead of one chunk per tick,
  and lighting skips neighbour checks that cannot change the result.
- Block changes are sent per chunk section (one packet per section instead of
  one per block).
- Random ticks are sampled serially below 256 chunks; idle zombies rest their
  decision loop.

## Upgrade notes

Back up the world and configuration before upgrading. 1.0 does not open
v0.0.8 native world directories in place. Move a v0.0.8 world through Anvil
once, with each version's own binary, while the server is stopped:

```sh
# with the v0.0.8 binary
solaris --config server.toml world export-anvil --source world --destination world-anvil --receipt export.json
# with the 1.0 binary
solaris --config server.toml world import-anvil --source world-anvil --destination world-1.0 --receipt import.json
```

Then point `[data].world_dir` at `world-1.0`.

This moves the world's vanilla data (terrain, entities, players, containers).
Plugin state is **not** carried over: the imported world starts with empty
plugin storage. Keep the original v0.0.8 world directory.

If 1.0 is started on a v0.0.8 world, it refuses and prints these two commands. It does not
offer `world upgrade-worldgen` for such a world, and refuses that command too without writing
anything, so the world stays readable by v0.0.8.

Worlds created by pre-rc.1 development builds need `solaris world upgrade-worldgen`
once, with the server stopped and the same `--config` used to run that world.
Worldgen revision 30 corrects the deepslate transition to the vanilla Y 0..8 linear
gradient. The offline upgrade preserves existing chunks and gameplay data; newly
generated chunks use the corrected rule.

## Install

```sh
curl -fsSL https://raw.githubusercontent.com/kaiserproger/solaris/v1.0.0-rc.1/install.sh | \
  SOLARIS_VERSION="v1.0.0-rc.1" bash
solaris content import --version 26.3 --download
```

Solaris does not redistribute Mojang data: `content import` downloads the
Mojang server once, checks its size and SHA-1 and derives a local content
cache. The server refuses to start without that cache and names the command
to run.

## Validation boundary and known gaps

Validation for this release is recorded in the release receipt. Gates that
did not run are listed there as not run. In short, on the release build:

- A vanilla Java 26.3 client joins and plays: join and chat, inventory and
  crafting, mining and placing, feeding, damage, death and item pickup. A
  vanilla Java 26.1.2 client joins and chats.
- The native client joins, renders, reconnects, dies and respawns, and its
  title screen connect flow works. The packaged singleplayer start reached
  Play only with the 26.3 content served from a local test manifest: the
  launcher's default content URL still serves 26.1.2 content, so a fresh
  singleplayer install fails until the 26.3 content is published there.
- The settlement acceptance gate (house, workshop, storage, mine, camp,
  binding, doors, sleep, harvest, mining and lumber work) passes.

Known gaps:

- A village that starts with no materials does not yet gather its own logs and
  stone, so it never builds its first storage on its own. Targeted for 1.0.
- The buildings gate verified house levels 1-3 only; the other blueprints
  were not reached before its time limit.
- The army gate passed combat and guard return in separate runs, not yet in
  one full run.
- The native client's 30-minute session gate fails its memory budget: memory
  grew by up to about 37 MB after warm-up (budget 4 MB) under software
  rendering, and ended 0.8 MB above the start. The cause is not known yet.
- The settlement gates ran without plugin packages.
