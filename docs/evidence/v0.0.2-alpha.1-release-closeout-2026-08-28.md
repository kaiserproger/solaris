## AArch64 and publication boundary

The repository release workflow builds both final assets after the tag is pushed:

- `x86_64-unknown-linux-gnu` on `ubuntu-24.04`;
- `aarch64-unknown-linux-gnu` on the native `ubuntu-24.04-arm` runner.

For each target, CI validates the release tag, performs a locked release server build, packages the exact release payload, verifies `VERSION` and `--version`, runs `--check`, publishes SHA-256 files, and finally creates/updates the GitHub prerelease using `docs/releases/v0.0.2-alpha.1.md`.

Therefore the local release closeout does not pretend to substitute an x86 cross-build for the native AArch64 release job. The pushed tag is the trigger for the authoritative two-architecture packaging gate.

## Initial tag-run infrastructure retry

The first GitHub tag run (`33146371005`) reached the Loader job with the reproducible fixture check green, then failed while Forge Mavenizer was configuring `:loader-forge`: the clean runner timed out downloading `forge-26.1.2-64.1.0-userdev.jar` from `maven.minecraftforge.net`. The log reports `java.net.http.HttpTimeoutException`; Maven Central and `libraries.minecraft.net` fallbacks returned the expected 404 because they do not host that Forge artifact. No Loader test or Solaris assertion failed.

The Loader CI step now retries the complete Gradle Loader test command up to three times. A successful attempt exits immediately; the third failure remains terminal, so this does not convert a persistent Loader/code failure into success. No Loader production code changed. Because the failed tag run had not reached release-build/publication and no GitHub release assets existed, the release tag is moved to this CI-portability fix commit before publication.
