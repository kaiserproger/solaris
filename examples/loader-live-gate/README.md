# Loader Live-Gate Fixture

**Deployment: Requires Solaris Loader on client.** A client profile without
Solaris Loader protocol support is rejected during Configuration with the
supported loader platforms and required bundle identities.

This is the isolated two-owner input for the Solaris Loader real-client gate.
It uses production plugin discovery and artifact transfer; it does not alter a
PrismLauncher instance.

Both owners are the *same* real component: `sdk/rust/examples/hello` built in its
`loader-live` mode, deployed twice under the two manifests below. The owner is
the plugin id the host bound to the instance, so the two packages differ by their
manifest, their client bundle and the ids they own rather than by a second
program, and a third plugin id fails its instance instead of being served as one
of the two.

The deployment selects the component frontend explicitly: `playable.toml` sets
`[plugins] runtime = "wasm"`, and both owners are API `0.7.0` WebAssembly
components discovered by the component host. Nothing here falls back to the
retained Luau frontend - a deployment still configured as `runtime = "luau"`
refuses these manifests instead of reading them under the other contract.

## Contents

- `plugins/<owner>/plugin.toml.in` - the authored manifest template.
- `plugins/<owner>/plugin.toml` - the manifest, generated by the fixture build.
- `plugins/<owner>/client-src/` - the inspectable index and assets the client
  bundle is built from.
- `plugins/<owner>/client/rich-content.zip` - the generated client bundle whose
  SHA-256 and size the manifest pins.
- `playable.toml` - the isolated server configuration. Its plugin directory is
  the staged deployment root, which `--prepare` writes (see below).

The tracked archives are reproducible from their inspectable sources:

```sh
tools/build-loader-live-gate-fixture.sh --check
```

`--check` regenerates each bundle and manifest from `client-src/` and compares
them byte for byte with the tracked outputs; the default mode regenerates them.
The bundle index declares both owners' screens, their custom block and item, the
verified tone asset and the key bindings described below.

Fixture generation requires `ffmpeg` with `libvorbis` for the tones and
`python3` for the Ogg normalizer:

```sh
tools/build-loader-live-gate-fixture.sh --audio
```

That regenerates the tracked mono OGG sources deterministically: eight-second
440 Hz Ruby and 660 Hz Sapphire tones, 48 kHz. The audio phase measures the
440/660 Hz amplitudes of a real stereo capture, so a tone that is not the one the
index pins cannot pass.

## Preparation

The one piece a source tree cannot carry is the built component, because a
package's `plugin.wasm` entry must not be committed here:

```sh
tools/build-loader-live-gate-fixture.sh --prepare
```

`--prepare` verifies the tracked bundles and manifests are current, compiles the
SDK guest for `wasm32-unknown-unknown`, encodes it into a component exactly as a
published package is built, and stages complete deployable packages - manifest,
component, `config.toml` (`mode = "loader-live"`) and verified client bundle -
under `.analysis/loader-live-gate/plugins`. Nothing untracked is left in
`examples/`. Preparation does not run the gate and does not claim a gameplay
result; it is the step the harness performs before starting the server.

## Running the gate

Run the automated real-client gate for any supported Loader platform:

```sh
python3 -m tools.harness run loader-live --platform fabric
python3 -m tools.harness run loader-live --platform neoforge
python3 -m tools.harness run loader-live --platform forge
```

Each invocation prepares the deployment, creates an isolated Xvfb display, world,
game directory, permission/cache directory, server log, client log, and
`scenario.json` plus the canonical harness `result.json` receipt below
`.analysis/validation/`. The gate starts the production server, connects to
`127.0.0.1:25567`, accepts the exact Loader permission prompt through the
embedded MCP endpoint, runs `/loader_ruby` and `/loader_sapphire`, presses each
owner's exact button, verifies the corresponding real inventory grants, checks
both exact bundle cache identities, and requires the client to remain in Play. It
then presents both owner HUDs, updates Ruby, hides only Ruby, proves ordinary
jump input still works, and reconnects with the same cache. Loader wire protocol
3 is required.

Native Space also reports Ruby press/release. G reaches both owners; opening the
armed Ruby modal releases both actions before native key-up. Menu input is
suppressed, including declared Escape while closing inventory or a Loader modal.
Declared F2/F11 report both edges while vanilla writes a screenshot and toggles
fullscreen on/off. Mixed valid/invalid named-key batches in press and respawn
must fail before movement or plugin actions. Reconnect resets counts and
reinstalls bindings. Named input invokes Minecraft's actual callback, not OS
hardware emulation.

The sound gate additionally needs PulseAudio-compatible `pactl`/`parec`. It
creates a private null sink and selects it only in the isolated Minecraft profile.
It disables vanilla music there, records actual stereo 48 kHz float32 audio to
`audio.f32le`, and removes the sink on exit; the desktop default sink is untouched.
Spectral measurements cover personal playback, quarter volume, pitch 1.5,
near/mid/far world attenuation, simultaneous owners, owner-local and foreign stop,
disconnect silence, reconnect silence and newly requested playback. `result.json`
records each sample's byte range, RMS and 440/660 Hz amplitudes; chat is an
ordering barrier, not proof of playback.

Screenshots under each run's `screenshots/` directory wait for the real loading
overlay to disappear. `passed` covers protocol, view/HUD, inventory, input and
measured audio checks; `ui_visual_review` explicitly remains required. Inspect
the images for both HUDs, updated text, owner-local removal and no stale HUD after
reconnect before claiming rendering/lifecycle acceptance.

The owner-approved Forge Xvfb profile sets `earlyWindowControl=false`: Minecraft
creates its normal game window instead of the failing FML early-window GL context
handoff. The real game renderer and HUD are still exercised; Forge's early-window
GL features are explicitly outside this gate's evidence.

For manual inspection, prepare the deployment and start the server with:

```sh
tools/build-loader-live-gate-fixture.sh --prepare
cargo run --bin mc-server -- --config examples/loader-live-gate/playable.toml
```

and launch one isolated client with a per-run MCP bearer token:

```sh
SOLARIS_CLIENT_MCP_TOKEN=change-me \
python3 -m tools.harness client --platform <fabric|neoforge|forge>
```

After accepting the permission prompt, `/loader_ruby` and `/loader_sapphire`
open owner-specific screens and grant their owner block carriers; placing and
breaking them exercises the distinct world projection and presentation path.
Add `hud`, `update`, or `hide` to either command to open the owner's non-modal
HUD, change its declared text, or remove that exact instance. A HUD is its own
view instance, separate from the modal: `hud` closes the modal that owner's own
command opened, and no HUD open, present or close touches a modal or another
owner's view. Screen-mode requests keep their verified item/block display and
interaction buttons.

## What each owner declares

One client bundle per owner, `rich-content`, schema 2, one archive per loader.

| | ruby-live | sapphire-live |
|---|---|---|
| Screen (`settlement`) | `ruby-live:showcase` "Ruby Loader Fixture" | `sapphire-live:showcase` "Sapphire Loader Fixture" |
| HUD (`hud`) | `ruby-live:hud` "Ruby HUD" | `sapphire-live:hud` "Sapphire HUD" |
| Input HUD (`hud`, no widgets) | `ruby-live:input` | `sapphire-live:input` |
| Block / item | `ruby-live:ruby_block` / `ruby-live:ruby` | `sapphire-live:sapphire_block` / `sapphire-live:sapphire` |
| Sound | `ruby-live:tone` (440 Hz) | `sapphire-live:tone` (660 Hz) |

The input HUD declares the key bindings the client installs with the view:

| Key | ruby-live | sapphire-live |
|---|---|---|
| `key.keyboard.g` | `key_press` / `key_release` | `key_press` / `key_release` |
| `key.keyboard.space` | `jump_press` / `jump_release` | - |
| `key.keyboard.escape` | `escape_press` / `escape_release` | - |
| `key.keyboard.f2` | `f2_press` / `f2_release` | - |
| `key.keyboard.f11` | `f11_press` / `f11_release` | - |

Each id is the owner's own, prefixed with its plugin id, and the view the owner
opens on a join carries every press and release action enabled. The fixture
counts an edge only when the server admits the corresponding view action against
that live instance, so a run whose client produced no real key edge reports zeros.

One HUD open is outstanding per owner and connection. While an open the owner has
not answered is pending, the fixture keeps only the latest requested model and
visibility rather than asking for a second instance: the answer applies that
latest state to the instance and revision the owner returned - presented, or
closed when the latest request was a hide. A refused open releases the pending
state and is logged with the owner's own reason instead of being retried
automatically; the next explicit command asks again.

## Commands

Each owner answers its own root only:

| Command | Effect |
|---|---|
| `/loader_<owner>` | Grants one block carrier and opens the owner's modal screen |
| `/loader_<owner> hud` | Closes the modal instance this connection already holds for the owner, then opens (or refreshes) the owner's visible HUD |
| `/loader_<owner> update` | Presents the same HUD instance with its updated text |
| `/loader_<owner> hide` | Closes the HUD instance this connection holds |
| `/loader_<owner> input_status` | Reports the per-player G/Space phase counts |
| `/loader_<owner> input_modal` | Opens the modal on the next declared press (Ruby) |
| `/loader_<owner> edge_status` | Reports the Escape, F2 and F11 counts (Ruby) |
| `/loader_<owner> sound` | Plays the owner's tone |
| `/loader_<owner> sound_stop` | Stops the owner's tone |
| `/loader_<owner> sound_quiet` | Plays at quarter volume (Ruby) |
| `/loader_<owner> sound_pitch` | Plays at pitch 1.5 (Ruby) |
| `/loader_<owner> sound_world x y z` | Plays at that world position (Ruby) |
| `/loader_<owner> sound_foreign_stop` | Asks to stop the *other* owner's tone (Ruby) |

`/loader_ruby input_status` and `/loader_sapphire input_status` report per-player
G/Space phase counts. `/loader_ruby input_modal` opens a modal on the next
declared press; `hud` disarms it. `/loader_ruby edge_status` reports Escape, F2
and F11 counts. These server replies provide ordering barriers for negative input
assertions, rather than treating a timeout as success.

`hud` closes only the modal instance this owner opened on this connection - the
fixture asks for that close itself, because a HUD never closes a modal - and it
does not touch the other owner's views. `update` and `hide` address
the exact HUD instance this connection holds, and a second `hide` with nothing
held stages no close.

`/loader_ruby sound` and `/loader_sapphire sound` play their personal tones;
`sound_stop` stops that owner's tone. Ruby also provides `sound_quiet`,
`sound_pitch`, `sound_world x y z`, and `sound_foreign_stop` (which the server
refuses, because this package does not own the other owner's sound id). A
`sound_world` whose three coordinates do not parse is reported as a usage line
and stages no playback. These fixture commands call the public sound API rather
than a client test-only playback hook.

## Native tests

`crates/mc-plugin-host/tests/loader_operations.rs` deploys the same component
twice and drives it through the host boundary: both owners answer only their own
root and own only their own ids, the counters advance only from admitted view
actions and reset on the connection that left, a refused open is never presented
against, an update uses the revision the owner answered with, and a mode an owner
has no answer for stages nothing. It requires the guest to be built and started,
so it fails rather than skips when the component or the contract drifts.

## Compatibility

The complementary no-Loader compatibility gate is:

```sh
python3 -m tools.harness run core-client
```

It proves that a server-only `basic-economy` plugin accepts the ordinary
real-client profile and opens its server-owned `/economy` menu, while the same
client profile without Solaris Loader is rejected by this client-required
fixture during Configuration with an explicit Loader-required reason.
